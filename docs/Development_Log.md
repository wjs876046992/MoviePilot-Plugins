### Rsync115Sync v0.5.10 —— 源端游标按 mtime 判据导致「永久静默漏扫」

用户问：「这两处都有媒体，但实际生成的 strm 只有 6 个，是什么问题呢，重启插件数据丢失？」
紧接着补充了一个自己的猜测：「我发现是115上没有这些文件，是因为cd2没上传？」

后者很接近真因，但方向刚好相反 —— **CD2 没有失败，是它从来没有东西可传。**

#### 现象

某季 22 集，只有 6 集有 strm。缺的 14 集在系统里**没有任何痕迹**：
台账 0 条、无告警、插件日志里连文件名都没出现过。

#### 根因（用 ctime 与日志双向证实）

`stat` 显示这 20 个 mkv 的 `nlink` 都是 2 —— 是硬链接，而硬链接会**保留源端 mtime**：

| | mtime（被保留） | ctime（真实落地） | 有 strm |
|---|---|---|---|
| 6 集 | 09:25–09:34 | 09:26–09:38 | ✅ |
| 14 集 | 09:32–09:36 | **09:45–09:58** | ❌ |

扫描判据是 `getmtime > 游标`，而游标每轮推进到 `now_ts`。
日志把因果钉死：

```
09:30:02 游标=09:20:00 候选=23 → 入队 3（ctime 09:26–09:29）
09:42:37 游标=09:30:00 候选=7  → 入队 3（ctime 09:38）
（游标此后 = 09:42:37+，而 14 个文件的 mtime 是 09:32–09:36，永远落在窗口外）
```

**验证补充**：直接查 CD2 挂载点，mkv 恰好也是那 6 集；日志中去重 S04 集号，
同样只有那 6 集。所以 CD2 上传队列是空的 —— 那是**正确**的，不是故障。

「重启丢数据」也不成立：重启发生在次日，文件落地早了一天，而 6 个 strm 的
时间戳都在重启之后。

#### 为什么值得记

1. **症状与根因距离极远**：用户能观察到的只有「strm 少了几个」，而真因是
   文件系统层面的 mtime/ctime 语义差异。中间隔了队列、游标、上传、CD2、strm 五层。
2. **完全静默**：没有一条日志、没有一条告警。若不是用户逐个目录对账，永远发现不了。
3. **不是边缘情况**：qBittorrent 做种硬链接、`cp -p`、`rsync -t`、
   Trash/Link 类工具都会保留 mtime。媒体入库几乎必然经过其中一种。
4. **它解释了一个更广的问题**：任何走「硬链接 + 保留时间戳」入库的媒体都可能中招，
   而不止这一季。

#### 做法

- 判据改为 `max(mtime, ctime)`（ctime 无法被拷贝保留）。
- **冷却基准保持 mtime**：ctime 回答「何时出现」，mtime 回答「何时写完」，
  用错哪个都会产生一类静默错误。
- 重叠窗口保留（它负责同秒批量落盘，与本缺陷是两件事）。
- 新增**定向补传**：`path_filter` 参数让补传可以只处理某一季。历史漏掉的文件
  不会因修好判据而自动回来，补传是唯一补救路径；而原来只能全量补传。

#### 测试

11 条新用例，其中 9 条已用修复前的代码验证会失败。含两条「接入点」断言
（函数写对但没被调用 = 没修）。

#### 一个只有真机才抓得到的缺陷

定向补传做完、单测全绿之后，对着 NAS 实际打了一次请求：

```
POST /backfill_scan {"filter": "天蝎 (2014) .../Season 04"}
→ {"success": true, "data": {"count": 20, "filter": "", ...}}   ← filter 是空的
```

`/backfill_scan` 原本注册成 **GET**，而它从 `body: Optional[Dict]` 读参数 ——
FastAPI 不会把 query string 塞进 body 形参。于是筛选被静默丢弃，
HTTP 200、`success: true`，**看起来完全正常**。

签名合法、逻辑正确、5 条单测全过 —— 静态检查没有任何信号。
改成 POST 后同一请求立刻返回 `count=20` 且样例正确。

已加 `test_scan_endpoint_is_post_not_get`。这条经验的普适形式：
**「参数传进去了吗」不是靠读代码能确认的事**，它取决于框架如何绑定，
只能打一次真实请求看返回。

### Rsync115Sync v0.7.0 —— 失败清单只剩一份，忽略只剩规则（精简阶段 1）

用户要求「完成剩下的阶段，做好代码 Review 和功能测试」。阶段 1 收敛的是
**失败态**：同一件事此前有两份清单、两条相反的结算语义。

- **症状**：传不上去的文件，有时每 2 小时刷一次「存在未完成项」，有时报一次
  就再也不提。用户无法从通知判断"到底还有没有事"。
- **根因**：对账失败同时存在内存与落盘两份清单；冷却就绪路径把失败项留在队列里
  无限重试（于是每轮都发通知），存量补传路径把失败项放进清单后只能等人工
  （于是报一次后永久沉默）。忽略同源：规则与台账文件行两份存储，写入只写一份。
- **做法**：`failed` 成为唯一的传输失败状态（`fail_reason` 区分缺失/残缺）；
  两条路径共用一份清单，retry 候选从它取；通知只在清单**变化**时发；
  忽略删掉台账那一份，遗留行转成 exact 规则后删行。详见 DEVELOPMENT §4.0t。

#### Code review 抓出两条会丢数据的缺陷（均已修复）

1. **忽略迁移覆盖用户规则**：迁移函数本来放在 `_open_store()` 里，早于
   `init_plugin` 载入 `ignored_files`。它往仍是空的规则列表追加迁移结果并
   `save_data`，用户原有的 `contains` 规则被永久覆盖。修法：迁移移到规则载入**之后**。
2. **旧异常清单被静默丢弃**：迁移用 `_allow_legacy_seed` 做判据，而它等价于
   `legacy_migrated != 1` —— 所有已有台账的老用户都已经是 1，于是升级后
   第一次启动跳过迁移，随后清理逻辑又删掉旧键。修法：改用独立的 meta 标记。

另外 4 条真实问题：恢复项只摘缓存导致重载复活（force/backfill/非视频路径
不会再写 status）；失败清单非空就独占 cron 会饿死补传；忽略只摘缓存导致
`/items` 立刻又显示 `broken`；把行改成 failed 时不清其它视图缓存，造成
台账与内存分叉。都已修复并配了回归哨兵。

#### 功能测试：这一次真的跑在真实后端上

此前本机没有 `../MoviePilot`，整个套件只能报 `ModuleNotFoundError`。这次发现
**NAS 的 `mp3` 容器本身就是完整后端**：

pytest 是从 `/tmp` 里一份纯 Python 包注入的（容器没有 pip，不改动它的环境）。
结果：**23 failed / 717 passed**，与 v0.6.0 的基线 **23 条失败逐条相同**
（全部是既有失败），通过数 703 → 717。失败集合比对仍然按逐条 diff，不看数量。

> 期间多出的 1 条冷却队列条目是源端扫描自然发现的真实新剧集。

### Rsync115Sync v0.8.2 —— CD2 在传核对统一到失败判定（TODO 10.5）

最后一处「同一判据两套使用」的收敛：CD2 的「在传/排队」核对此前只保护 strm
疑似那条路，对账失败那条路完全不查 —— 大文件还在上传时会被立即判
缺失/残缺并报警，还消耗一次重试计数。

- **hold**：结算判失败前批量问一次 CD2，在传的条目本轮不判失败；ready 轮
  **留在冷却队列**（出队会失去跟踪）。
- **revert**：巡检入口把「上轮判失败、此刻 CD2 在传」的条目移回冷却队列
  （rsync 刚写完时 CD2 可能还没扫到挂载点）；达上限的人工处理项不自动回退。
- 判据只有 `_cd2_in_flight_for` 一个；三态语义（查不到≠没在传）、
  FINISH/ERROR 刻意排除、卡死豁免上限原样保留。

#### 真机验证的假阴性教训

注入假 CD2 队列验证 hold 时，任务 `dest_path` 用挂载点路径
（`/CloudNAS/115/...`）得到「匹配不上」—— 真实队列里是**云端路径**
（mount 映射的 `/115open/HomeTheater/...`）。同一路径的两套坐标，
用错一套就是静默假阴性。另外 60MB 内网直传几秒完成，「真实在传窗口」
抓不到，行为验证只能注入队列。

真机结果：hold →「⏳ 对账不一致但仍在传，本轮不判失败」；revert →
failed 行移回冷却队列（candidate，基准=冷却时长 1/4）。套件 14/738 零回归。

### Rsync115Sync v0.8.1 —— 重试预算：计数、停止、告警（原始需求收尾）

用户最初的「上传失败自动重试 3 次后告警」在三轮精简后落地：`retry_count` +
`exhausted_at` 与 failed 值同记录；首次失败不计数、retry 轮失败 +1、达上限移出
自动重试并单独告警一次；手动重试清零。code review 6 条全部修复，其中两条
会导致数据/语义错误：恢复时不清预算（残留 `exhausted_at` 在下一次失败时复活，
文件永远不自动重试）、开关关闭时也计数（用户一开开关立刻"达上限"，通知宣称
3 次实际 11 次）。

#### 真机验证卡了两次的地方都不是代码问题

探针放在映射 src 下制造持续失败，结果**源端游标扫描把它重新入队** ——
`_ingest_stamp = max(mtime, ctime)`，任何 `touch` 都刷新 ctime，文件在
failed/candidate 间循环，retry 轮被 ready 抢占，计数纹丝不动。可靠验证要
临时关掉扫描开关 + 直接 UPDATE 台账行。第二个坑：直改数据库后运行实例的
`LedgerMapping` **内存缓存不会刷新**，必须重载插件。两次"达上限没触发"
都是验证方法问题 —— 与 DEVELOPMENT §4.0s「守卫必须重建视图（等价重载）」
是同一条原则在真机上的再现。

#### 最终端到端（全部在真实宿主上）

首次失败 count=0 → 定时 retry 轮 +1 → 手动 retry 先清零再计数 → 达上限
`exhausted_at` 落位 + 告警推送 + 看板 `exhausted=True` → 达上限后手动重试
count 归零。真实后端套件 14 failed / 733 passed（相对 0.8.0 零回归）。

### 三、Rsync115Sync v0.5.8 —— CD2 Token 保存后静默丢失

用户报「cd2 已经提供 token，能测试功能是否正常吗」。测试时先查错了表
（`systemconfig`），实际配置在 Postgres 的 **`plugininstance.config_data`**。

排查中发现一个真 bug：`_api_save_config` 把 token 只赋给实例属性
`self._cd2_api_token`，而方法末尾的 `update_config(config)` 持久化的**是那个字典**，
字典里没有 token。前端又按约定在「已配置」状态下把空 token 的键整个删掉
（表示"保持不变"），于是后端拿不到值、也不写回。

**症状极难自查**：保存返回成功、开关显示已开启、当次会话里 `cd2_api_token_set`
为真（读内存属性）—— 一路绿灯，**只有重载插件后 token 才消失**。

修法：token / 地址 / 开关都以最终生效值回写进 `config` 字典再持久化。
新增 AST 守卫，已用修复前的代码验证它会失败。

同时清掉 4 处**后端返回给用户**的字面星号（看板纯文本区块、`window.confirm`、
聊天纯文本回复三者都不解析 Markdown）。日志里的 `**` 刻意保留。

### 五、Rsync115Sync v0.5.9 —— 配置页顶栏与保存按钮固定

用户要求：「配置页面，顶部 title 包含高级设置的按钮部分固定」。

**这轮最大的收获不是修好了什么，而是暴露了一个方法论问题。**

#### 症状与根因

滚动配置页时标题栏（连同「高级设置」开关）与底部「保存配置」一起被滚出视口。

根因必须实测才能拿到：宿主把插件配置包在
`<VDialog scrollable>` → `.v-card` → `.v-card-text.pa-0` 里，而那一层
`.v-card-text` 的高度由 flex 决定、CSS 里没有可被百分比引用的 `height`，
于是插件内所有 `height:100%` 都解析成 `auto` —— 滚动实际上发生在**宿主那一层**，
标题栏与底栏作为它的普通内容一起滚走。移动端走 `fullscreen` 分支，
滚动容器换成 `.v-overlay__content`，同样在插件之外。

#### 第一次判断是错的，而且"验证"过

第一版照搬看板 `Page.vue` 的 flex 高度链（根 div 加 `h-100`），并且用一个
**手写 CSS 的简化 harness** 测出「桌面端修好了」，据此写下双机制设计
（桌面 flex 链、移动 sticky），还加了一条测试断言**禁止使用 sticky**。

真实结构下复测：桌面端根本没修好。两个原因叠加：

1. harness 缺 `.v-dialog` 类 —— `VDialog.css` 的选择器是
   `.v-dialog > .v-overlay__content`，缺类则整套尺寸规则不生效；
2. scoped 哈希取错 —— 正则先命中了 CSS **注释文本**里的 `[data-v-xxxx]`。

**简化 harness 里"看起来对"= 没测。** 这与流程文档 2.2「外部事实必须先落到
真实数据上」是同一条，只不过这次违反它的地方是测试工具本身。

#### 做法

`position: sticky` + 放开**本卡片**的 `overflow`（它继承 `overflow:hidden`，
会成为 sticky 的最近裁剪祖先使其静默失效）。

放开范围是逐项实测定的，不是推出来的：

| 放开哪一层 | 标题栏 | 保存条 |
|---|---|---|
| 都不放开 | ✗ top=-1636 | ✓ |
| **只放开本卡片** | ✓ top=24 | ✓ bottom=876 |
| 只放开宿主 `.v-card` | ✓ | ✗ bottom=2536 |
| 只放开宿主 `.v-card-text` | ✓ | ✗ bottom=2536 |

放开宿主那两层会让底栏失效。另外 `:deep(.v-card)` 编译成后代选择器，
够不到作为**祖先**的宿主卡片 —— 写了也是死代码，故写成一条测试禁止它。

#### 验证

用 headless Chromium 加载**真实构建产物 + 真实 Vuetify 样式表 + 宿主真实 DOM**：

| | 桌面 1280×900 | 移动 390×844 |
|---|---|---|
| 修复前 标题栏 | ✗ `top=-1672` | ✗ `top=-1704` |
| 修复后 标题栏 | ✓ `top=24` | ✓ `top=10` |
| 修复后 保存条 | ✓ `bottom=858`/900 | ✓ `bottom=844`/844 |

回归用失败集合比对：186 条失败逐条相同（全部来自无后端），通过数 180 → 186。

### 六、Rsync115Sync v0.6.0 —— 状态迁移不得删行（精简阶段 0，本轮主线之一）

用户先提了「上传失败自动重试 3 次后告警」的需求；分析后发现重试早已存在且**过量**

「先不做，业务逻辑本身有点复杂了，需要先精简」。梳理业务路径后确立精简主线：
**一个文件一条记录、一个状态字段，队列只是它的查询视图。**

本轮（0.6.0）是精简的地基，同时修掉三个静默 bug：

1. **状态迁移删行**：PQ/SW/SS 是同一张 `files` 表按 status 切的三个视图，
   但业务代码用「旧视图 pop + 新视图赋值」表达"移动"—— `pop` 等于 `DELETE`，
   正交列（成功时刻、补生成标记、入库来源、冷却基准）全部清零。当前进程靠内存

修正两处与后端不符的文案（「入库监听是总闸」—— 实际只拦 webhook；
`source_scan_enabled` 注释引用已废弃常量还说反了默认值）。

新增 `test_state_transition.py`（15 条，不依赖后端，`store.py` 按文件路径加载），
**缺陷版对照 14 失败 / 1 通过** —— 通过的那条记录的正是 pop 的破坏性。回归用

> **执行过程里踩了一次本仓自己的坑**：做基线对照时用了 `git stash push -- <插件目录>`，
> 而当时有一个并发 agent 正在写 `src/`。stash 把它当时的 `.vue` 改动一起卷走，

> 正确做法是 **`git worktree add /tmp/x HEAD`**：基线侧与当前侧各跑各的，工作树全程不动，
> 不存在和并发写者抢文件的可能。**有并发写者时不要用 stash 做基线。**

### Rsync115Sync（`plugins.v3/rsync115sync/`）

**版本：** v0.5.5 → v0.5.6（本仓改动，未同步上游）

#### 问题：一个自我维持的破坏环路

用户的原话：

> 在添加为疑似时能否通过 cd2 的 API 查询是否属于正在排队或者正在上传，因为存在
> 需要真实上传的，也会放疑似，不清楚情况时会一直删除一直重传，目前我是人工去
> cd2 确认的

本插件的疑似判据是「rsync 报成功，宽限期内没有 `.strm`」，而宽限期默认 **5 分钟**。
一条 8 GB 的文件在 CD2 侧要传几十分钟，于是：

    同步报成功 → 5 分钟后判疑似 → 点「删旧重传」
    → 删掉**正在上传**的文件 → 从零重传 → 又传不完 → 又判疑似 → …

每一轮都真实地作废掉已经传完的几个 GB，而且没有任何一条日志说明发生了什么。

在线上实例上直接验证到了这个场景：查询时恰有两条正在上传的条目
（`预处理中 5.7 GB / 8.1 GB`、`预处理中 0.9 GB / 3.6 GB`），
它们正是会走进上述环路的文件。

#### 方案：查询 CD2 上传队列，只做「降噪」不做「放行」

新增 `cd2.py`（纯函数：gRPC-web 编解码 + 路径匹配）与 `cd2_ops.py`（插件侧接线），
在三个位置接入：

| 位置 | 行为 |
|---|---|
| `_strm_check` 到期转疑似前 | 正在传 ⇒ **留在观察期**，不转疑似、不通知 |
| 已有疑似清单 | 正在传 ⇒ 移出清单，附实时进度（第三条清理出口） |
| `_retransfer_keys` 删除前 | 正在传 ⇒ **拒绝删除**并给出进度与预计 |

第三个位置是**唯一挡住真实破坏**的地方：看板勾选、`/rsync_strm retry <序号>`、
`/rsync_retry <文件名>`、全部重传四条入口各有各的前置判定，其中有些针对早已在
清单里的条目、根本不经过「新发现」判定 —— 唯一的共同必经点就是删除。

**设计红线**：查询结果绝不用于判定「上传成功」。查不到（没开、地址错、Token 过期）
一律按原有判据处理并限频记 warning；CD2 状态为 `FINISH`（已完成但没有 strm）
仍然照常报警 —— 那正是要抓的异常。把「不在队列里」当成「上传失败」或把
「在队列里」当成「上传成功」，都会重蹈 v0.3.0 删掉的「云端可见性」错判。

#### 三个在验证阶段才暴露的实现细节

1. **失败与成功的 `grpc-status` 藏在两个不同位置**：成功在 trailer 帧（响应体末尾
   的 `0x80` 帧），鉴权失败在 **HTTP 响应头**，而两种情况 HTTP 码**都是 200**、
   失败时响应体为空。只读 trailer 的实现会把「token 无效」读成「队列为空」 ——
   于是保护看起来在工作、实际一次都没生效，日志里连失败都没有。
   *实测踩到*：错误 token 返回了「0 条任务」。
   修复后同一场景正确返回 `None`（查不到）并进入静默期。

2. **挂载路径与云端路径不是同一个字符串空间**：CD2 报的 `mountPoint` 是
   **它自己看到的宿主机路径**（`/volume2/CloudNAS/115`），而插件配置的 `dest`
   是**容器内**路径（`/CloudNAS/115`）。`dest.startswith(mountPoint)` 恒为假，
   但两者描述同一个挂载。改为按**路径分量**对齐后取最长匹配。

3. **卡死的任务会变成掩护**：若有任务永远停在 `预处理中`，豁免会让对应文件
   **再也不出现在疑似清单里** —— 用户看到"一切正常"，而云端文件其实是残缺的。
   一个把真问题藏起来的保护比没有保护更糟。因此豁免有期限：移动中状态 6 小时、
   暂停状态 24 小时，超时后自动退回原判据并记一条 warning 提示去 CD2 确认。
   CD2 不报上传开始时间，因此"卡住"由**本地已等待时长**推断。

#### 配置

默认**关闭**，需要用户在 CD2 网页「API Tokens」页生成 Token。理由：拿不到 token
时功能会静默失效，若默认开启，用户会以为它在工作。

配置页的 Token 字段**从不回显**已保存值，只回 `cd2_api_token_set` 布尔量；
留空保存＝保持不变（后端按「键存在但为空」判为清除，因此前端保存前会把空串的键
整个删掉 —— 否则用户每保存一次无关配置就静默丢掉一次 token）。
看板明确区分「没开」「开了但没填 Token」「开了在跑」三种状态。

#### 测试

`tests/v3/rsync115sync/test_cd2_query.py`（21 条）用**线上抓包的真实报文**做
回归样本，而不是手工构造 —— 上面三个细节每一个都曾在探测阶段把一个"看起来正确"
的实现判错；手工样本会把同样的误解写进测试里，于是测试全绿而线上全错。

覆盖：帧/消息/trailer 分离、空队列（消息体长度为 0）、鉴权失败位置、
挂载路径分量对齐与兄弟挂载、精确匹配（非前缀）、`FINISH` 不得算作在传、

### P115StrmHelper（`plugins.v3/p115strmhelper/`）

**版本：** v3.4.6 → v3.4.7（本仓改动，未同步上游）

**提交：** `3fb390a`

#### 问题：通知只说「1 个」，用户不知道是哪个文件

用户收到：

```
✅【115网盘】生活事件生成 STRM 文件

📄 生成STRM文件 1 个
```

原话是「这是通知，能具体到是哪个文件吗」。N=1 时既不知道文件，也无法判断是不是
自己在等的那个事件，只能再去翻日志。

#### 方案：计数与展示分离

目录事件（整季上传、整目录复制）会一次展开上千个文件，全列会撑爆消息渠道，
只列前几条又会让「N 个」失真。因此把两件事拆开：

| 关注点 | 行为 |
|---|---|
| 计数 | 照常累加，`生成STRM文件 500 个` 永远是真实数量 |
| 展示 | 路径只保留前 `_NOTIFICATION_ITEM_LIMIT`（默认 10）条，其余折成 `... 还有 490 个` |

计数与渲染抽到 `helper/life/notification.py` 的 `NotificationBatch`，**只依赖标准库**，
因此可在无 MoviePilot 后端的环境下直接单测 —— 放在 `client.py` 里做不到，那个模块
一导入就触发 `app.*`。

#### 顺带修掉的静默丢失

原实现是「取计数 → 发送 → 归零」。发送是同步 HTTP 调用，耗时几百毫秒到几秒；
期间若恰好有新事件累加计数器，**归零会把它们一起抹掉**，那次事件不推送也不留痕。

改为「先摘下当前批次 → 立刻换新批次 → 再发送」，发送期间的累加落进新批次。
这条时序约束写在 `_send_notification` 的注释里，防止后续改动退回旧写法。

#### 测试

`tests/v3/p115strmhelper/test_life_notification.py`（7 条，`--noconftest` 可跑）：
单文件带路径、超限折叠、批量计数大于列举数、上限为 0 仍计数、未知类别报错。

#### 部署时暴露的一个坑

`git pull` 后重启，日志仍显示 `加载插件：P115StrmHelper 版本：3.4.6`。
原因是文件变更发生在**旧进程退出、新监听器启动之前**，新 monitor 没看到事件，
`/app/app/plugins/<id>/` 的副本没同步。`touch` 一个文件触发监听后即同步完成。

判断方法：直接比对两边：

```bash
docker exec mp3 diff -rq /config/local_plugins/plugins.v3/<id> /app/app/plugins/<id>
```

以后遇到「pull 了但版本没变」，先查这个而不是反复重启。

而它读的是由异步 watcher 填充的 refs —— 那一瞬间 refs 还是空数组，已有配置被读成

修法：聚合改为直接解析 `config.*` 原始字符串，与时序无关；四种格式的解析抽成

#### 小结（可复用的结论）

1. **Vue watcher 是异步的** —— 在 `Object.assign` 之后同步读取由 watcher 派生的

2. **"渲染出来再藏掉" vs "让它压根不渲染"** —— 与同仓 `Rsync115Sync` 的结论一致：

旧架构中，微信通知与第三方通知耦合在 `MySender` 内部，通过 `_wechat_available` 标志控制降级。新架构将两者解耦：

- **第三方通知**：通过 `MySender` 发送（Server酱、PushPlus、IYUU 等），由 `notification_token` 配置项控制
- 两种通知独立并行，互不影响

核心变更：
- 移除 `_wechat_available` 标志和 `_send_wechat` / `_send_v2_wechat` 方法
- `MySender.__init__` 不再接收 `func` 参数，仅负责第三方通道
- 所有通知点（cookie 失效、二维码推送、IP 变更、测试通知）统一为双通道模式
- 修复 `change_ip` 中仍调用已删除的 `diy_channel="WeChat"` 问题

#### 新增配置项

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| `use_mp_notify` | 是否使用 MP 内置通知 | `True` |
| `pinned_ips` | 固定可信IP，始终保留在可信IP列表中 | `""` |

`pinned_ips` 与检测到的IP通过 `_merge_pinned_ips()` 合并去重后填入企微应用。

#### 缺陷修复

- **`parse_cookie_header` 空值防御**：旧代码对空字符串、无 `=` 字段做了跳过处理，重构时误删。补回 `if not cookie_header: return []` 和 `if '=' not in item: continue`
- **CookieCloud 返回格式兼容**：适配 `download()` 返回 tuple 和非 tuple 两种情况
- **日志级别**：8 处 `debug` → `info` 误提升已恢复（后台循环、扫码等待、任务取消等正常流程）

#### 测试通知功能

详情页新增"测试通知推送"按钮，通过 `GET /test_notify` API 端点触发，同时测试 MP 内置通知和所有第三方通道，返回成功/失败计数。

### WatchSync（`plugins.v2/watchsync/`，新增）

**版本：** v3.0.0

#### 功能概述

Emby/极影视观看记录跨用户同步插件。当组内某用户播放、收藏或标记媒体时，自动同步到组内其他用户。

#### 支持的同步类型

| 事件 | 同步内容 |
|------|----------|
| `playback.pause` / `playback.stop` | 播放进度（PositionTicks） |
| `user.favorite` / `item.favorite` / `item.rate` | 收藏状态 |
| `playback.scrobble` / `item.markplayed` | 标记已播放 |
| `item.markunplayed` | 标记未播放 |

#### 片尾自动标记已播放

问题：`playback.stop`/`playback.pause` 在片尾触发时仅同步进度，不标记已播放。依赖 `playback.scrobble` 但该事件在部分 Emby 配置下不触发。

修复：在 `_handle_playback_event` 中检测 `position_ticks >= RunTimeTicks * 0.9`，满足时额外调用 `_sync_played_status_to_targets` 标记目标为已播放。

#### 极影视支持

- 通过 `ModuleManager` 获取 Emby/ZSpace 服务器实例
- 自动发现本机极影视：读取 `/zvideo/zvideo.db` 获取凭证，探测 8021 端口
- `LocalZSpaceInstance`：极影视 Emby 兼容层封装，支持 `get_data` / `post_data`
- 极影视源端进度轮询：`BackgroundScheduler` 定时拉取继续观看列表，检测变化后触发同步

#### 防循环机制

`SyncLoopProtector`：同步操作成功后，将目标用户-媒体-操作类型加入保护缓存（TTL 30秒）。短时间内收到的回弹事件自动跳过。

#### 代码质量修复（Review 后）

- 删除 `_add_to_ignore_cache` 死代码（引用未初始化的 `_sync_ignore_cache`）
- `_init_database()` 从 `__init__` 移至 `init_plugin`，避免 `PLUGIN_DATA_PATH` 未就绪
- 约 80 处 `logger.info` 降为 `logger.debug`（匹配过程、API 详情、属性检查）
- 删除不应提交的 `yarn.lock`

### 代码审查要点备忘

本次 Review 发现的典型问题，后续开发中注意避免：

1. **版本号一致性**：`plugin_version`、`package.json` 的 `version`、`history` 最新三处必须一致
2. **日志级别**：中间匹配过程、API 详情、属性检查用 `debug`；实际操作结果、状态变更用 `info`
3. **删除方法后检查调用点**：`_send_wechat` 删除后，`change_ip` 中的 `diy_channel="WeChat"` 调用未同步清理
4. **属性初始化**：引用 `self.xxx` 前确保 `__init__` 中已初始化
5. **防御性编程**：`cookie_header.split()` 等链式调用前检查空值
6. **`__init__` 中避免副作用**：数据库初始化等依赖运行时配置的操作放到 `init_plugin`
7. **不提交构建产物**：`yarn.lock`、`node_modules` 等不应进入插件目录

# 插件开发工作流

本文档规定本仓**后续所有插件开发**的标准流程。核心是三条硬性顺序：

```
先设计 UI  →  再罗列开发计划  →  最后执行开发
                    ↓
              迭代过程中同步记录文档
```

不是建议，是流程。下面每一节给出**为什么**、**怎么做**、**验收标准**，以及从
`p115strmhelper` 与 `rsync115sync` 两个插件近几轮迭代中提炼的实例。

---

## 0. 为什么是这三步

### 先设计 UI

用户对插件的全部认知来自两个页面（配置页 `Config.vue` 与看板 `Page.vue`）。
后端能力再完整，只要页面上找不到入口，对用户就等于不存在。

**实证（rsync115sync v0.5.6 → v0.5.7）**：CD2 上传队列核对做完了、测试全绿、
`USAGE.md` 里写着「强烈建议开启」——但开关被收在「高级设置」后面。
配置页默认收起高级区，用户填完映射里的「strm 目录」就以为配完了，
那个决定误报率的开关**从来没有出现在他的屏幕上**。

同一插件另一例：看板上解释「CD2 核对是否生效」的提示被嵌在
`v-if="watchingCount"` 里面。而这个保护的作用正是让文件**不进**疑似、
观察期归零——保护一生效，解释它的那行就跟着消失。**越有用越看不见。**

这两处都不是代码 bug，是**先写代码、后想界面**的必然结果：
界面的信息层级与代码的模块划分本来就不是一回事。

### 再罗列开发计划

计划的作用不是"写给人看"，而是**在动手前逼自己发现依赖与顺序**。

**实证（rsync115sync v0.5.6）**：`cd2.py` 的 gRPC-web 解析写完后才发现
「失败与成功的 `grpc-status` 藏在两个不同位置」——成功在 trailer 帧、
鉴权失败在 HTTP 响应头，而两者 HTTP 码都是 200、失败时响应体为空。
如果计划阶段就列「① 抓真实报文 ② 列出所有失败形态 ③ 再写解析」，
这个坑在写代码前就会暴露，而不是等到线上把「token 无效」读成「队列为空」。

### 最后执行开发

只做计划里的事。执行中发现的额外问题**先记进计划**再决定做不做，
不在执行阶段顺手扩大范围——那会让"这一轮改了什么"失去边界，
下一篇文档也写不清。

## 1. 第一步：设计 UI

### 1.1 产出物

动手写代码之前，必须先在对话里给出：

1. **页面结构草图**（ASCII 即可），标出每个区块在首屏还是折叠区；
2. **每个新增字段的位置**：哪个卡片、第几行、靠左还是靠右；
3. **每个状态的文案**：正常 / 警告 / 未配置 / 失败，四种都要有；
4. **移动端形态**：窄屏下这一块怎么排（见 1.3）。

### 1.2 首屏准入判据

一个控件该不该在首屏，只问一句：

> **新用户的第一个决定依赖它吗？**

| 属于 | 例子 | 位置 |
|---|---|---|
| 「要不要用这个功能」 | 总开关、启用入库监听 | 首屏 |
| 「用它需要先填什么」 | 目录映射、Token | 首屏 |
| 「判据松紧要多少」 | 宽限期、限流阈值 | 首屏（若直接影响误报率） |
| 「用了一段时间才想调」 | 催办时段、cron、超时、排除规则 | 高级区 |
| 「排除故障时才看」 | 依赖说明、补生成前提 | 高级区，或折叠说明 |

⚠️ **反例（必须避免）**：把「启用 X」放首屏、把「X 的关键参数」收进高级区。
用户填完入口就以为配完了，参数永远保持默认值——而那个默认值可能正是误报来源。
`strm 交叉验证` 在 v0.5.7 就是这么拆的：启用 + 宽限期 + CD2 核对上首屏，
催办提醒与依赖说明留高级区。

### 1.3 移动端三条规定（血泪教训）

1. **含输入框的行必须纵向排布**（`setting-row-stacked`）
   —— 横排下「左说明 + 右输入框」会互相挤压。前三次都靠调 flex 宽度解决，
   全部失败；改用纵向排布后"被挤压"在结构上不可能发生。
2. **标签放框外**（`.stacked-label` 在 `v-text-field` 之上），
   **不传 `label=` 属性** —— Vuetify 在 outlined 变体下会渲染两份 label
   （框内 + 边框缺口），用 CSS 藏掉已失败三次。
3. **超长不可断串必须包 `class="wrap-anywhere"`**
   —— URL / cron / 路径在浏览器眼里是"一个超长的词"，放不下就直接溢出，
   而卡片是 `overflow-hidden`，右侧控件会被整条裁掉，**没有滚动条可救**。

### 1.4 状态的四种形态

任何开关/功能都必须能回答「它现在到底是什么状态」，且四种状态在界面上**互不混淆**：

| 状态 | 文案示例 | 配色 |
|---|---|---|
| 未启用 | 「建议开启…」 | 中性/提示 |
| 已启用但缺前置条件 | 「已开启，但**尚未填写 Token**，实际未生效」 | 警告 |
| 已启用且在跑 | 「已启用：正在上传的文件不会被判疑似」 | 成功/中性 |
| 查不到/失败 | 「上次查询失败（已按原判据处理）：<原因>」 | 警告 |

⚠️ **不要合并成布尔量**。「看起来在保护」与「实际没保护」必须能分辨 ——
一个静默失效的保护比没有保护更糟。

### 1.5 状态提示的挂载位置

**提示必须挂在它描述的对象上，而不是挂在恰好会同时出现的邻居上。**

自检方法：把提示所描述的那件事推到极端（全空 / 全满 / 全失败），
问「这时提示还在吗？它该在吗？」

- `watchingCount=0` 时，「观察中 N 个」该消失 ✅
- `watchingCount=0` 时，「CD2 核对是否生效」**不该**消失 ❌（前者与它无关）

## 2. 第二步：罗列开发计划

### 2.1 固定格式

```markdown
## 目标
一句话：改完之后用户能做什么以前做不到的事。

## 非目标
明确列出这一轮「不做」什么（防止范围蔓延）。

## 任务清单
- [ ] 1.1 <可独立验证的一步>
- [ ] 1.2 ...

## 验证方式
每条任务对应的验证手段（测试 / 真机 / 日志）。

## 风险与依赖
可能踩的坑、需要先确认的外部事实。
```

### 2.2 三条硬规矩

1. **「风险与依赖」必须先做，不能边做边发现**
   —— 尤其是涉及外部系统（CD2 API、宿主行为、上游插件）时，
   先抓真实数据 / 读对方源码，把事实钉死再设计。
   `cd2.py` 的教训：照着 GitHub 上的 proto 写解析，而**线上实例的响应格式
   与之不同**（失败状态在 HTTP 头）。后来改成先抓真实报文、逐字段核对，
   才发现差异。
2. **任务粒度 = 可独立验证**
   「写解析」不是一步，「用真实报文验证解析」才是。
3. **用户可见的部分单独列一条**，与后端实现并列 ——
   不要把它们塞进「实现 XXX」里，那会被默认忽略。

### 2.3 计划确认点

计划写完先给用户看，确认后再开工。用户明确说「按你建议的做」才继续。

## 3. 第三步：执行开发

### 3.1 顺序

```
后端逻辑 + 单元测试  →  前端实现  →  构建  →  门禁  →  真机验证  →  提交部署
```

**Vue 模式插件（`get_render_mode()` 返回 `"vue"`）必须构建 `dist/`。**
`dist/` 就是运行代码，不重建等于没改 —— 用户会对着一份没在跑的代码报 bug。

### 3.2 每次改动必过的门禁

```bash
# 1. 前端构建（Vue 插件必做）
cd plugins.v3/<id> && ./node_modules/.bin/vite build   # 或 pnpm/npm run build

# 2. 联邦 CSS 门禁（硬约束，不可绕过）
python3 .github/scripts/check_federation_css.py

# 3. 版本门禁（严格模式，验证你改的插件）
CHECK_STRICT_PLUGINS=<plugin_id> python3 \
  .github/scripts/check_plugin_versions.py package.json package.v2.json package.v3.json

# 4. 语法与空白
python3 -m compileall plugins.v3/<id>
git diff --check
```

### 3.3 测试基线法（本仓特有，必须遵守）

本机常常**没有 MoviePilot 后端**，大量用例会因 `ModuleNotFoundError: app` 失败。
此时**不能报「全部通过」，也不能报「N 条失败」** —— 两个数字都不代表任何事。

正确做法是**取基线做差集**：

```bash
# 改动前
git stash push -u -- <改动路径>
uv run --with pytest pytest tests/v3/<id>/ --noconftest -q \
  --continue-on-collection-errors 2>&1 | grep '^FAILED' | sort > /tmp/before.txt
git stash pop

# 改动后
uv run --with pytest pytest tests/v3/<id>/ --noconftest -q \
  --continue-on-collection-errors 2>&1 | grep '^FAILED' | sort > /tmp/after.txt

diff /tmp/before.txt /tmp/after.txt && echo "无回归"
```

**判据是失败集合逐条相同**，不是失败数量相同 —— 数量相同也可能是一换一。
`rsync115sync` 的每轮迭代都用这个方法，通过数从 155 涨到 180 而失败集合纹丝不动。

### 3.4 真机验证（不可省）

单测覆盖逻辑，**覆盖不了**：真实响应格式、容器网络可达性、宿主的样式覆盖、
页面上"看不看得见"。

最少要做：

- 用**真实配置数据**跑一遍核心路径（不是构造数据）；
- 检查插件日志有无异常；
- 确认新版本号出现在 `加载插件：<ID> 版本：x.y.z`。

### 3.5 给用户可见文案的三条红线

1. **不得出现 Markdown 标记**（`**加粗**`、`` `代码` ``）。
   三条渲染路径全都不解析：看板纯文本区块、`window.confirm` 弹窗、
   聊天纯文本回复。要强调就用 `<b>`（模板内）或 `【】`（纯文本内）。
   **日志里的 `**` 不受此限** —— 那只给维护者看。
2. **不写内部术语**。用户不知道什么是「冷却队列」「补生成标记」，
   要写成「还在等上传时间」「让 strm 插件重新生成指针文件」。
3. **能行动的才写**。一句「这是有意设计，不是待办」如果没有下一个动作，
   就只是在自我辩护。

## 4. 贯穿全程：文档记录

### 4.1 四个文档，各管一段

| 文档 | 位置 | 写什么 | 何时写 |
|---|---|---|---|
| **用户文档** | `plugins.v3/<id>/USAGE.md` | 怎么用、每个选项什么意思、出问题怎么查 | 功能完成后，与代码同批提交 |
| **设计文档** | `plugins.v3/<id>/DEVELOPMENT.md` | 为什么这样设计、踩过什么坑、否决过什么方案 | 每轮迭代，与代码同批提交 |
| **开发日志** | `docs/Development_Log.md` | 跨插件的关键变更叙事 | 一轮迭代收尾时 |
| **索引 history** | `package.v3.json` 的 `history` | 面向市场页的版本说明 | 每次改版本号时 |

### 4.2 记录什么才有价值

**只有「当时不知道、事后很难重新推导」的东西值得写。**

✅ 值得写：

- **否决的方案及理由**
  「曾想把豁免做成布尔量，但那样卡死的任务会永久压住告警」
- **反直觉的事实**
  「失败与成功的 grpc-status 在两个不同位置（实测）」
- **症状与根因距离很远的**
  「保存一路显示成功，只有重载后 token 才消失 —— 因为持久化的是字典不是实例属性」
- **同一个坑踩了两次以上的**
  「flex 宽度调了三次都失败，真因是不可断长串撑宽了卡片」

❌ 不必写：

- 代码做了什么（读代码就知道）
- 修了什么拼写错误（看 commit 就知道）
- 泛泛的「提升了可维护性」

### 4.3 写作模板（设计文档）

```markdown
### <版本> <一句话标题>

#### 问题
用户原话 / 观测到的现象 / 复现步骤。**先写症状，不要先写方案。**

#### 根因
为什么会出现。如果做过误判，把**错误的第一判断也写下来** ——
那是下一个人最容易重复的弯路。

#### 做法
改了什么，为什么这样改而不是另一种改法（列出被否决的方案）。

#### 边界
哪些情况下这个方案**不生效**或**刻意不处理**。
（例：CD2 查询失败时按原判据处理，绝不因为"查不到"就当成功）

#### 测试
覆盖了什么，样本从哪来（真实抓包 vs 手工构造），以及
**是否用缺陷版验证过守卫会失败**。
```

### 4.4 索引 history 的写法

面向市场页，用户是"要不要升级"视角。要求：

- 开头一句话说清**用户能感知到的好处**；
- 用 ①②③ 分点，每点「症状 → 修法」；
- 不写实现细节，技术理由放 `DEVELOPMENT.md`。

### 4.5 文档与代码同批提交

不要"代码先提交、文档下次补"。下次补的时候，当时的判断依据已经想不起来了 ——
那些恰恰是文档唯一有价值的部分。

## 5. 检查清单

### 开发前

- [ ] 页面结构草图已给出并获确认
- [ ] 每个新增控件的首屏/折叠归属有理由
- [ ] 四种状态（未启用/缺前置/在跑/失败）的文案都写了
- [ ] 开发计划含「非目标」「风险与依赖」
- [ ] 涉及外部系统的事实已用真实数据核实

### 开发中

- [ ] 只做计划里的事；额外发现先记入计划
- [ ] 每个用户可见字符串检查过 Markdown 与内部术语
- [ ] 状态提示挂在它描述的对象上（不是挂在邻居上）

### 交付前

- [ ] `vite build` 已执行（Vue 插件）
- [ ] 联邦 CSS 门禁通过
- [ ] 严格版本门禁通过（五个版本字段一致）
- [ ] 测试失败集合与基线**逐条**相同
- [ ] 真机验证：核心路径 + 日志无异常 + 版本号已生效
- [ ] `USAGE.md` / `DEVELOPMENT.md` / `Development_Log.md` / 索引 history 都已更新
- [ ] 提交信息说明了「症状 → 根因 → 修法」，不只是复述 diff

以下问题在 `rsync115sync` v0.5.6–v0.5.8 与 `p115strmhelper` v3.4.x 中实际发生，
可作为本流程各条目的反面教材：

| 问题 | 违反的条目 | 后果 |

| CD2 开关藏在高级区 | 1.2 首屏准入 | 「强烈建议开启」的功能用户找不到 |
| CD2 提示嵌在 `watchingCount` 内 | 1.5 挂载位置 | 保护生效时提示消失 |
| 模板里写 `**加粗**` | 3.5 文案红线 | 界面显示字面星号 |
| token 只写实例属性未写回字典 | 3.1 顺序（未做真机保存验证） | 重载后 token 消失，全程显示成功 |
| flex 调宽度三次未解决挤压 | 1.3 移动端规定 | 绕了三个版本的弯路 |
| 照 proto 猜 CD2 响应格式 | 2.2 风险与依赖前置 | 把「token 无效」读成「队列为空」 |

# 115 网盘同步助手 — 本地使用说明

> 面向使用者的操作手册。开发与设计说明见 [DEVELOPMENT.md](./DEVELOPMENT.md)，
> 待办事项见 [TODO.md](./TODO.md)。
>
> 当前版本：**v0.1.8**

---

## 1. 这个插件能做什么

把本地媒体库（NAS 上的电影 / 剧集）通过 `rsync` 同步到 CloudDrive2（CD2）挂载的
115 网盘目录，并具备：

- **入库发现**：源端扫描（主通道，默认 30 分钟一轮）+ Webhook（可选加速），
  手动放入、外部工具搬入、9KG 这类不入库的目录都能覆盖
- **入库冷却**：新入库的媒体先等 N 小时再上传 —— 既留时间给外挂字幕下载与刮削，
  也等文件写完（源端扫描没有"写完了"这个信号，冷却期是唯一挡住半截文件上传的机制）
- **双向对账**：同步后核对源端与目标端文件大小，找出缺失和残缺文件
- **上传限流**：控制单位时间的上传文件数，避免触发 115 风控
- **存量补传**：把启用插件之前就已入库的历史文件补齐到 115
- **手机指令**：通过聊天指令查看状态、重试、忽略文件

## 2. 前置条件（务必先确认）

### 2.1 依赖 CD2 挂载

本插件通过 **rsync 写入 CD2 的 FUSE 挂载点**来间接上传到 115，自身不调用 115 的
API。因此：

1. 宿主机上必须已用 CloudDrive2 把 115 网盘挂载到本地路径（例如
   `/volume2/CloudNAS/115`）
2. 如果 MoviePilot 跑在 Docker 容器里，**必须把宿主机上的 CD2 挂载路径和本地媒体
   目录一并映射进容器**，建议挂载模式使用 Slave 共享（可读写）

> ⚠️ 两个路径都不可省略。只映射了本地媒体目录、没映射 CD2 目录，同步会直接失败。

### 2.2 系统需支持 rsync

容器或宿主机内需能执行 `rsync`。Debian/Ubuntu 系：

```bash
apt update && apt install -y rsync
```

### 2.3 目录写入权限

MoviePilot 进程需要对 CD2 挂载目录有写权限，否则 rsync 会以权限错误退出。

## 3. 快速上手（三步）

### 第一步：配置目录映射

打开插件配置页，在「同步目录映射对」中点击**添加目录映射**，每组填写：

| 字段 | 说明 | 示例 |
|---|---|---|
| 任务备注名称 | 仅用于日志与清单显示，建议用短名 | `电视剧` |
| 本地源目录 | NAS 上的媒体目录（宿主机/容器内均可访问的路径） | `/volume3/HomeTheater/emby/TV` |
| CD2 挂载 115 目录 | CD2 挂载点下对应的目标目录 | `/volume2/CloudNAS/115/TV` |
| 同步所有文件类型 | 关闭=只传扩展名白名单内的文件（推荐） | 关闭 |

> 💡 任务备注名称会成为文件清单的前缀（如 `电视剧:剧名/剧名 S01E01.mkv`），
> 改名不会导致重复同步，但会让旧的异常清单条目失去对应关系，建议一次定好。

### 第二步：确认冷却与限流参数

默认值适合大多数场景，**建议先按默认跑一段时间**再调整：

| 参数 | 默认 | 作用 |
|---|---|---|
| 源端扫描入库 | 开启 | **入库发现的主通道**，见第 3.5 节 |
| 源端扫描 Cron | `*/30 * * * *` | 多久遍历一次本地源目录（cron 写法） |
| 入库冷却延迟时长 | 4 小时 | 发现后等多久才上传（见下） |
| strm 观察宽限期 | 5 分钟 | 同步成功后等多久才判定 strm 缺失 |
| 定时检查 Cron | `0 */2 * * *` | 每 2 小时巡检一次，把冷却到期的文件送上传 |
| 单批文件数上限 | 200 | 单次 rsync 提交多少文件 |
| 单窗口上传上限 | 500 | 一个窗口内累计上传多少文件 |
| 限流窗口时长 | 1800 秒 | 窗口长度，到期额度重置 |
| 命中风控后退避 | 3600 秒 | 命中风控后暂停多久 |

配置页会实时把限流参数换算成**速率**（如「约 17 个/分钟」），并给出参数合理性提醒。

### 第三步：保存并观察

保存配置后，看板会显示冷却队列与异常清单。新入库的媒体会在冷却结束后自动上传。

## 4. 存量补传（重要）

### 4.1 什么情况下需要补传

本插件**只能感知启用之后**的入库（源端扫描按文件修改时间判断，看不到插件启用前
就已存在的存量）。对于以下文件，看板看不到、也永远不会自动同步：

- 安装 / 启用插件之前就已经入库的媒体
- 因扩展名不在白名单而从未入队的文件（例如早期版本遗漏的字幕）

**需要补传一次，把它们纳入 115。**

### 4.2 两种触发方式

**看板按钮**：点「补传存量媒体」→ 插件先本地扫描 → 弹出确认框显示候选数量与预计
需要多少个限流窗口 → 确认后开始。

**聊天指令**：发送 `/rsync_backfill`。

### 4.3 补传的代价（务必理解）

- **扫描阶段零开销**：只读本地磁盘，不会请求 115
- **传输阶段有开销**：每个候选文件至少要向 115 发一次校验请求。已存在的文件会被
  rsync 跳过（不会重传），但这次请求省不掉

所以补传前那个确认框很重要 —— 它告诉你候选有多少个。**候选数 ≈ 最少请求次数**。

> 💡 如果候选过多（上万），建议先只补字幕：把「同步的扩展名」临时改为
> `srt,ssa,ass`，补完再改回来。

### 4.4 补传会自动分批

补传受**单批上限**与**窗口配额**约束，一次跑不完是正常的：

```
建立队列(比如 5000 个)
  → 本轮传 200 个（单批上限）
  → 窗口内累计到 500 个后暂停（窗口配额）
  → 等下一个窗口，定时巡检自动续跑
  → 循环直到队列排空
```

进度会持久化，**插件重载、宿主重启都不会丢失**，无需重新点击。看板会显示剩余数量。
想中止就点「取消补传」或发 `/rsync_backfill_clear`。

## 4.5 入库发现：源端扫描（主通道）与 Webhook（加速器）

> **2026-09-25 起，入库发现换了架构。** 此前插件订阅宿主的「整理完成」事件，
> 那条路**已整条删除** —— 原因与影响见本节。老用户请读 4.5.4 的迁移说明。

### 4.5.0 两条来源的分工（先看这张表）

| | **源端扫描（主通道）** | **Webhook（加速器）** |
|---|---|---|
| 谁负责完整性 | ✅ **只有它** | ❌ 不承担 |
| 怎么发现 | 定期遍历源目录，比对文件修改时间与游标 | 发送端主动推送到平台 webhook |
| 能看到手动放入的文件 | ✅ | 需要发送端配置 |
| 能看到 9KG 这类不入库的目录 | ✅ | ✅（这是它存在的主要理由） |
| 插件重载期间发生的入库 | ✅（游标续上，下一轮补回） | ❌ 与事件一样会丢 |
| 默认状态 | 开启，30 分钟一轮 | 需要你在发送端配置 |

**为什么把完整性交给扫描而不是 webhook**：webhook 依赖"你的发送端配置永远正确、
永远在线"，扫描依赖的是"文件在源目录里"——后者不依赖任何外部组件。
即使 webhook 整条失效，扫描也会在下一轮把同一个文件捞回来
（去重由队列幂等保证，不会重复上传）。

### 4.5.1 源端扫描（默认开启，通常不需要动）

> 💡 **想立刻看一次扫描结果**，不用改 cron 也不用等：看板上的
> 「**立即运行一次**」会马上扫一次源端，并顺手跑一轮就绪同步。
> 它**不绕过冷却** —— 冷却中的文件仍要等满，这一点在返回消息里会写明
> （有多少个在冷却、最快还需多久）。要立刻传某个**已经冷却到位**的文件，
> 用队列列表里那条的单条「立即同步」。

插件按配置的 **cron 表达式**（默认 `*/30 * * * *`，即每 30 分钟）遍历各映射的
本地源目录，把「修改时间晚于上次成功扫描时刻」的文件纳入冷却队列。
它**只读本地目录、不访问 115 挂载点**，因此不消耗上传配额、不触发风控。

用 cron 而不是"固定间隔"是因为前者能表达"只在夜里扫"这类节奏，而大库的整树遍历
有成本。写法与「定时检查」完全一致。

要点：

- **首次启用时以「当日 0 点」为基线**：今天已入库的存量会被纳入队列（它们确实
  还没上传），昨天及更早的不会 —— 那是 `/rsync_backfill` 的职责（见第 4 节）。
- **漏不掉**：重载/重启期间发生的入库，下一轮扫描会补回来（这是它取代事件订阅的
  主要原因）。
- **不会重复上传**：已入队的文件不重复入队；已经就绪的文件由 `rsync --size-only`
  判为无需传输。
- **看板会显示扫描健康状况**：若超过 3 倍间隔（默认 30 分钟）没有推进，看板会
  给出警告 —— 那意味着新文件不会被发现。

**间隔怎么选**：默认 30 分钟。每轮是**每个映射一次全树遍历**，大媒体库下这个成本
是实打实的；而扫得更勤**不会让文件更早上传** —— 进队列之后仍要等满冷却（默认 4 小时），
扫描频率只决定"它多早开始等那 4 小时"。所以没必要调到每分钟。
只有在"入库后希望尽快进入队列"这件事对你很重要时，才值得调到 10 分钟或更密。

**关掉它会怎样**：入库只能靠 Webhook 通知发现 —— 手动放入、外部工具搬入、
以及 webhook 配置出问题时入库的文件都会**静默丢失**。除非你有明确的理由，否则别关。

### 4.5.2 冷却时长为什么是 4 小时（改动过，从 2 小时上调）

冷却期现在**同时兜两件事**：

1. 等外挂字幕、nfo、图片一起到齐（原来的职责）；
2. **等文件写完** —— 源端扫描没有「整理完成」这个信号，它唯一能看见的是文件
   修改时间，而**正在写入的文件修改时间恰好是最新的**。

第 2 条是这次上调的直接原因。一部几十 GB 的 4K 文件从开始写入到写完，慢速来源
（qB 完成后搬入、SMB 跨机拷贝）上一小时以上很常见；冷却太短会让插件在文件还在
变化时就去上传，rsync 中途被打断，**在 115 云端留下半截文件**（外观是
`影片.mkv..xxxxxx` 这种带随机后缀的残留，见「常见问题」）。

4~6 小时是推荐区间。**已经手工改过这个值的用户不会被自动迁移** —— 迁移只作用于
"从未改过、仍是旧默认 2 小时"的配置。

### 4.5.3 Webhook 入库（可选，9KG 用户的加速通道）

Webhook 让文件**早一点**进队列。它**不承担完整性** —— 即使完全不配，扫描也会发现
同一个文件，只是晚最多 30 分钟。

**配置方式**：在发送端（或 Emby 后台 → 通知 → Webhooks）填平台地址：

```
http://<moviepilot地址>:3001/api/v1/webhook/?token=<API_TOKEN>&source=rsync115sync
```

- `token` 填 MoviePilot 的 API Token（设置 → 安全 → API Token）
- `source` 必须**恰好**是 `rsync115sync`
- 也可用请求头 `X-Webhook-Target: rsync115sync` 代替查询串

> ⚠️ **`source` 只能是 `rsync115sync`。** 本插件只认显式发给自己的报文；
> 写成 `<emby实例名>` 会被**平台自己的解析器**接管，本插件一行日志都不会有。

本插件侧**没有任何 webhook 配置项**。配置页那段说明就是在讲这件事 ——
入口判据（收件人标识）是内置的，不需要你声明"接收哪些渠道"。

**想停用 webhook**：关闭「**启用入库监听**」总开关（配置页第一组）。它与源端扫描**共用**
这个总闸（两者都是入库来源；分成两个开关会让用户遇到「关了一个、另一个还在
悄悄入队」）。关掉后入库只剩源端扫描一条路。

#### 顺带一条：自定义发送端也可以走平台的 webhook 地址

发送端（自建脚本、MDC-ng 之类）都走**同一个**平台 webhook 地址 + 一个专属标识，
由插件认领。这是**唯一**的入口（插件自带的端点在 2026-09-22 已移除，见 4.5.3）：

```bash
curl -X POST "http://<mp>:3001/api/v1/webhook/?token=<API_TOKEN>&source=rsync115sync" \
  -H "Content-Type: application/json" \
  -d '{"paths": ["/volume3/HomeTheater/emby/电影/x.mkv"]}'
```

好处是鉴权交给宿主（API Token）、请求有宿主日志；代价是需要填对 `source`。
也可用请求头 `X-Webhook-Target: rsync115sync` 代替查询串。

> ⚠️ `source` 必须**恰好**是 `rsync115sync`。这个标识是插件用来认领报文的唯一凭据，
> 写成别的值（包括写成 `emby`）插件都不会处理 —— 而写成 `emby` 更糟：那会让报文
> 被宿主的 Emby 解析器接管，插件一条日志都不会有。

> ⚠️⚠️ **`Content-Type` 必须与 body 形态匹配，否则请求根本到不了插件。**
> 这是实测踩过的坑，也是「平台能看到请求、插件却一行日志都没有」的头号原因。
>
> 宿主端点在调用插件之前会先解析表单。若你声明
> `Content-Type: multipart/form-data` 却发**裸 JSON body**（没有 boundary ——
> 很多 webhook 配置界面的「Content-Type 下拉框」会诱导这么选），宿主会直接返回
> **400 Missing boundary in multipart**，请求在进入本插件之前就被拒。
> 此时插件看不到任何东西，宿主日志里只有一条内容为空的 400。
>
> **改法：把 Content-Type 改成 `application/json`**（或直接不带这个头）。
> 发 JSON 就不要声明 multipart；两者混用宿主不接受。已验证：同一个报文、仅改这一个
> 请求头，行为从「400 + 插件零日志」变成「200 + 正常入队」。

**先把这条路单独打通，再去调那个工程**（发送端还没摸清时，这能省下大量来回）：

```bash
curl -i -X POST "http://192.168.1.8:3001/api/v1/webhook/?token=<API_TOKEN>&source=rsync115sync" \
  -H "Content-Type: application/json" \
  -d '{"event":"download.finish","data":{"title":"某电影 (2024)","source_path":"/volume3/9KG/某电影 (2024)"}}'
```

> ⚠️⚠️ **注意 `webhook` 后面那个 `/` —— 少一个斜杠就全部失效。**
> 宿主把端点注册为 `/`（`app/api/endpoints/webhook.py` 的 `@router.post("/")`），
> 最终地址是 `/api/v1/webhook/`。写成 `/api/v1/webhook?token=...`（缺尾斜杠）
> 会在**路由层**被 starlette 重定向：
>
> ```
> POST /api/v1/webhook?token=...&source=rsync115sync HTTP/1.1 307 Temporary Redirect
> ```
>
> 此时请求**没有到达插件**，插件一行日志都不会有 —— 现象和「发送端没配」完全一样。
> 这是真机第二次踩到的坑，且比 Content-Type 那个更隐蔽：**307 看起来像「已成功投递」**
> （静默跟随后结果确实是 200），只有插件侧的彻底沉默暴露了问题。
> 改法：地址补上尾斜杠，其余不动。

期望：HTTP **200** + body `{"success":true}`，插件日志出现一条
`监听到 N 个新入库文件（... 路径来源=候选字段）`，看板「平台解析入口到达」+1、
「最近报文样本」出现这条报文。**这四样齐了，就说明插件侧没问题**，
剩下的差异全在发送端。

> 💡 上面的路径请换成你**映射源目录下真实存在**的路径。若插件日志说
> 「取到的路径不属于任何映射」，那就不是 Content-Type 的问题了 ——
> 它会把你当前配置的全部映射源目录列出来，照着改报文即可。

**发送端的 Content-Type 改不了怎么办**：这是**发送端侧**的问题，插件无法兜底
（请求在进入插件之前就被宿主拒了）。可选的途径：

- 找一个能改请求头的中间层（反代、`curl` 脚本、n8n/HomeAssistant 之类的转发节点），
  由它把 Content-Type 写对再转给平台地址；
- 若该工具支持，直接把 Content-Type 设为 `application/json`（或干脆不带这个头）。

> ⚠️ **本插件自 2026-09-22 起不再自带端点**，因此没有「换个地址绕开」这条路了。
> 此前那个免登录端点正是为了绕开这类发送端限制而存在，但它同时意味着
> 向网络暴露一个可写入接口，而宿主端点已能满足同一需求（鉴权交给宿主）。
> 少一个暴露面，少四条容易配错的安全配置。理由与取舍见 DEVELOPMENT §9.18。
>
> 也正因如此，**唯一的地址就是宿主端点**，尾斜杠必须带（见上一条）。

**报文形态参考**（另一个工程常用的形态，字段名不必完全一致，见下）：

```jsonc
{
  "event": "download.finish",
  "data": {
    "title": "某电影 (2024)",
    "first_actor": "某人",
    "source_path": "/volume3/9KG/某电影 (2024)",   // ← 入库位置，插件要的就是它
    "target_path": "/9KG/某电影 (2024)"
  }
}
```

`source_path` 这个字段名**本来就在候选表内**，且 `data` 也是已知的嵌套容器 ——
所以这个形态无需任何配置即可识别。**它此前没生效的原因不是字段名，而是 Content-Type。**

> 📌 **`source_path` 是目录也可以。** 插件会自己展开成目录内的文件
> （只收扩展名白名单内的、跳过 `@eaDir` 这类排除目录），发送端不必先遍历目录。

**走这条路时，日志长什么样？**

- **认领成功** → 一条 `INFO ... 监听到 N 个新入库文件（... 路径来源=...）`。有它就说明通了。
- **声明了 `source=rsync115sync` 但没认领成功** → 现在会留下 **info** 级日志，
  明确写出是「取不到路径」还是「路径不属于任何映射」，并列出当前配置的映射源目录。
  （此前这里是静默的 debug —— 那正是「插件看不到任何日志」的成因。）
- **完全没有任何日志** → 报文没到插件。去看宿主日志里那条请求的状态码：
  **4xx 且内容为空**基本就是上面的 Content-Type 问题；看板上的
  「平台解析入口到达」计数也能帮你判断（它由插件在解析入口统计，
  没有到达就不会增加）。

看板顶部有这几个数字，组合起来就是结论：

| 看板现象 | 结论 |
|---|---|
| 「平台解析入口到达」= 0 | 报文**没到插件**：查地址尾斜杠、Content-Type、API Token |
| 到达 > 0，但「收到事件」= 0 | 到了但**没认领**：日志会写明原因（取不到路径 / 路径不在映射内） |
| 到达 > 0 且有入队日志 | 正常 |

「到达 = 0」时，**按这个顺序查**（前两个都踩过，第三个最常见）：

1. **地址有没有尾斜杠** —— 见上面的 307。发送端日志里的 `307 Temporary Redirect`
   就是它的指纹。
2. **Content-Type 是否与 body 形态匹配** —— 见上面的 400。宿主日志里一条
   内容为空的 400 就是它的指纹。
3. `token` 是否为宿主的 API Token、`source` 是否**恰好**是 `rsync115sync`。
4. **插件版本是否包含本次修复** —— 若你用的版本早于本次改动，则存在一个
   **插件自身**的缺陷：它实现了认领逻辑却没有向宿主声明（`get_module()`），
   因此宿主从不会调用它，表现为**宿主的 200/307 都正常、插件彻底无反应**。
   这类失效没有任何日志可查（详见 DEVELOPMENT §9.17）。**升级插件即修复。**

   **怎么一眼确认版本对不对**：看插件启动日志里有没有这一行 ——

   ```
   [Rsync115Sync] 认领钩子已注册（webhook_parser 已向宿主声明）…
   ```

   没有它（或看到 `认领钩子**未注册**` 的 error）就说明环境里的插件不是含本次
   修复的版本，先更新插件再排查。另外在宿主的 DEBUG 日志里，
   **`请求插件 xxx 执行：webhook_parser`** 这条信息级日志才代表插件真被调用了；
   只出现 `请求系统模块执行：webhook_parser` 而**没有**前者，即表示插件未被收集。

   > ⚠️ **若「检查更新」里看不到本插件**：宿主判断「有无更新」是比较
   > **已安装版本号 < 索引版本号**，两者相等时不会提示更新。
   > 本插件 alpha 迭代期间**版本号不递增**（详见 DEVELOPMENT §6 的说明），
   > 因此想拿到最新修复请用**重新安装**的方式覆盖（市场里对本插件执行重装，
   > 或走 `local_plugins` + `git pull`），装完刷新页面并以启动日志里的
   > 「认领钩子已注册」那行确认。

一次推多个文件时，报文的 `paths` 数组会被**全部**入队（不是只取第一个）。

### 4.5.4 为什么没有自建端点（已于 2026-09-22 移除）

早先插件自带一个免登录端点（`POST /api/v1/plugin/Rsync115Sync/webhook`），理由是
MDC-ng 一类的发送端不会被宿主解析。它付出了两处代价：

1. **多一个可写入的暴露面** —— `allow_anonymous` 意味着知道地址的人都能往插件里灌
   数据，伪造入库会真实消耗 115 风控配额；
2. **多四条容易配错的安全配置** —— 端点开关、密钥、路径白名单、来源 IP 白名单，
   配错任何一条都可能「看起来开着、其实没防住」。

而它解决的问题用平台入口就能解决：发送端把 `source` 指到 `rsync115sync` 即可，
**鉴权由宿主用 API Token 负责**，请求也有宿主日志可查。因此端点与其四条配置一并移除。

**唯一地址就是宿主端点**，且**尾斜杠必须带**（见 4.5.3）。

### 4.5.5 怎么确认这条路通了

> 这一节讲的是 **webhook 那条路**的诊断。源端扫描的诊断简单得多：
> 看板会在它超过 3 倍间隔没有推进时直接报警，日志里的关键词是
> `🔍 源端扫描：N 个新文件已入冷却队列`。

看板顶部会显示一行计数：**收到 N 条 · 入队 M 个文件 · 🎯 平台解析入口到达 K 条**
（面板只在收到过请求后出现，全 0 时不占位）。

「平台解析入口到达」是**宿主调用本插件解析器的次数**（认领成功与否都算），
与「收到」是两个不同的点位 —— 前者记「请求到没到插件」，后者记「认领后广播回来」。
两者之差就是**到了却没认领**，这是排查时最需要区分的一件事。

取不到路径时，看板还会显示**最近报文的字段结构**（只记字段名与类型，**不记值**）——
拿到字段名就足以判断该把哪个字段加进候选表。

| 看到的现象 | 结论 |
|---|---|
| 全为 0 | 请求根本没到插件：查地址尾斜杠、Content-Type、宿主 API Token、`source` 是否写对 |
| 入口到达 > 0，而收到 = 0 | 请求到了插件，但**没认领**：路径不在任何映射内、或插件未启用。日志有 info 级说明 |
| 收到 > 0，入队 = 0，未识别 > 0 | 到了但字段名对不上：看「最近报文的字段结构」，把字段名反馈给插件以扩展候选表 |
| 收到 > 0，被拒 > 0 | 认领阶段未通过（路径不在任何映射内等），日志会写明原因 |
| 收到 > 0，入队 > 0 | 正常。若队列没涨，说明这些文件**已经在队列里**（幂等，不重复入队） |
| 收到 > 0，消息显示「目录已展开但无文件入队」 | 目录收到了，但里面没有符合扩展名的文件（或全在忽略清单里）|

> 📌 看板曾提供「最近报文样本（含值）」。它在字段表对齐后已移除 ——
> 完整报文值属于开发期对齐字段用的信息，而它的代价一直存在（明文展示、
> 落盘、逐字段脱敏）。需要看具体值时请查宿主日志或发送端本身的记录。

日志里的关键词：`监听到 N 个新入库文件（... 路径来源=...）` —— 这里的「路径来源」
会告诉你是从 `item_path`、`json_object.Item.Path` 还是候选字段取到的路径。

#### 发送端推「目录」还是「文件」？

**两种都支持，推目录更省事。** 推目录时插件会自己展开成文件（只收扩展名白名单内的、
跳过 `@eaDir` 这类排除目录），所以另一个工程下完一部电影后，直接把电影目录发过来即可，
不必先遍历目录、也不用担心它算错了文件名。

展开有上限（默认 500 个文件/次）：推整个媒体库根目录会被截断，日志里会写明少了多少 ——
这既是防止一次灌爆冷却队列，也是提示你改推具体子目录。

**推单个文件时的补充规则（只对「同步所有文件类型」映射生效）**：勾选了该选项的映射，
若发送端只推来**一个文件**，插件会把**同目录的其它文件一并入队**（只取同一层，不递归子目录）。
原因是该选项承诺「这个目录下的文件都要上传」，而发送端手里往往只有「整理完成的那一个文件」，
它不知道同目录还有哪些文件。未勾选该选项的映射不受影响：只入队被推来的那个文件
（上传范围由「同步的扩展名」决定，不会因为这条规则扩大）。

> 例：9KG 映射勾选了「同步所有文件类型」，发送端推来 `/volume3/9kg/某电影 (2024)/movie.mkv`
> → 队列里会同时出现同目录的 `movie.zh.srt`、`poster.jpg`、`movie.nfo` 等**全部**文件。
> 单目录超过 300 个文件时截断，日志会写明漏掉多少。

> 典型用法：另一个工程下完 9KG 内容后，POST 一个目录路径到**平台入口**即可 ——
> ```bash
> curl -X POST "http://mp:3001/api/v1/webhook/?token=<API_TOKEN>&source=rsync115sync" \
>   -H "Content-Type: application/json" \
>   -d '{"Event": "download.finish", "path": "/volume3/9kg/某电影 (2024)"}'
> ```
> 目录里只放媒体文件时，`Event`/`path` 之外的字段随便叫什么都能识别（候选字段表）；
> 若字段名不在候选表内，看板的报文样本会让你一眼看出该报哪个名字。

## 5. 上传限流：为什么慢，为什么不能快

115 会统计**单位时间内上传的文件个数**。大量小文件（尤其是字幕、样张）在短时间内
集中上传，最容易被判定为异常流量，导致上传被拒绝甚至临时封禁。

插件用两层限制来规避：

| 机制 | 限制什么 | 防的是 |
|---|---|---|
| 单批文件数上限 | 一次 rsync 提交多少文件 | 命令行过长、单次请求峰值 |
| 窗口配额 | 一段时间内累计多少文件 | **115 风控（主要闸门）** |

超出部分**不会丢失**，会在下一个窗口自动继续。

另外，如果 rsync 的错误输出中出现风控特征（`429`、`too many requests`、`频繁` 等），
插件会**立即暂停上传并进入退避**，等退避结束后再继续。

> 💡 如果你频繁看到「风控退避中」，说明限流阈值还是偏松。可以降低
> 「单窗口上传文件数上限」，或延长「限流窗口时长」。配置页会在速率超过
> 每分钟 60 个时给出告警。

- 只有成功执行才计入冷却，失败可立即重试

**绝大多数情况下你不需要它。** 补齐存量请用 `/rsync_backfill`，它只扫源端、

## 8. strm 交叉验证（自动发现上传异常）

> **依赖说明（先看这个）**
>
> 本插件**绝大多数功能不依赖任何外部插件**，包括整个 strm 交叉验证链路的
> 观察、扫描、清理与**删旧重传** —— 它们只读本地文件系统。
>
> **唯一例外**是 8.3.1 的「先尝试生成 strm」，它需要
> **P115StrmHelper**（且需要额外两处配置，见该节）。不装、不配都不影响其它功能，
> 只是不能使用这一个可选的增强项。
>
> 配置页与看板上对该项均以「依赖 P115StrmHelper」标注区分。

### 8.1 它解决什么问题

CD2 改名失败后，挂载视图显示「文件存在且正常」，插件的全部判断都被蒙蔽 ——
看板一切正常、对账无异常，但 115 云端实际只有改名失败的半成品。
**strm 交叉验证用一个与 CD2 无关的独立视角发现这种假成功。**

原理：strm 类插件（如 P115StrmHelper）依据媒体库文件在本地生成 .strm 指针文件，
它判断「文件是否可用」的依据与 CD2 挂载无关。若某文件同步成功后、
宽限期内对应的 .strm 始终没出现，大概率上传并未真正完成。

> ⚠️ **只有视频文件参与这项验证**。strm 插件只为视频容器（mkv/mp4/ts 等）生成
> 指针文件，**字幕（srt/ass）、图片（jpg/png）、元数据（nfo）永远不会有 .strm** ——
> 它们本就该「没有 strm」，所以插件**不把它们纳入监控**，不会出现在疑似清单里。
> 这也意味着：同步了 10 个文件（3 个视频 + 7 个字幕/图片）时，只有 3 个会进入观察期，
> 「入库数与观察数对不上」属于正常现象（日志里会写明跳过数量）。
> 即使映射勾了「同步所有类型」也一样 —— 那是「同步哪些文件」，与此处无关。

### 8.2 怎么启用

1. 在映射配置的「strm 目录」填入 strm 插件的输出根目录（与源目录**不同根**，
   由你手动配置；**留空则该映射不启用验证**）
2. 前提条件：strm 文件名与整理后文件**同名**（仅扩展名不同），
   且目录结构与源端一致（源端 `A/B/剧名 S01E03.mkv` → strm 端 `A/B/剧名 S01E03.strm`）
3. 可调「观察宽限期」（默认 **5 分钟**，配置页「strm 交叉验证」模块）：
   strm 生成不实时（可能在上传/刮削中），宽限期内不报警。
   > 单位是**分钟**，此前是小时（2026-09-25 改）。老配置的值不会被自动换算 ——
   > 同一个 `6` 从小时变分钟会把 6 小时的需求悄悄变成 6 分钟，那会大面积误报。
   配置页同时显示「N / M 个映射已配置」，便于确认配置是否生效
4. **（可选）想用「先尝试生成 strm」的话**，还需要额外配两处，见 8.3.1

### 8.2.1 读懂扫描结果：为什么「缺 N 个」与「新增 M 个」对不上

扫描（看板「扫描缺 strm 的文件」或 `/rsync_strm`）报的是**两个不同的数**，
它们不必相等，差额一定有说法：

| 数字 | 含义 |
|---|---|
| **缺 strm N 个** | 源端有、strm 目录里没有 —— 本次扫描**看见**的 |
| **新增疑似 M 个** | 其中**真正新写进**疑似清单的 |

差额的三个去向（结果里会逐条列出来）：

- `🚫 其中 X 个已命中「忽略」规则` —— 你明确忽略过的文件不再报警，Scan 看见它、
  但不会把它塞回清单。**这是最常见的差额来源。**
- `⏳ 其中 Y 个正在观察期` —— 刚同步成功或刚请求过补生成，交给观察窗口自行判定，
  扫描**有意不降级**（否则你刚点完补生成，扫描就把条目打回疑似，功能等于没作用）。
- `ℹ️ 另有 Z 个已在疑似清单中` —— 本来就在清单里，只是又被看见了一次，
  不计入「新增」。兜底句；若它出现而前两条都不是，说明有跳过的原因没被解释，
  请把结果发出来。

结果里还会直接列出**缺 strm 的文件名**（前 10 个），不必自己去源端找。

### 8.3 发现疑似异常后

疑似清单在**独立的「strm 疑似异常」标签页**内（不再混在对账异常清单里），
有两种处理方式，**建议按顺序**：

#### 8.3.1 第一步：先尝试生成 strm（推荐先做这个）

> ⚠️ **本节是全插件唯一依赖 P115StrmHelper 的功能**。
> 不想装助手的话，跳过本节，直接用 8.3.2 的删旧重传 —— 其余功能一概不受影响。

「缺 strm」其实有**两种成因**，处理成本差很多：

| 成因 | 云端实际状态 | 正确处置 |
|---|---|---|
| **① 助手漏生成** | 文件是好的，只是没生成指针 | 请助手重新生成即可，**无需重传** |
| **② CD2 假成功** | 只有改名失败的半成品 | **必须删旧重传** |

插件在本地视角**无法区分**这两者（表现完全一样）。但借助手遍历一次云端目录就能
判别：生成成功 ⇒ 是 ①；生成后仍无 ⇒ 是 ②，此时再做删旧重传就心里有数了。

操作：看板 strm 标签页点「**先尝试生成 strm**」（或单条点「尝试生成 strm」）。
被请求的文件会移回「观察中」重新计时（**1 小时**），之后：

- strm 出现 → 自动解除，结束（**省下一整轮删除与上传**）
- 1 小时到仍无 → 回到疑似清单，标记为「**补生成后仍无**」，
  此时「云端确实缺文件」的可能性比首次疑似大得多，该考虑删旧重传了

移回观察期是**有意**的：那里有现成的判定机制（自动巡检 + 手动检查），
你不必盯着看 —— 点「检查 strm」就能立刻知道结果，什么都不点也会有
自动兜底（窗口到就回到清单，不会丢）。

> ⚠️ 这里的 1 小时是**固定值**，不跟随你的「宽限期」配置。
> 两者量的是不同的东西：宽限期量「rsync 报成功 → strm 出现」的刮削/入库延迟，
> 而这里等的是助手的一次云端目录遍历。把宽限期调大（比如 24 小时）不该连带让
> 补生成的结果在半天内无法判定。

> **配好它需要两处配置**（缺一不可）：
>
> 1. **本插件配置页**：在对应映射里填「**网盘目录**」——
>    这是该目录在 115 网盘里的**真实路径**（如 `/HomeTheater/TV`），
>    不是 CD2 挂载路径。本地 strm 目录与网盘目录是两棵独立的树，
>    无法自动推导，所以必须单独填。
> 2. **P115StrmHelper 配置页**：该网盘路径必须已配在它的
>    「**全量同步路径**」里。助手的 `/p115_strm` **只接受这个列表里的路径**，
>    配在它其它字段（如「监控生活路径」）里的目录传过去会被拒绝，
>    提示「路径匹配错误」——**而这个提示只发给助手侧，本插件看不到**，
>    表现为「点了按钮什么也没发生」。遇到这种情况请先核对助手配置。
>
> 例：本插件填 `/HomeTheater/TV`，助手「全量同步路径」里需有
> `/media/strms/TV#/HomeTheater/TV` 这样的映射行。

**为什么是手动触发**：这一步会让助手**访问 115 网盘**（按目录遍历云端子树）。
清单有几十条时自动触发就等于自动打出几十次遍历，因此设计为手动、逐目录去重，
且单次涉及目录数有上限（默认 20 个，超过则**整批拒绝**，不会自动放大访问量）。

#### 8.3.2 第二步：删旧重传

上一步看到「补生成后仍无」（或你已明确知道是假成功），再执行：

| 方式 | 操作 | 适用场景 |
|---|---|---|
| **单条「删旧重传」** | 点击该行按钮 → 确认 | 只处理个别文件 |
| **「全部删旧重传」** | 点区域标题右侧按钮 → 确认 | 清单规模小、想一次清完（会提示总数） |
| **批量勾选** | 点上方「批量选择」→ 勾选若干条 → 点工具栏按钮 | 从清单里挑一部分处理（推荐） |

三种方式都是「删除 115 端该文件 → 立即定向重传 → 传完自动复核 strm」
（生成即自动解除，无需再确认），点击前都会弹确认框，且共用同一条通道 ——
因此「探测显示云端完好」时那个二次确认在三种入口上都会出现。

> ⚠️ **一批里混着「你确认过的」与「机器报的」时，整批会被拒绝**，
> 并提示你先取消勾选几条。这是刻意的：半执行的破坏性操作（删了一部分、
> 拦了一部分）会让你事后无法判断「那次点击到底做了什么」，
> 而取消勾选的成本远低于此。取消掉未确认的条目后，单独对确认过的重试即可。

> ⚠️ 目录名含**连续空格**的文件不会出现在补生成参数里（命令通道会把连续空格
> 折叠成单个，导致助手侧匹配失败）。这类文件请直接用删旧重传，不要指望补生成。

**批量勾选的一个细节**：勾选状态是**跨分组保留**的，因此提交时按**选中项的
成分**自动分流，而不是按你当前在哪个标签页：

- 全部为 strm 项 → 执行「删旧重传」
- 混合选择 → 先弹确认框说明分流规则，再分别提交
- 纯普通项 → 普通定向重传

两条通道对目标端文件的处理并不一样，这也是为什么必须分流：

| 你选中的条目 | 目标端实际状态 | 处理方式 |
|---|---|---|
| 对账：缺失 | 文件不存在 | 直接补传 |
| 对账：残缺 | 文件在，大小不符 | 先清理残缺再传 |
| **strm 疑似** | 文件在，**大小一致** | **必须删旧再传**，否则 rsync 认为「已同步」直接跳过 |
| 冷却队列中的正常文件 | 文件在，大小一致 | rsync 自动跳过，不传也不删，不会浪费流量 |

最后两行的区别是本功能存在的原因：**它们在大小上完全一样**。
「上传坏得很彻底」和「本来就传好了」在 `getsize()` 眼里无法区分，
只有 strm 疑似清单能提供这个判断。因此删除操作**只对 strm 疑似清单开放**
（服务端另有一道校验，非清单内的 key 一律拒绝）。

**误报是安全的**：若只是 strm 插件自身漏生成（媒体不识别等），
重传一个已同步的文件也不会重复上传（rsync `--size-only` 跳过）。

### 8.4 观察期：不用干等，可以立即检查

观察期默认 **5 分钟**（请求过补生成的条目是 1 小时），而自动巡检**30 分钟才跑一轮**。
若你刚跑完 strm 生成任务、或在文件管理器里看到 .strm 已经出来了，不必等下一轮
—— 看板上可直接检查：

| 操作 | 位置 | 作用 |
|---|---|---|
| **检查 strm** | 每个观察中条目的右侧按钮 | 只查这一个文件 |
| **立即检查全部** | 观察期小标题右侧 | 一次查完所有观察中条目 |
| 远程命令 | `/rsync_strm check` | 同上（全部） |

> 窗口内检查**只回答等待规则**，不会去读 CD2 挂载视图 —— 判据只有一条：
> `.strm` 有没有生成。

观察期里有两类条目，看板会分别标出，**等的对象不同**：

| 标记 | 来源 | 等什么 | 窗口 |
|---|---|---|---|
| `观察中` | 刚同步成功 | 刮削/入库传播后生成 .strm | 「宽限期」配置值（默认 5 分钟） |
| `已请求生成` | 你点过「先尝试生成 strm」 | 助手遍历云端目录 | 固定 1h |

检查结果立即反映在看板上：

- **已生成** → 立刻解除观察（不再占用清单）
- **仍未生成且窗口内** → 继续等待（属正常，不会误报）
- **仍未生成且窗口已过** → 转入「疑似异常」清单，此时才需要判断是否删旧重传
- 源端文件已删 / 映射取消 strm 目录 → 移出观察

> 对「已请求生成」的条目，窗口过了回到清单时，会带上「补生成后仍无」标记 ——
> 意思是「生成动作已经做过而指针文件仍不出现」，判断强度比首次疑似高得多，
> 此时才值得考虑删旧重传。

> 纯本地文件读取，**不访问 115、不消耗配额、不与同步冲突** ——
> 同步任务跑着的时候照样可以查。
>
> 为什么这里不放「删旧重传」：观察期的文件刚同步成功，strm 可能还在生成中，
> 此时提供删除按钮只会诱导误操作（删掉刚传好的文件、白耗一次删除 API 与重传
> 配额）。观察期只提供不碰文件的操作，真正的删除仍在疑似清单里、仍需你确认。

> ⚠️ **窗口不再是下界**（v0.3.0 起）：曾经有个「确认失败」按钮，让你越过窗口
> 提前把条目转成疑似。它连同「云端可见性」整套判定一起删了 —— 详见 8.6。

### 8.5 通知

发现新的疑似异常时会**推送一条通知**（受众按宿主「通知场景开关」，默认仅管理员），
内容含文件清单、判定依据与处理入口。两个设计点：

- **只在新发现时提醒一次**：清单里的旧条目不会每轮重复推送，避免被静音；
- **全部恢复时补推一条「已全部解决」**，让你知道之前的告警已经处理完
  （而不是被静默遗忘）。恢复后若再有新发现，会重新提醒。

可在配置页关闭通知总开关（与同步报告共用 `notify` 开关）。

### 8.6 窗口到了还是没有 strm —— 只剩一个判据，和一个动作

补生成之后仍然没有 .strm，说明这一次上传几乎可以确定没真正完成。**插件不再替你
分辨「云端到底是哪种坏法」** —— v0.3.0 之前它试过（读 CD2 挂载点的大小与目录
内容，给出「可见且大小一致 / 只剩残留 / 不可见」三路结论），现已被证明**不成立**：

> **CD2 挂载视图对主成因必然给出相反结论。**
> 「CD2 改名失败」的典型形态是云端只剩 `<正式名>.<6位随机>` 的残留，而那个残留
> 与正式文件**字节数完全相同**（见常见问题 `..xrp4gj` 一节）。于是不管比大小
> 还是看目录，挂载视图都会显示成「可见、大小一致」—— 插件据此劝你「文件很可能是
> 好的、先别删」，而真相恰恰相反：那个文件在 115 上根本不能用。
>
> 两个方向的结论里必有一个是错的，而错的那一边会把你引向错误动作。
> 所以它被整条删掉了，**不是关掉**。

现在的判据只有一条，与你的需求一致：

| 判据 | 结论 | 动作 |
|---|---|---|
| `.strm` **存在** | 上传成功（助手只在视频正确上传后才生成指针） | 条目自动解除，不用管 |
| `.strm` **不存在** | 上传失败或助手漏生成 | 先「尝试生成 strm」，仍无则「删旧重传」 |

处理顺序与 8.3 相同：**先补生成**（便宜，且能免掉一整轮删除+上传），
补生成后仍无再**删旧重传**（此时判定的强度高得多）。

> 删旧重传的闸门全部在删除之前判（v0.2.6 起）：执行锁、风控退避、窗口配额、
> CD2 挂载未就绪，任一不满足都**不会删除任何文件**，而是直接告诉你原因。
> 此前这些闸门住在删除之后，命中的结果是「文件已从云端删掉、却永远不重传」
> 且没有任何提示 —— 若你遇到过「点了删旧重传没反应」，就是它。

### 8.6.0 看板四个标签各是什么

打开看板，主体区有四个标签页。它们对应**文件在生命周期里的不同处境**，
互不重叠：

| 标签 | 里面是什么文件 | 你要做什么 |
|---|---|---|
| **入库延迟冷却队列** | 已发现、还在等冷却到期的文件 | 等。冷却到期会自动传，不必操作 |
| **对账异常清单** | rsync 对账后发现**云端缺失或大小不符**的文件 | 点「重试」重传，或确认是存量后「忽略」 |
| **strm 疑似异常** | 见下方说明，内含**两个列表** | 先「尝试生成 strm」，仍无再「删旧重传」 |
| **已忽略** | 你明确要求不再报警的规则 | 误忽略时在这里删掉规则即可恢复 |

#### 疑似条目会自己消失吗 —— 会，有两种情况会自动清掉

| 情况 | 为什么 | 什么时候清 |
|---|---|---|
| **`.strm` 出现了** | 上传其实成功了（助手补生成 / 你手动处理过） | 巡检（≤30 分钟）/ 扫描 / 立即检查 |
| **文件还在冷却队列里** | **它还没上传**，按定义不可能有 `.strm` —— 属于误报 | 同上 |

> ⚠️ 第二条很重要，因为它影响你怎么处理清单：冷却期的文件**不该点「删旧重传」**
> —— 那个动作是给"上传失败"用的，而这些文件是"**还没轮到上传**"。
> 删了反而打断正常的冷却流程（它们冷却结束会自动同步）。

#### 疑似条目会自己消失吗（详细）

原先是：疑似条目会自己消失吗 —— 会，只要 .strm 出现了

**不需要你手工清理**。只要那个文件的 `.strm` 出现（不管是谁生成的），
条目就会自动移出待处理清单，并在日志里记一条。

具体在三个时机检查：

| 时机 | 说明 |
|---|---|
| **每轮巡检**（顺带跑，最长 30 分钟） | 自动兜底，不用你管 |
| 点「**扫描缺 strm 的文件**」 | 立即全面检查一遍 |
| 点「**立即检查全部**」 | 立即检查观察期 + 待处理两边 |

> **为什么需要这个**：补生成是**按目录**下发的 —— 助手收到 `Season 01`
> 就会把该目录下**所有**视频都生成一遍。所以如果你只勾了同目录的一部分文件，
> 没勾的那几个其实也生成了。没有这条机制，它们会一直挂在清单里当假警报。

> ⚠️ 判据**只有** `.strm` 文件存不存在这一条 —— 不看 CD2 挂载视图。
> 挂载视图对「CD2 改名失败」这个主成因必然判错（残留与正式文件字节数相同，
> 它照样显示"可见、大小一致"），这正是 v0.3.0 把它整条删掉的原因。

#### 「strm 疑似异常」标签里的两个列表（容易混淆）

这个标签同屏显示两段，**它们的处境完全不同**：

| 列表 | 含义 | 能不能操作 |
|---|---|---|
| **观察中** | 刚同步成功，正在等 .strm 生成（宽限期内） | ❌ 只读。此刻文件大多正常，给操作按钮会诱导误删 |
| **待处理（疑似异常）** | 宽限期过了仍没等到 .strm | ✅ 每个条目都有「尝试生成 strm」「删旧重传」「忽略」 |

> 为什么分开：观察中的文件只是"还没轮到"，而待处理的是"需要你判断"。
> 混在一起会让人去处理一批本来会自己好的文件。

#### 每个列表都分页

四个标签的全部列表（共 5 个：strm 标签里有两个）**都按每页 15 条分页**，
超出时页面底部出现翻页条。

- **每个标签的页码是独立的**：在队列翻到第 3 页，切到「已忽略」不会被带过去；
- **strm 标签里的两个列表也各有各的页码**：翻「待处理」不会把上面的
  「观察中」一起翻走；
- 条目数变少时（同步成功后会被移出）页码会自动回退到有效范围，
  不会让你停在空白页。

> 为什么必须分页：这几个列表都会随媒体库增长。实测数据是队列 102 条、
> 观察中 91 条、对账缺失 102 条 —— 每条都是一个卡片，一次全渲染既卡顿
> 也没法浏览。

> 📌 「已忽略」列表的「恢复对账」按钮曾有一个**只在第 2 页起才会出现**的缺陷：
> 点第 2 页的某条会删掉另一条（页内序号被当成了全表序号）。已在 v0.3.1 修掉。

### 8.6.1 同步时能看进度吗 —— 能

同步跑起来后，看板顶部会出现一块**进度卡片**（空闲时整块消失，不占地方）：

```
☁ 传输                        电视剧 (1/3)              已运行 12 分 30 秒
━━━━━━━━━━━━━━━━━━━━━━━━━━━  47%
📄 丹道至尊 S01E135.2160p.WEB-DL.H265.AAC.mp4
⚡ 12.4MB/s   ⏳ 约剩 0:14:22   📦 61/102 个文件
```

它显示：**当前传哪个文件、整批百分比、实时速率、预计剩余、已完成/总数**。

#### 实机发现：进度条「停在 100% 不动」多半是在对账

这是部署到真机后发现的，值得记住：**102 个文件那轮，rsync 只跑了 2 秒**
（全部命中了 115 秒传，不需要真的传字节），而**随后的对账核对了 3 分半**。

所以进度卡的行为是：进度条很快冲到 100% → 阶段变成「对账核对」→
那段时间进度条不动。**这是正常的**，插件正在逐个核对云端文件是否完整。

（对账阶段不会再说「没有收到 rsync 输出」—— 那时 rsync 已经退出了，
说那句话会让人去查一个没在跑的进程。）

#### 三条你需要知道的

| 现象 | 说明 |
|---|---|
| **秒传的文件 0% 直接跳 100%** | 正常。115 秒传不传字节，没有中间过程 |
| **ETA 会来回跳** | 正常。它按瞬时速率估算，只作参考 |
| **出现「⚠️ 已 N 秒没有收到 rsync 输出」** | 说明 rsync 现在没在动。扫描/收尾阶段短暂静默是正常的；**长时间**（超过你配置的「rsync I/O 超时」+ 60 秒）插件会判定停滞并中止本轮 |

> 最后那条不是吓唬人：在此之前你只能看到「正在同步 ⏳」五个字，
> 一次 28 分钟的传输全程黑屏，**根本分不出"在慢慢传"与"卡死了"**。

#### 为什么进度只在看板上有

远程命令（`/rsync_status`）**不报进度**，是有意为之：进度每秒都在变，
用聊天渠道推送只会变成刷屏，而它更适合"看一眼结论"。
手机上想看进度，打开看板插件页面即可 —— 同步运行期间页面会自动每 5 秒刷新
（空闲时 30 秒），不用手动点刷新。

#### 任务结束后进度就没了，这正常吗

正常。进度是**正在跑的进程**的观测，不是可恢复的状态 —— 进程结束（或被中断）
它就没有意义了，所以插件不会把它存下来。

也因此：**重启插件/容器会中断正在进行的传输**，而 rsync 会从头再传
（本插件刻意不用 `--partial`：115 的秒传要求完整文件参与哈希，断点续传
反而会让已传部分作废）。传输期间请避免重载插件。

### 8.7 边界与注意

- 观察、扫描、判定全程**纯本地文件检查，零 115 API 开销**；巡检 30 分钟一轮
  （例外：8.3.1 的「先尝试生成 strm」会让助手访问 115，因此是手动触发）
- **不会自动删除重传**：疑似 ≠ 确诊，删除是破坏性操作，必须你确认
- **不会自动补生成 strm**：同样手动触发，避免清单大时自动放大对 115 的访问量
- **观察期状态可在看板查看**：提示条会显示「交叉验证进行中 N 个文件处于观察期」，
  这属于正常等待，不是异常；也可用 8.4 的「检查 strm」手动催一下判定，不必等巡检
- **观察期内只提供只读操作**（检查 strm）：不提供删旧重传，避免诱导用户删掉
  刚传好的文件、白耗配额
- ⚠️ **「删旧重传」不再清理云端残留**（v0.3.0 起）：插件只删你点名的那一个
  正式文件（相对路径精确对齐的那条路径）。此前它会顺带扫同目录、把
  `<正式名>.<6位随机>` 形态的残留一并删掉，那条能力随「云端可见性」整套
  判定一起删除了 —— 残留识别本事就来自那套判据。若云端确实堆了残留，
  需要手动清（见常见问题 `..xrp4gj` 一节）
- 若 strm 插件关闭或大面积漏生成，会产生成批误报 —— 报警后请先确认
  strm 插件本身正常，再逐个处理
- 「先尝试生成 strm」**只对配了「网盘目录」的映射可用**；没配的映射下，
  这些文件会留在疑似清单里并明确告知，不会被静默跳过
- 补生成条目回到观察期后，**主动扫描不会再把它报成疑似**（否则刚点完按钮
  就被下一次扫描打回原形，功能等于没作用）。这类条目由观察窗口自行判定，
  扫描结果里会单独列出「已在观察期未重复计入」的数量
- **非视频文件不参与本验证**：字幕/图片/元数据不会生成 strm，因此不进入观察期、
  也不会出现在疑似清单里（详见 8.1 的说明）。升级前版本遗留在清单里的这类条目，
  插件会在**载入时自动清理**并记入日志，无需手动处理；也可用看板的
  「清理无效条目」按钮主动清一次
- **判据只有 `.strm` 存不存在这一条**（v0.3.0 起）：CD2 挂载视图**不参与任何
  判断** —— 它对改名失败这个主成因必然给出相反结论（见 8.6），据此摘掉条目
  等于静默忽略一个真的坏了的文件

## 8.8 收到的通知在说什么

同步完成后会推一条报告。它有两种形态，看「**实际传输**」那个数字即可区分：

| 通知 | 含义 |
|---|---|
| 📤 **实际传输 N 个** · 核对 M 个 | 这一轮真的上传了 N 个文件，其余 M−N 个云端已有（秒传/已存在） |
| ✅ **完成（无需上传）** · 核对 M 个 | 这一轮**一个字节都没传** —— 候选的 M 个文件云端全都已存在且大小一致 |

> **为什么要区分**：`核对 M 个` 是"交给 rsync 检查的候选数"，不是"传了几个"。
> 命中 115 秒传时 rsync 直接跳过、不传字节，所以候选 102 个也可以是 0 传输。
> 此前这两种情况都被说成「本次处理 102 个文件，全部完整上传到位」，
> 而那句话在一轮没有任何上传时也照发 —— 与实际不符。

> 📌 v0.3.1 还修了一个**每 2 小时复发一次**的问题：已同步完成的条目会在插件
> 重载时被一份陈旧快照复活，于是"重新冷却 → 再跑一轮 → 全部跳过 → 又报一次成功"
> 无限循环（累计推送 69 次成功通知）。修掉之后这类重复通知不会再出现。

## 8.8.1 本插件的能力边界（重要，请先读）

**本插件没有直连 115 网盘的能力。** 它对 115 的所有读写都要经过
**CloudDrive2（CD2）挂载点** —— 也就是说，它看到的是 CD2 呈现给它的视图，
不是 115 服务端本身。

这决定了两件事：

| 你想知道 | 能不能 | 说明 |
|---|---|---|
| 云端文件**大小**对不对 | ✅ 能 | 读挂载点的大小，与源端比对。但**大小一致不等于云端可用**（见下） |
| 云端文件**是不是真的完好** | ❌ **不能** | 见下方「为什么大小不可信」 |
| 删除云端文件 | ⚠️ **间接** | 删挂载点上的文件，由 CD2 转发成 115 的删除。**插件无法验证 CD2 是否真的转发了** |

### 为什么"大小一致"不能证明云端可用

CD2 改名失败时，115 上只剩一个形如 `影片.mkv..xrp4gj` 的**残留**，而它与正式文件
**字节数完全相同**（实测）。于是：

- rsync 的 `--size-only` 会认为"已同步"而跳过 → 重传永远不会发生
- 读挂载点大小也会显示"一致" → 看起来一切正常

**两种常规手段都分辨不出来。** 这就是本插件把判据交给 `.strm` 的原因 ——
它由 strm 助手在**视频正确上传到云端之后**才生成，是唯一与"云端真的可用"
同构的信号。

> 也因此，看板上的「对账异常清单」反映的是**挂载视图**的缺失/大小不符，
> 不是"云端一定坏了"。反过来也一样：对账通过**不代表**云端一定完好。

## 8.9 数据存在哪里（备份时看这里）

三处，备份时别漏：

| 数据 | 位置 | 丢了会怎样 |
|---|---|---|
| **文件台账** | 插件数据目录下的 `ledger.sqlite3` | 队列/观察/待处理/忽略**全部重置**；扫描会重新发现源端文件，但冷却与观察期从头计时 |
| **用户配置** | MoviePilot 平台的数据库（开关 / cron / 目录映射 / 扩展名…） | 需重新配置 |
| **运行态小状态** | MoviePilot 平台的数据库（扫描游标、限流窗口用量、忽略规则、对账异常清单、webhook 计数） | 游标回到当日 0 点，会重扫一遍（幂等吸收） |

> **扫描游标为什么不能手改**：实测往回拨游标会让**已同步完成的文件重新入队**
> —— 队列的去重只在条目还在队列里时生效，而同步成功后台账行已被删除，
> 那个文件就再没有"已处理过"的记录。于是它会重新冷却、重新上传一轮。
>
> 想"捞一批老文件"请用「**扫描存量并补传**」：它按**状态**（源端存在、且从未
> 被本插件处理过）筛，不按时间猜，天然不会重新发现已同步的文件，
> 而且会**先预览再确认**。

## 9. 常见问题

### 入库了很多文件，看板里的数量却对不上

**先看这条**：如果看板出现
「🔍 源端扫描已 X 未推进」，说明**入库发现的主通道停摆了** ——
新文件根本不会被发现。按提示检查「源端扫描入库」开关是否开启、映射源目录是否
可读。这种情况下的"数量对不上"是症状，不是原因。

若扫描正常运行、数量仍对不上，按顺序排查：

1. **文件是否在映射的源目录内**：不在任何映射里的文件不会被同步，
   日志会给出「路径不在任何映射内」并列出你当前配置的源目录。
2. **扩展名是否在白名单内**：被挡下的文件会进看板的
   「⏭ 有文件因扩展名不在同步白名单被跳过（累计）」提示，按扩展名分桶列出。
   **这一条以前是完全看不见的** —— 判定只写 debug 日志，界面上零痕迹，
   于是"某一类文件 100% 被丢弃"能潜伏很久。现在它会在第一次发生时就被看到。
3. **是否在忽略清单里**：看板「已忽略」标签页可查。
4. **是否已经在队列里**：重复投递是幂等的（不重复入队、不刷新冷却）。

> 历史上还有一类原因：插件曾订阅宿主的「整理完成」事件，而**音频文件在当时
> 的默认扩展名白名单里一个都没有**，于是一批音频在入队闸门第一行就被丢弃。
> 2026-09-25 起默认白名单已补上音频与 `sup/sub/idx/vtt` 字幕。
> 如果你从更早的版本升级且改过那一栏，旧配置**不会**被自动迁移
> （迁移只作用于"从未改过"的配置）—— 建议对照配置页的新默认值检查一遍。

> 若以上都没有解释，把日志级别调成 `DEBUG` 后复现一次：
> 入队闸门会列出被跳过文件的扩展名与原因。

### 上传被拒 / 提示风控退避

触发限流了。等待退避结束即可，或调低「单窗口上传文件数上限」。

### 文件一直显示「缺失未同步」

1. 先用「立即同步」手动触发该文件
2. 若仍失败，检查源文件是否存在、CD2 挂载是否正常
3. 确实不想同步的存量文件，加入「忽略清单」即可不再报警

### 字幕没有同步

- 确认「同步的扩展名」包含你要的字幕格式。默认已包含
  `srt,ssa,ass,sup,sub,idx,vtt` —— 其中 `sup`/`sub`/`idx` 是蓝光转制常见的
  图形字幕，早期默认值里**没有**它们，只认前三个会导致"部分外挂字幕静默丢弃"
- 存量字幕需要**补传一次**才会纳入
- 补传时媒体文件会自动带上同主名的字幕一起传

### 补传进度卡住不动

说明当前窗口配额用尽或处于退避期。看板顶部会显示原因与恢复时间，
**不需要任何操作**，定时巡检会自动继续。

### 115 上出现 `影片名.mkv..xrp4gj` 这类临时文件

**是什么**：这是上传未完成时留下的半成品。rsync 先把文件写成
`<正式文件名>.<随机后缀>`（后缀形如 `xrp4gj`），**全部传完后才改名为正式文件名**。

**最常见的成因（实测确认）**：文件其实**已经传完**，最后一步「改名为正式文件」失败了 ——
通常是**网络波动导致 CD2 的改名请求没有成功**（改名要真实调用 115 接口）。
这种情况下临时文件**大小与正式文件一致**，只是名字没改过来。
另一种成因是传输中途被中断（任务超时被杀、插件重载），此时临时文件较小。

**为什么插件看不到它**：插件所有判断都基于 CD2 挂载点；而这类残留**只出现在
115 云端**（网页版 / APP），挂载点视图里往往没有它（CD2 视图与 115 服务端可能不一致）。
所以看板、对账清单都不会显示它 —— 不是插件漏了，是它在插件的视野之外。
**清理它只能去 115 云端手动删除。**

**危害**：

| | 影响 |
|---|---|
| 会占空间吗 | ✅ 会。若改名失败（最常见成因），大小与正式文件**完全一致** |
| 会被媒体服务器识别吗 | ❌ 不会。扩展名是随机后缀，不被刮削器当作视频 |
| 会越来越多吗 | ⚠️ 有可能。每次中断都会新增一个，且**插件不会自动清理** |

#### 怎么处理

**第一步：确认它确实是临时文件**（而不是正常影片）。
名字形如 `xxx.mkv..` 后面跟 6 位随机字符，且**没有第二个点**，就是残留。
正规文件名不会在扩展名后再出现 `..`。

**第二步：在 115 云端（网页版 / APP）里删掉它。**
用文件名搜索定位后直接删除即可。**不需要停插件、不需要改配置**——
插件不引用这个文件，删掉不影响同步记录与冷却队列。

**第三步（重要）：确认正式文件是否真的在 115 上。**
在 115 云端看同目录下有没有**没有随机后缀**的同名正式文件：

- **有正式文件** → 只差改名那一步其实已经补救成功，删掉残留即可，无事发生
- **没有正式文件** → 说明这次入库实际没完成（改名失败了）。删掉残留后，
  需要让插件把文件重新传一次 —— 见下方「怎么触发重传」

#### 怎么触发重传

**首选（v0.1.4 起，一条指令闭环）**：

```
/rsync_retry 黄泉的使者 S01E03
```

插件会自动完成三步：**在源目录按关键字定位文件 → 删除 115 端的旧文件 → 立即定向重传**。
「先删再传」是关键：CD2 视图可能显示文件"存在且正常"，`--size-only` 会因此跳过重传；
先经挂载点删除（CD2 会真实调用 115 删除接口），两边状态强制对齐后，
重传产物才是干净的正式文件。

| 情况 | 操作 |
|---|---|
| 知道是哪个文件没传上 | **`/rsync_retry 文件名`**（首选，一步到位） |
| 看板「对账异常清单」里有这个文件 | 点「定向重试失败文件」，或发 `/rsync_retry`（重传整个异常清单） |
| 只记得剧名/部分文件名 | `/rsync_retry 关键字` 同样适用；想先看列表再选，用 `/rsync_search` + `/rsync_confirm` |
| 想立即全量核对一遍 | 发 `/rsync_force`（注意：会遍历 115 挂载点，API 开销大，7 天冷却） |

**带关键字重传的安全护栏**：

- 关键字一次最多匹配 15 个文件，超出会**直接拒绝**并提示缩小范围 ——
  删除是破坏性操作，宁可不执行也不大范围误伤；
- 只按「源端相对路径 → 目标端同路径」**精确**删除，绝不按关键字模糊删除；
- 删除失败的文件会跳过并明确告知（此时视图可能仍是脏的，带脏视图重传会被
  `--size-only` 跳过，白占配额）；
- 关键字只搜**源端**，云端 `..` 中缀的残留（如 `xxx.mkv..xrp4gj`）不在源端清单里，
  **这条指令不直接删它**。v0.2.5～v0.2.x 期间删掉目标端正式文件后会顺带清理
  同目录里属于该文件的残留，**v0.3.0 起不再清理**（那条能力来自「云端可见性」
  判据，已整套删除）—— 云端已有的残留需要手动删。

#### 怎么减少它再次出现

1. **网络波动是主因**：这类残留多发生在「文件传完、改名失败」的瞬间，
   根源是 CD2 与 115 之间网络抖动，插件侧无法避免，只能事后清理。
2. **调大 I/O 超时**：配置页「rsync I/O 超时」默认 600 秒。若 115 上传经常
   中断，可适当调大（CD2 挂载下大文件单次 I/O 慢是正常现象）。
3. **避免在同步中途重启插件**：同步期间重载插件会杀掉 rsync 进程，
   必然留下半成品。
4. **让单次传输量小一些**：减小「单批文件数上限」，每批处理更少文件，
   单批被中断波及的文件更少。

#### 关于默认排除规则 `..*`（重要说明）

配置页默认排除规则里有一条 `..*`，但它**挡不住你遇到的这种形态**：

| 排除写法 | 匹配的名字 | 能否挡住 `影片.mkv..xrp4gj` |
|---|---|---|
| `..*`（当前默认） | **以 `..` 开头**的名字 | ❌ **挡不住**（`..` 在中间） |
| `*..*` | **任何位置含 `..`** 的名字 | ✅ 能挡住 |

若要挡住这类临时文件，把排除规则里的 `..*` 改成 **`*..*`**。
（这是实测 rsync 通配行为得出的结论，不是推测。）

> ⚠️ 注意两点：
> 1. **排除规则只作用于源端**——它只防止把源端的临时文件传到 115，
>    **无法清理 115 上已经存在的残留**，已存在的仍需手动删。
> 2. 改排除规则属于配置变更，改完记得点「保存配置」。

### 修改了「同步的扩展名」，老文件会重新同步吗

不会自动重新同步。扩展名过滤只作用于**入队时刻**，已入库的老文件不受影响。
如果要让新扩展名的存量文件参与同步，请执行一次**补传**。

## 9. 手机端使用说明

插件已针对手机端（窄屏）做过适配，界面会自动切换布局：

- **按钮**不再溢出卡片 —— 宽度不足时按钮组自动换行或纵向堆叠；
- **列表条目**（冷却队列 / 异常清单 / 已忽略）在窄屏改为上下排布：
  上面是文件名与状态，下面是操作按钮，避免文件名被挤成几个字；
- **选项卡**（冷却队列 / 异常清单 / 已忽略）标签较长时，会出现左右滚动箭头，
  可横向滑动切换；
- **设置页**的开关从右侧移到说明下方，底部「查看看板 / 保存配置」各占一行。

适配断点为屏幕宽度 **600px**：小于 600px 用纵向布局，大于等于则恢复桌面横排。

> 若在手机上看仍有元素溢出，多数是浏览器缩放或宿主弹窗容器宽度异常所致，
> 可先尝试关闭浏览器缩放（保持 100%）再观察。

## 10. 兼容性说明

- 从 v0.0.10 起，插件会自动把**从未修改过**的旧默认配置迁移到新默认值

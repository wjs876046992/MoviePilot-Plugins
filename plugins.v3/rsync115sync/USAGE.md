# 115 网盘同步助手 — 本地使用说明

> 面向使用者的操作手册。开发与设计说明见 [DEVELOPMENT.md](./DEVELOPMENT.md)，
> 待办事项见 [TODO.md](./TODO.md)。
>
> 当前版本：**v0.1.8**

---

## 1. 这个插件能做什么

把本地媒体库（NAS 上的电影 / 剧集）通过 `rsync` 同步到 CloudDrive2（CD2）挂载的
115 网盘目录，并具备：

- **入库冷却**：新入库的媒体先等 N 小时再上传，留时间给外挂字幕下载和刮削
- **双向对账**：同步后核对源端与目标端文件大小，找出缺失和残缺文件
- **上传限流**：控制单位时间的上传文件数，避免触发 115 风控
- **存量补传**：把启用插件之前就已入库的历史文件补齐到 115
- **手机指令**：通过聊天指令查看状态、重试、忽略文件

---

## 2. 前置条件（务必先确认）

### 2.1 依赖 CD2 挂载

本插件通过 **rsync 写入 CD2 的 FUSE 挂载点**来间接上传到 115，自身不调用 115 的
API。因此：

1. 宿主机上必须已用 CloudDrive2 把 115 网盘挂载到本地路径（例如
   `/volume2/CloudNAS/115`）
2. 如果 MoviePilot 跑在 Docker 容器里，**必须把宿主机上的 CD2 挂载路径和本地媒体
   目录一并映射进容器**，建议挂载模式使用 Slave 共享（可读写）

> ⚠️ 两个路径都不可省略。只映射了本地媒体目录、没映射 CD2 目录，同步会直接失败。

### 2.2 系统需支持 rsync

容器或宿主机内需能执行 `rsync`。Debian/Ubuntu 系：

```bash
apt update && apt install -y rsync
```

### 2.3 目录写入权限

MoviePilot 进程需要对 CD2 挂载目录有写权限，否则 rsync 会以权限错误退出。

## 3. 快速上手（三步）

### 第一步：配置目录映射

打开插件配置页，在「同步目录映射对」中点击**添加目录映射**，每组填写：

| 字段 | 说明 | 示例 |
|---|---|---|
| 任务备注名称 | 仅用于日志与清单显示，建议用短名 | `电视剧` |
| 本地源目录 | NAS 上的媒体目录（宿主机/容器内均可访问的路径） | `/volume3/HomeTheater/emby/TV` |
| CD2 挂载 115 目录 | CD2 挂载点下对应的目标目录 | `/volume2/CloudNAS/115/TV` |
| 同步所有文件类型 | 关闭=只传扩展名白名单内的文件（推荐） | 关闭 |

> 💡 任务备注名称会成为文件清单的前缀（如 `电视剧:剧名/剧名 S01E01.mkv`），
> 改名不会导致重复同步，但会让旧的异常清单条目失去对应关系，建议一次定好。

### 第二步：确认冷却与限流参数

默认值适合大多数场景，**建议先按默认跑一段时间**再调整：

| 参数 | 默认 | 作用 |
|---|---|---|
| 入库冷却延迟时长 | 2 小时 | 入库后等多久才上传 |
| 定时检查 Cron | `0 */2 * * *` | 每 2 小时巡检一次 |
| 单批文件数上限 | 200 | 单次 rsync 提交多少文件 |
| 单窗口上传上限 | 500 | 一个窗口内累计上传多少文件 |
| 限流窗口时长 | 1800 秒 | 窗口长度，到期额度重置 |
| 命中风控后退避 | 3600 秒 | 命中风控后暂停多久 |

配置页会实时把限流参数换算成**速率**（如「约 17 个/分钟」），并给出参数合理性提醒。

### 第三步：保存并观察

保存配置后，看板会显示冷却队列与异常清单。新入库的媒体会在冷却结束后自动上传。

## 4. 存量补传（重要）

### 4.1 什么情况下需要补传

本插件只能感知**启用之后**发生的入库事件。对于以下文件，看板看不到、也永远不会
自动同步：

- 安装 / 启用插件之前就已经入库的媒体
- 插件处于停用期间入库的媒体
- 因扩展名不在白名单而从未入队的文件（例如早期版本遗漏的字幕）

**需要补传一次，把它们纳入 115。**

### 4.2 两种触发方式

**看板按钮**：点「补传存量媒体」→ 插件先本地扫描 → 弹出确认框显示候选数量与预计
需要多少个限流窗口 → 确认后开始。

**聊天指令**：发送 `/rsync_backfill`。

### 4.3 补传的代价（务必理解）

- **扫描阶段零开销**：只读本地磁盘，不会请求 115
- **传输阶段有开销**：每个候选文件至少要向 115 发一次校验请求。已存在的文件会被
  rsync 跳过（不会重传），但这次请求省不掉

所以补传前那个确认框很重要 —— 它告诉你候选有多少个。**候选数 ≈ 最少请求次数**。

> 💡 如果候选过多（上万），建议先只补字幕：把「同步的扩展名」临时改为
> `srt,ssa,ass`，补完再改回来。

### 4.4 补传会自动分批

补传受**单批上限**与**窗口配额**约束，一次跑不完是正常的：

```
建立队列(比如 5000 个)
  → 本轮传 200 个（单批上限）
  → 窗口内累计到 500 个后暂停（窗口配额）
  → 等下一个窗口，定时巡检自动续跑
  → 循环直到队列排空
```

进度会持久化，**插件重载、宿主重启都不会丢失**，无需重新点击。看板会显示剩余数量。
想中止就点「取消补传」或发 `/rsync_backfill_clear`。

## 4.5 Webhook 入库（第二来源）

### 4.5.1 它能解决什么问题

现有的入库监听挂在宿主的**「整理完成」事件**上。它看不到这三类入库：

| 场景 | 为什么看不到 |
|---|---|
| 你**手动**把文件拷进媒体库 | 没经过下载器/整理流程，不产生整理事件 |
| **外部工具**（其它脚本、其它容器）搬入文件 | 同上 |
| 整理事件**漏发** | 宿主的事件走 durable outbox，超过重试上限即**永久丢弃**，不会重放 |

Webhook 作为**补充来源**覆盖它们。注意是补充**不是替代** —— 同一份入库可能同时
从两条路进来，插件内部的重复检测会保证：**不重复上传，也不刷新冷却计时**。

### 4.5.2 通道 A：Emby（推荐，无需额外配置）

宿主原生支持 Emby 的 webhook。你只需要在 **Emby 后台 → 通知 → Webhooks** 里添加：

```
http://<moviepilot地址>:3001/api/v1/webhook/?token=<API_TOKEN>&source=<emby实例名>
```

- `token` 填 MoviePilot 的 API Token（设置 → 安全 → API Token）
- `source` 填你在 MoviePilot 里配置的 **Emby 实例名**。可省略，但多实例时建议填，
  否则宿主可能解析到别的实例上
- 事件勾选**新媒体入库**一类即可

> ✅ **播放类事件填了也没关系**：插件只处理入库类事件（`library.new` 等）。
> 播放、标记、收藏类事件一律忽略 —— 这一点很重要，因为播放事件同样携带文件路径，
> 不忽略的话「你看一集，那集就会被重新上传一次」。

本插件侧**不需要任何配置**（默认已启用 `emby` 渠道）。想关掉就把配置页
「Webhook 入库 → 来源渠道」清空并保存（会自动回落到默认值 `emby`），
或直接关闭「监听媒体转移入库事件」总开关 —— webhook 与该总开关联动。

#### 顺带一条：自定义发送端也可以走平台的 webhook 地址

发送端（自建脚本、MDC-ng 之类）都走**同一个**平台 webhook 地址 + 一个专属标识，
由插件认领。这是**唯一**的入口（插件自带的端点在 2026-09-22 已移除，见 4.5.3）：

```bash
curl -X POST "http://<mp>:3001/api/v1/webhook/?token=<API_TOKEN>&source=rsync115sync" \
  -H "Content-Type: application/json" \
  -d '{"paths": ["/volume3/HomeTheater/emby/电影/x.mkv"]}'
```

好处是鉴权交给宿主（API Token）、请求有宿主日志；代价是需要填对 `source`。
也可用请求头 `X-Webhook-Target: rsync115sync` 代替查询串。

> ⚠️ `source` 必须**恰好**是 `rsync115sync`。这个标识是插件用来认领报文的唯一凭据，
> 写成别的值（包括写成 `emby`）插件都不会处理 —— 而写成 `emby` 更糟：那会让报文
> 被宿主的 Emby 解析器接管，插件一条日志都不会有。

> ⚠️⚠️ **`Content-Type` 必须与 body 形态匹配，否则请求根本到不了插件。**
> 这是实测踩过的坑，也是「平台能看到请求、插件却一行日志都没有」的头号原因。
>
> 宿主端点在调用插件之前会先解析表单。若你声明
> `Content-Type: multipart/form-data` 却发**裸 JSON body**（没有 boundary ——
> 很多 webhook 配置界面的「Content-Type 下拉框」会诱导这么选），宿主会直接返回
> **400 Missing boundary in multipart**，请求在进入本插件之前就被拒。
> 此时插件看不到任何东西，宿主日志里只有一条内容为空的 400。
>
> **改法：把 Content-Type 改成 `application/json`**（或直接不带这个头）。
> 发 JSON 就不要声明 multipart；两者混用宿主不接受。已验证：同一个报文、仅改这一个
> 请求头，行为从「400 + 插件零日志」变成「200 + 正常入队」。

**先把这条路单独打通，再去调那个工程**（发送端还没摸清时，这能省下大量来回）：

```bash
curl -i -X POST "http://192.168.1.8:3001/api/v1/webhook/?token=<API_TOKEN>&source=rsync115sync" \
  -H "Content-Type: application/json" \
  -d '{"event":"download.finish","data":{"title":"某电影 (2024)","source_path":"/volume3/9KG/某电影 (2024)"}}'
```

> ⚠️⚠️ **注意 `webhook` 后面那个 `/` —— 少一个斜杠就全部失效。**
> 宿主把端点注册为 `/`（`app/api/endpoints/webhook.py` 的 `@router.post("/")`），
> 最终地址是 `/api/v1/webhook/`。写成 `/api/v1/webhook?token=...`（缺尾斜杠）
> 会在**路由层**被 starlette 重定向：
>
> ```
> POST /api/v1/webhook?token=...&source=rsync115sync HTTP/1.1 307 Temporary Redirect
> ```
>
> 此时请求**没有到达插件**，插件一行日志都不会有 —— 现象和「发送端没配」完全一样。
> 这是真机第二次踩到的坑，且比 Content-Type 那个更隐蔽：**307 看起来像「已成功投递」**
> （静默跟随后结果确实是 200），只有插件侧的彻底沉默暴露了问题。
> 改法：地址补上尾斜杠，其余不动。

期望：HTTP **200** + body `{"success":true}`，插件日志出现一条
`监听到 N 个新入库文件（... 路径来源=候选字段）`，看板「平台解析入口到达」+1、
「最近报文样本」出现这条报文。**这四样齐了，就说明插件侧没问题**，
剩下的差异全在发送端。

> 💡 上面的路径请换成你**映射源目录下真实存在**的路径。若插件日志说
> 「取到的路径不属于任何映射」，那就不是 Content-Type 的问题了 ——
> 它会把你当前配置的全部映射源目录列出来，照着改报文即可。

**发送端的 Content-Type 改不了怎么办**：这是**发送端侧**的问题，插件无法兜底
（请求在进入插件之前就被宿主拒了）。可选的途径：

- 找一个能改请求头的中间层（反代、`curl` 脚本、n8n/HomeAssistant 之类的转发节点），
  由它把 Content-Type 写对再转给平台地址；
- 若该工具支持，直接把 Content-Type 设为 `application/json`（或干脆不带这个头）。

> ⚠️ **本插件自 2026-09-22 起不再自带端点**，因此没有「换个地址绕开」这条路了。
> 此前那个免登录端点正是为了绕开这类发送端限制而存在，但它同时意味着
> 向网络暴露一个可写入接口，而宿主端点已能满足同一需求（鉴权交给宿主）。
> 少一个暴露面，少四条容易配错的安全配置。理由与取舍见 DEVELOPMENT §9.18。
>
> 也正因如此，**唯一的地址就是宿主端点**，尾斜杠必须带（见上一条）。

**报文形态参考**（另一个工程常用的形态，字段名不必完全一致，见下）：

```jsonc
{
  "event": "download.finish",
  "data": {
    "title": "某电影 (2024)",
    "first_actor": "某人",
    "source_path": "/volume3/9KG/某电影 (2024)",   // ← 入库位置，插件要的就是它
    "target_path": "/9KG/某电影 (2024)"
  }
}
```

`source_path` 这个字段名**本来就在候选表内**，且 `data` 也是已知的嵌套容器 ——
所以这个形态无需任何配置即可识别。**它此前没生效的原因不是字段名，而是 Content-Type。**

> 📌 **`source_path` 是目录也可以。** 插件会自己展开成目录内的文件
> （只收扩展名白名单内的、跳过 `@eaDir` 这类排除目录），发送端不必先遍历目录。

**走这条路时，日志长什么样？**

- **认领成功** → 一条 `INFO ... 监听到 N 个新入库文件（... 路径来源=...）`。有它就说明通了。
- **声明了 `source=rsync115sync` 但没认领成功** → 现在会留下 **info** 级日志，
  明确写出是「取不到路径」还是「路径不属于任何映射」，并列出当前配置的映射源目录。
  （此前这里是静默的 debug —— 那正是「插件看不到任何日志」的成因。）
- **完全没有任何日志** → 报文没到插件。去看宿主日志里那条请求的状态码：
  **4xx 且内容为空**基本就是上面的 Content-Type 问题；看板上的
  「平台解析入口到达」计数也能帮你判断（它由插件在解析入口统计，
  没有到达就不会增加）。

看板顶部有这几个数字，组合起来就是结论：

| 看板现象 | 结论 |
|---|---|
| 「平台解析入口到达」= 0 | 报文**没到插件**：查地址尾斜杠、Content-Type、API Token |
| 到达 > 0，但「收到事件」= 0 | 到了但**没认领**：日志会写明原因（取不到路径 / 路径不在映射内） |
| 到达 > 0 且有入队日志 | 正常 |

「到达 = 0」时，**按这个顺序查**（前两个都踩过，第三个最常见）：

1. **地址有没有尾斜杠** —— 见上面的 307。发送端日志里的 `307 Temporary Redirect`
   就是它的指纹。
2. **Content-Type 是否与 body 形态匹配** —— 见上面的 400。宿主日志里一条
   内容为空的 400 就是它的指纹。
3. `token` 是否为宿主的 API Token、`source` 是否**恰好**是 `rsync115sync`。
4. **插件版本是否包含本次修复** —— 若你用的版本早于本次改动，则存在一个
   **插件自身**的缺陷：它实现了认领逻辑却没有向宿主声明（`get_module()`），
   因此宿主从不会调用它，表现为**宿主的 200/307 都正常、插件彻底无反应**。
   这类失效没有任何日志可查（详见 DEVELOPMENT §9.17）。**升级插件即修复。**

   **怎么一眼确认版本对不对**：看插件启动日志里有没有这一行 ——

   ```
   [Rsync115Sync] 认领钩子已注册（webhook_parser 已向宿主声明）…
   ```

   没有它（或看到 `认领钩子**未注册**` 的 error）就说明环境里的插件不是含本次
   修复的版本，先更新插件再排查。另外在宿主的 DEBUG 日志里，
   **`请求插件 xxx 执行：webhook_parser`** 这条信息级日志才代表插件真被调用了；
   只出现 `请求系统模块执行：webhook_parser` 而**没有**前者，即表示插件未被收集。

   > ⚠️ **若「检查更新」里看不到本插件**：本插件的版本号没有变化（alpha 阶段
   > 不占版本号，见下），而宿主判断「有无更新」是比较**已安装版本号 < 索引版本号**，
   > 两者相等时不会提示更新。此时请用**重新安装**的方式覆盖（市场里对本插件
   > 执行重装，或删掉插件目录后重新安装），装完刷新页面并看上面那行启动日志确认。

一次推多个文件时，报文的 `paths` 数组会被**全部**入队（不是只取第一个）。

### 4.5.3 自建端点（已于 2026-09-22 移除）

**宿主不认识的发送端也能走平台入口**，因此不再需要自建端点。

早先的做法是插件自带一个免登录端点（`POST /api/v1/plugin/Rsync115Sync/webhook`），
理由是 MDC-ng 一类的发送端不会被宿主解析。但这条路要付出两处代价：

1. **多一个可写入的暴露面** —— `allow_anonymous` 意味着知道地址的人都能往插件里灌数据，
   伪造入库会真实消耗 115 风控配额；
2. **多四条容易配错的安全配置** —— 端点开关、密钥、路径白名单、来源 IP 白名单，
   配错任何一条都可能「看起来开着、其实没防住」。

而它解决的问题用平台入口就能解决：发送端把 `source` 指到 `rsync115sync`
（或带 `X-Webhook-Target: rsync115sync` 头）即可，**鉴权由宿主用 API Token 负责**，
请求也有宿主日志可查。这个判断经复查成立，因此端点与其四条配置一并移除。

> 📌 若你此前配了这个端点，**升级后请把发送端地址改成平台入口**（见 4.5.2）：
> 旧地址会返回 404。这一条只影响「当初没用平台入口」的发送端 —— 用 Emby 的话
> 本来就一直在走平台入口，无需任何改动。

### 4.5.5 怎么确认这条路通了

看板顶部会显示 webhook 的四项计数：**收到 / 入队 / 被拒 / 未识别**（外加「平台解析入口到达」），
以及两个更具体的：

- **最近报文的字段结构**（只记字段名与类型，**不记值**）—— 用于日志排障；
- **最近报文样本（含值）** —— 展开就能看到发送端实际传了什么，值已截断、密钥已隐去。

两个都留着是有原因的：结构摘要告诉你**有哪些字段**，但答不出「值长什么样」——
而字段能否被识别为路径，恰恰取决于值的形态（`/vol3/x.mkv` 是路径，`12345` 是媒体库 ID）。

| 看到的现象 | 结论 |
|---|---|
| 收到 = 0 | 请求根本没到插件：查地址尾斜杠、Content-Type、宿主 API Token、`source` 是否写对 |
| 收到 > 0，入队 = 0，未识别 > 0 | 到了但字段名对不上：展开「最近报文样本」，把字段名反馈给插件以扩展候选表 |
| 收到 > 0，被拒 > 0 | 认领阶段未通过（路径不在任何映射内等），日志会写明原因 |
| 收到 > 0，入队 > 0 | 正常。若队列没涨，说明这些文件**已经在队列里**（幂等，不重复入队） |
| 收到 > 0，消息显示「目录已展开但无文件入队」 | 目录收到了，但里面没有符合扩展名的文件（或全在忽略清单里）|

日志里的关键词：`监听到 N 个新入库文件（... 路径来源=...）` —— 这里的「路径来源」
会告诉你是从 `item_path`、`json_object.Item.Path` 还是候选字段取到的路径。

#### 发送端推「目录」还是「文件」？

**两种都支持，推目录更省事。** 推目录时插件会自己展开成文件（只收扩展名白名单内的、
跳过 `@eaDir` 这类排除目录），所以另一个工程下完一部电影后，直接把电影目录发过来即可，
不必先遍历目录、也不用担心它算错了文件名。

展开有上限（默认 500 个文件/次）：推整个媒体库根目录会被截断，日志里会写明少了多少 ——
这既是防止一次灌爆冷却队列，也是提示你改推具体子目录。

**推单个文件时的补充规则（只对「同步所有文件类型」映射生效）**：勾选了该选项的映射，
若发送端只推来**一个文件**，插件会把**同目录的其它文件一并入队**（只取同一层，不递归子目录）。
原因是该选项承诺「这个目录下的文件都要上传」，而发送端手里往往只有「整理完成的那一个文件」，
它不知道同目录还有哪些文件。未勾选该选项的映射不受影响：只入队被推来的那个文件
（上传范围由「同步的扩展名」决定，不会因为这条规则扩大）。

> 例：9KG 映射勾选了「同步所有文件类型」，发送端推来 `/volume3/9kg/某电影 (2024)/movie.mkv`
> → 队列里会同时出现同目录的 `movie.zh.srt`、`poster.jpg`、`movie.nfo` 等**全部**文件。
> 单目录超过 300 个文件时截断，日志会写明漏掉多少。

> 典型用法：另一个工程下完 9KG 内容后，POST 一个目录路径到**平台入口**即可 ——
> ```bash
> curl -X POST "http://mp:3001/api/v1/webhook/?token=<API_TOKEN>&source=rsync115sync" \
>   -H "Content-Type: application/json" \
>   -d '{"Event": "download.finish", "path": "/volume3/9kg/某电影 (2024)"}'
> ```
> 目录里只放媒体文件时，`Event`/`path` 之外的字段随便叫什么都能识别（候选字段表）；
> 若字段名不在候选表内，看板的报文样本会让你一眼看出该报哪个名字。

## 5. 上传限流：为什么慢，为什么不能快

115 会统计**单位时间内上传的文件个数**。大量小文件（尤其是字幕、样张）在短时间内
集中上传，最容易被判定为异常流量，导致上传被拒绝甚至临时封禁。

插件用两层限制来规避：

| 机制 | 限制什么 | 防的是 |
|---|---|---|
| 单批文件数上限 | 一次 rsync 提交多少文件 | 命令行过长、单次请求峰值 |
| 窗口配额 | 一段时间内累计多少文件 | **115 风控（主要闸门）** |

超出部分**不会丢失**，会在下一个窗口自动继续。

另外，如果 rsync 的错误输出中出现风控特征（`429`、`too many requests`、`频繁` 等），
插件会**立即暂停上传并进入退避**，等退避结束后再继续。

> 💡 如果你频繁看到「风控退避中」，说明限流阈值还是偏松。可以降低
> 「单窗口上传文件数上限」，或延长「限流窗口时长」。配置页会在速率超过
> 每分钟 60 个时给出告警。

## 8. strm 交叉验证（自动发现上传异常）

> **依赖说明（先看这个）**
>
> 本插件**绝大多数功能不依赖任何外部插件**，包括整个 strm 交叉验证链路的
> 观察、扫描、清理与**删旧重传** —— 它们只读本地文件系统。
>
> **唯一例外**是 8.3.1 的「先尝试生成 strm」，它需要
> **P115StrmHelper**（且需要额外两处配置，见该节）。不装、不配都不影响其它功能，
> 只是不能使用这一个可选的增强项。
>
> 配置页与看板上对该项均以「依赖 P115StrmHelper」标注区分。

### 8.1 它解决什么问题

CD2 改名失败后，挂载视图显示「文件存在且正常」，插件的全部判断都被蒙蔽 ——
看板一切正常、对账无异常，但 115 云端实际只有改名失败的半成品。
**strm 交叉验证用一个与 CD2 无关的独立视角发现这种假成功。**

原理：strm 类插件（如 P115StrmHelper）依据媒体库文件在本地生成 .strm 指针文件，
它判断「文件是否可用」的依据与 CD2 挂载无关。若某文件同步成功后、
宽限期内对应的 .strm 始终没出现，大概率上传并未真正完成。

### 8.2 怎么启用

1. 在映射配置的「strm 目录」填入 strm 插件的输出根目录（与源目录**不同根**，
   由你手动配置；**留空则该映射不启用验证**）
2. 前提条件：strm 文件名与整理后文件**同名**（仅扩展名不同），
   且目录结构与源端一致（源端 `A/B/剧名 S01E03.mkv` → strm 端 `A/B/剧名 S01E03.strm`）
3. 可调「观察宽限期」（默认 6 小时，配置页「strm 交叉验证」模块）：
   strm 生成不实时（可能在上传/刮削中），宽限期内不报警。
   配置页同时显示「N / M 个映射已配置」，便于确认配置是否生效
4. **（可选）想用「先尝试生成 strm」的话**，还需要额外配两处，见 8.3.1

### 8.3 发现疑似异常后

疑似清单在**独立的「strm 疑似异常」标签页**内（不再混在对账异常清单里），
有两种处理方式，**建议按顺序**：

#### 8.3.1 第一步：先尝试生成 strm（推荐先做这个）

> ⚠️ **本节是全插件唯一依赖 P115StrmHelper 的功能**。
> 不想装助手的话，跳过本节，直接用 8.3.2 的删旧重传 —— 其余功能一概不受影响。

「缺 strm」其实有**两种成因**，处理成本差很多：

| 成因 | 云端实际状态 | 正确处置 |
|---|---|---|
| **① 助手漏生成** | 文件是好的，只是没生成指针 | 请助手重新生成即可，**无需重传** |
| **② CD2 假成功** | 只有改名失败的半成品 | **必须删旧重传** |

插件在本地视角**无法区分**这两者（表现完全一样）。但借助手遍历一次云端目录就能
判别：生成成功 ⇒ 是 ①；生成后仍无 ⇒ 是 ②，此时再做删旧重传就心里有数了。

操作：看板 strm 标签页点「**先尝试生成 strm**」（或单条点「尝试生成 strm」）。
被请求的文件会移回「观察中」重新计时（**1 小时**），之后：

- strm 出现 → 自动解除，结束（**省下一整轮删除与上传**）
- 1 小时到仍无 → 回到疑似清单，标记为「**补生成后仍无**」，
  此时「云端确实缺文件」的可能性比首次疑似大得多，该考虑删旧重传了

移回观察期是**有意**的：那里有现成的判定机制（自动巡检 + 手动检查），
你不必盯着看 —— 点「检查 strm」就能立刻知道结果，什么都不点也会有
自动兜底（窗口到就回到清单，不会丢）。

> ⚠️ 这里的 1 小时是**固定值**，不跟随你的「宽限期」配置。
> 两者量的是不同的东西：宽限期量「rsync 报成功 → strm 出现」的刮削/入库延迟，
> 而这里等的是助手的一次云端目录遍历。把宽限期调大（比如 24h）不该连带让
> 补生成的结果在半天内无法判定。

> **配好它需要两处配置**（缺一不可）：
>
> 1. **本插件配置页**：在对应映射里填「**网盘目录**」——
>    这是该目录在 115 网盘里的**真实路径**（如 `/HomeTheater/TV`），
>    不是 CD2 挂载路径。本地 strm 目录与网盘目录是两棵独立的树，
>    无法自动推导，所以必须单独填。
> 2. **P115StrmHelper 配置页**：该网盘路径必须已配在它的
>    「**全量同步路径**」里。助手的 `/p115_strm` **只接受这个列表里的路径**，
>    配在它其它字段（如「监控生活路径」）里的目录传过去会被拒绝，
>    提示「路径匹配错误」——**而这个提示只发给助手侧，本插件看不到**，
>    表现为「点了按钮什么也没发生」。遇到这种情况请先核对助手配置。
>
> 例：本插件填 `/HomeTheater/TV`，助手「全量同步路径」里需有
> `/media/strms/TV#/HomeTheater/TV` 这样的映射行。

**为什么是手动触发**：这一步会让助手**访问 115 网盘**（按目录遍历云端子树）。
清单有几十条时自动触发就等于自动打出几十次遍历，因此设计为手动、逐目录去重，
且单次涉及目录数有上限（默认 20 个，超过则**整批拒绝**，不会自动放大访问量）。

#### 8.3.2 第二步：删旧重传

上一步看到「补生成后仍无」（或你已明确知道是假成功），再执行：

| 方式 | 操作 | 适用场景 |
|---|---|---|
| **单条「删旧重传」** | 点击该行按钮 → 确认 | 只处理个别文件 |
| **「全部删旧重传」** | 点区域标题右侧按钮 → 确认 | 清单规模小、想一次清完（会提示总数） |
| **批量勾选** | 点上方「批量选择」→ 勾选若干条 → 点工具栏按钮 | 从清单里挑一部分处理（推荐） |

三种方式都是「删除 115 端该文件 → 立即定向重传 → 传完自动复核 strm」
（生成即自动解除，无需再确认），点击前都会弹确认框。

> ⚠️ 目录名含**连续空格**的文件不会出现在补生成参数里（命令通道会把连续空格
> 折叠成单个，导致助手侧匹配失败）。这类文件请直接用删旧重传，不要指望补生成。

**批量勾选的一个细节**：勾选状态是**跨分组保留**的，因此提交时按**选中项的
成分**自动分流，而不是按你当前在哪个标签页：

- 全部为 strm 项 → 执行「删旧重传」
- 混合选择 → 先弹确认框说明分流规则，再分别提交
- 纯普通项 → 普通定向重传

两条通道对目标端文件的处理并不一样，这也是为什么必须分流：

| 你选中的条目 | 目标端实际状态 | 处理方式 |
|---|---|---|
| 对账：缺失 | 文件不存在 | 直接补传 |
| 对账：残缺 | 文件在，大小不符 | 先清理残缺再传 |
| **strm 疑似** | 文件在，**大小一致** | **必须删旧再传**，否则 rsync 认为「已同步」直接跳过 |
| 冷却队列中的正常文件 | 文件在，大小一致 | rsync 自动跳过，不传也不删，不会浪费流量 |

最后两行的区别是本功能存在的原因：**它们在大小上完全一样**。
「上传坏得很彻底」和「本来就传好了」在 `getsize()` 眼里无法区分，
只有 strm 疑似清单能提供这个判断。因此删除操作**只对 strm 疑似清单开放**
（服务端另有一道校验，非清单内的 key 一律拒绝）。

**误报是安全的**：若只是 strm 插件自身漏生成（媒体不识别等），
重传一个已同步的文件也不会重复上传（rsync `--size-only` 跳过）。

### 8.4 观察期：不用干等，可以立即检查

观察期默认 6 小时（请求过补生成的条目是 1 小时），而自动巡检**30 分钟才跑一轮**。
若你刚跑完 strm 生成任务、或在文件管理器里看到 .strm 已经出来了，不必等下一轮
—— 看板上可直接检查：

| 操作 | 位置 | 作用 |
|---|---|---|
| **检查 strm** | 每个观察中条目的右侧按钮 | 只查这一个文件 |
| **立即检查全部** | 观察期小标题右侧 | 一次查完所有观察中条目 |
| 远程命令 | `/rsync_strm check` | 同上（全部） |

观察期里有两类条目，看板会分别标出，**等的对象不同**：

| 标记 | 来源 | 等什么 | 窗口 |
|---|---|---|---|
| `观察中` | 刚同步成功 | 刮削/入库传播后生成 .strm | 「宽限期」配置值（默认 6h） |
| `已请求生成` | 你点过「先尝试生成 strm」 | 助手遍历云端目录 | 固定 1h |

检查结果立即反映在看板上：

- **已生成** → 立刻解除观察（不再占用清单）
- **仍未生成且窗口内** → 继续等待（属正常，不会误报）
- **仍未生成且窗口已过** → 转入「疑似异常」清单，此时才需要判断是否删旧重传
- 源端文件已删 / 映射取消 strm 目录 → 移出观察

> 对「已请求生成」的条目，窗口过了回到清单时，会带上「补生成后仍无」标记 ——
> 意思是「生成动作已经做过而指针文件仍不出现」，判断强度比首次疑似高得多，
> 此时才值得考虑删旧重传。

> 纯本地文件读取，**不访问 115、不消耗配额、不与同步冲突** ——
> 同步任务跑着的时候照样可以查。
>
> 为什么这里只放「检查」而不放「删旧重传」：观察期的文件刚同步成功，strm 可能
> 还在生成中，此时提供删除按钮只会诱导误操作（删掉刚传好的文件、白耗一次删除
> API 与重传配额）。「检查」是只读的，没有这个风险。

### 8.5 通知

发现新的疑似异常时会**推送一条通知**（受众按宿主「通知场景开关」，默认仅管理员），
内容含文件清单、判定依据与处理入口。两个设计点：

- **只在新发现时提醒一次**：清单里的旧条目不会每轮重复推送，避免被静音；
- **全部恢复时补推一条「已全部解决」**，让你知道之前的告警已经处理完
  （而不是被静默遗忘）。恢复后若再有新发现，会重新提醒。

可在配置页关闭通知总开关（与同步报告共用 `notify` 开关）。

### 8.6 窗口到了还是没有 strm —— 先看「云端可见性」

这是补生成最常见的落空方式，也最容易白动手。本插件**分不出**下列几种成因，
所以不会替你下结论，但你也不必自己去 115 里翻：

| 实际成因 | 云端情况 | 删旧重传 |
|---|---|---|
| 从未传成功 | **没有**这个文件 | ✅ 对症（且删除是空操作，不会白删） |
| CD2 改名失败 | 只剩 `..xxx` 残留，正式名不存在 | ✅ 对症 |
| 传到一半中断 | 有，但大小不符 | ✅ 对症 |
| 助手没识别媒体 / 压根没执行 | **文件是好的** | ⛔ 删了纯属白删 |

前三种处理方式一样，第四种才是坑。条目回到疑似清单时，看板会给出一条
**「云端可见性」**探测结论帮你区分，`🔎` 开头：

| 显示 | 含义 | 该怎么办 |
|---|---|---|
| `云端不可见…删旧重传可修` | 云端没有正式文件 | 直接删旧重传 |
| `云端有文件但大小不符…删旧重传可修` | 传到一半 | 直接删旧重传 |
| `云端可见且大小一致…请先查 strm 生成侧` | **文件很可能完好** | 先查助手配置与生成日志 |
| `云端可见性未知` | CD2 挂载未就绪 / 读不到大小 | 稍后刷新看板重试 |

> 探测只是**读** CD2 挂载点里的大小，纯本地调用、零 115 API、不改动任何文件。

**唯一一处它会拦住你的地方**：你若对「可见且大小一致」的条目点「删旧重传」，
插件会拒绝并说明理由 —— 而不是默默执行。原因很实际：`rsync --size-only`
见大小一致会直接跳过，**删了也传不上去**，白耗一次云端删除与一次限流配额，
问题原样还在。这时正确的排查方向是生成侧（助手配置、媒体识别）。

> ⚠️ **这条探测有一个已知的假阳性方向，务必知道**：
> CD2 挂载视图可能过期（云端实际只有改名失败的残留，视图却显示大小正常，
> 见常见问题里 `..xrp4gj` 那一节）。此时它会显示成「可见且大小一致」。
> 因此**它只能作为「先别动手」的建议，不能作为「文件一定是好的」的结论**。
> 你如果已经在 115 上亲眼确认文件是坏的，请以你自己的判断为准 ——
> 重启同步任务即可重新探测并照常执行删旧重传。

### 8.7 边界与注意

- 观察、扫描、判定全程**纯本地文件检查，零 115 API 开销**；巡检 30 分钟一轮
  （例外：8.3.1 的「先尝试生成 strm」会让助手访问 115，因此是手动触发）
- **不会自动删除重传**：疑似 ≠ 确诊，删除是破坏性操作，必须你确认
- **不会自动补生成 strm**：同样手动触发，避免清单大时自动放大对 115 的访问量
- **观察期状态可在看板查看**：提示条会显示「交叉验证进行中 N 个文件处于观察期」，
  这属于正常等待，不是异常；也可用 8.4 的「检查 strm」手动催一下判定，不必等巡检
- **观察期内只提供只读操作**（检查 strm）：不提供删旧重传，避免诱导用户删掉
  刚传好的文件、白耗配额
- 该验证**不覆盖**云端 `..xrp4gj` 残留的清理 —— 残留仍需 115 云端手动删
- 若 strm 插件关闭或大面积漏生成，会产生成批误报 —— 报警后请先确认
  strm 插件本身正常，再逐个处理
- 「先尝试生成 strm」**只对配了「网盘目录」的映射可用**；没配的映射下，
  这些文件会留在疑似清单里并明确告知，不会被静默跳过
- 补生成条目回到观察期后，**主动扫描不会再把它报成疑似**（否则刚点完按钮
  就被下一次扫描打回原形，功能等于没作用）。这类条目由观察窗口自行判定，
  扫描结果里会单独列出「已在观察期未重复计入」的数量
- 「云端可见性」探测（8.6）**只读、只写回条目、不参与任何清单清理**：
  即使它显示「可见且大小一致」，条目也不会自动从清单里消失 —— 它有已知的
  假阳性方向，据此摘掉条目等于静默忽略一个可能真的坏了的文件

## 9. 常见问题

### 入库了很多文件，看板里的数量却对不上

v0.1.0 之前存在这个问题：**字幕和音轨文件不会被计入**。

原因是 MoviePilot 按文件类型把「整理完成」拆成三个不同的事件，插件早期只监听了
其中「视频文件」那一个，于是外挂字幕全部被漏掉。假设一季 40 集、每集带 1 条字幕，
你入库 46 个文件、插件只看到 40 个（字幕 6 个完全没记录）。

v0.1.0 起已同时监听三类事件，数量应与实际入库一致。

**另外**：如果看板出现「🕳️ 检测到 N 个文件可能因插件重载错过了入库事件」，
说明那批事件发生在插件正忙（同步会触发插件重载）的瞬间，事件已经永久丢失。
插件会在每轮同步开头扫描本地源端目录把它补回来 —— 这点扫描**不访问 115**，
不产生风控风险。补回的文件不再等待冷却，下次同步直接上传。

> 若数量仍然对不上，请把日志级别调成 `DEBUG` 后复现一次，
> 查看 `整理完成事件未产生入队` 那行会列出收到的文件数与跳过原因。

### 看板「冷却中」的数量和日志对不上 / 数字迟迟不降

按以下顺序排查：

**第一步：确认插件版本。** 启动日志现在会打印一行摘要，以版本号开头：

```
[Rsync115Sync] v0.1.0 初始化完成 | 启用=True 监听入库=True | 冷却=2.0h | 监听事件=transfer.complete,...
```

如果这行显示的版本低于 **v0.1.0**，请先升级 —— v0.1.0 之前只监听「视频文件」事件，
**外挂字幕完全不会被计入**，数量必然对不上。用版本号即可一眼确认，不必再猜。

**第二步：看事件日志。** v0.1.0 起每条事件都记录，含版本号、事件类型和**具体路径**：

```
v0.1.0 监听到 1 个新入库文件（事件=transfer.complete），已加入 2.0h 延迟冷却队列: S01/E01.mkv
v0.1.0 整理完成事件未入队（事件=transfer.complete，共 1 个路径：不在任何映射内 1），请检查目录映射是否覆盖: /other/E09.mkv
v0.1.0 事件中的 1 个文件已在冷却队列中，未刷新其冷却计时（事件=transfer.complete，队列共 9 条）
```

- **第一条**：正常入队。
- **第二条**：路径不在你配置的「同步目录映射」范围内 —— 按提示的路径去检查映射。
- **第三条**：同一事件被重复投递（正常现象，不会重复计时，也不会重复上传）。

**关于「每条日志只有 1 个文件」**：这是正常的。MoviePilot 的**入库事件是按文件逐个发布的**
（10 个文件入库 → 10 次事件），而**手机/微信收到的入库通知是按整批合并成一条**的 ——
两者是不同机制，不要拿通知的条数去对比事件日志。

**关于「文件已不存在」**：整理后目标文件被移走或删除时，会有一条 **DEBUG** 级日志
（默认不显示）。这属正常现象，不会影响同步。

**关于「整理很慢」**：MoviePilot 默认单线程整理（`TRANSFER_THREADS=1`），
一个几十集的剧集包逐个刮削重命名，耗时几十分钟到数小时都属正常。
可在宿主主日志看到 `正在整理 （M/N）文件名 ...` 的进度；只要 M 在增长就没问题。

**第三步：区分「源端已删除」。** 文件入库后又被删除时，队列条目要等到冷却到期、
下轮同步才会真正清理。这期间看板会把它单独显示为 **「🗑️ 源端已删除待清理」**，
**不再计入「冷却中」与「就绪」数字**。

**关于「已就绪」迟迟不下降**：冷却到期后需要等下一轮定时同步才会处理并移出队列，
不是到期瞬间清零。可以先点「同步已就绪媒体」手动触发一次。

### 上传被拒 / 提示风控退避

触发限流了。等待退避结束即可，或调低「单窗口上传文件数上限」。

### 文件一直显示「缺失未同步」

1. 先用「立即同步」手动触发该文件
2. 若仍失败，检查源文件是否存在、CD2 挂载是否正常
3. 确实不想同步的存量文件，加入「忽略清单」即可不再报警

### 字幕没有同步

- 确认「同步的扩展名」包含 `srt,ssa,ass`（v0.0.10 起已默认包含）
- 存量字幕需要**补传一次**才会纳入
- 补传时媒体文件会自动带上同主名的字幕一起传

### 补传进度卡住不动

说明当前窗口配额用尽或处于退避期。看板顶部会显示原因与恢复时间，
**不需要任何操作**，定时巡检会自动继续。

### 115 上出现 `影片名.mkv..xrp4gj` 这类临时文件

**是什么**：这是上传未完成时留下的半成品。rsync 先把文件写成
`<正式文件名>.<随机后缀>`（后缀形如 `xrp4gj`），**全部传完后才改名为正式文件名**。

**最常见的成因（实测确认）**：文件其实**已经传完**，最后一步「改名为正式文件」失败了 ——
通常是**网络波动导致 CD2 的改名请求没有成功**（改名要真实调用 115 接口）。
这种情况下临时文件**大小与正式文件一致**，只是名字没改过来。
另一种成因是传输中途被中断（任务超时被杀、插件重载），此时临时文件较小。

**为什么插件看不到它**：插件所有判断都基于 CD2 挂载点；而这类残留**只出现在
115 云端**（网页版 / APP），挂载点视图里往往没有它（CD2 视图与 115 服务端可能不一致）。
所以看板、对账清单都不会显示它 —— 不是插件漏了，是它在插件的视野之外。
**清理它只能去 115 云端手动删除。**

**危害**：

| | 影响 |
|---|---|
| 会占空间吗 | ✅ 会。若改名失败（最常见成因），大小与正式文件**完全一致** |
| 会被媒体服务器识别吗 | ❌ 不会。扩展名是随机后缀，不被刮削器当作视频 |
| 会越来越多吗 | ⚠️ 有可能。每次中断都会新增一个，且**插件不会自动清理** |

#### 怎么处理

**第一步：确认它确实是临时文件**（而不是正常影片）。
名字形如 `xxx.mkv..` 后面跟 6 位随机字符，且**没有第二个点**，就是残留。
正规文件名不会在扩展名后再出现 `..`。

**第二步：在 115 云端（网页版 / APP）里删掉它。**
用文件名搜索定位后直接删除即可。**不需要停插件、不需要改配置**——
插件不引用这个文件，删掉不影响同步记录与冷却队列。

**第三步（重要）：确认正式文件是否真的在 115 上。**
在 115 云端看同目录下有没有**没有随机后缀**的同名正式文件：

- **有正式文件** → 只差改名那一步其实已经补救成功，删掉残留即可，无事发生
- **没有正式文件** → 说明这次入库实际没完成（改名失败了）。删掉残留后，
  需要让插件把文件重新传一次 —— 见下方「怎么触发重传」

#### 怎么触发重传

**首选（v0.1.4 起，一条指令闭环）**：

```
/rsync_retry 黄泉的使者 S01E03
```

插件会自动完成三步：**在源目录按关键字定位文件 → 删除 115 端的旧文件 → 立即定向重传**。
「先删再传」是关键：CD2 视图可能显示文件"存在且正常"，`--size-only` 会因此跳过重传；
先经挂载点删除（CD2 会真实调用 115 删除接口），两边状态强制对齐后，
重传产物才是干净的正式文件。

| 情况 | 操作 |
|---|---|
| 知道是哪个文件没传上 | **`/rsync_retry 文件名`**（首选，一步到位） |
| 看板「对账异常清单」里有这个文件 | 点「定向重试失败文件」，或发 `/rsync_retry`（重传整个异常清单） |
| 只记得剧名/部分文件名 | `/rsync_retry 关键字` 同样适用；想先看列表再选，用 `/rsync_search` + `/rsync_confirm` |
| 想立即全量核对一遍 | 发 `/rsync_force`（注意：会遍历 115 挂载点，API 开销大，7 天冷却） |

**带关键字重传的安全护栏**：

- 关键字一次最多匹配 15 个文件，超出会**直接拒绝**并提示缩小范围 ——
  删除是破坏性操作，宁可不执行也不大范围误伤；
- 只按「源端相对路径 → 目标端同路径」**精确**删除，绝不按关键字模糊删除；
- 删除失败的文件会跳过并明确告知（此时视图可能仍是脏的，带脏视图重传会被
  `--size-only` 跳过，白占配额）；
- 关键字只搜**源端**，云端 `..` 中缀的残留（如 `xxx.mkv..xrp4gj`）不在源端清单里，
  **不会被这条指令碰掉** —— 残留仍需在 115 云端手动删除。

#### 怎么减少它再次出现

1. **网络波动是主因**：这类残留多发生在「文件传完、改名失败」的瞬间，
   根源是 CD2 与 115 之间网络抖动，插件侧无法避免，只能事后清理。
2. **调大 I/O 超时**：配置页「rsync I/O 超时」默认 600 秒。若 115 上传经常
   中断，可适当调大（CD2 挂载下大文件单次 I/O 慢是正常现象）。
3. **避免在同步中途重启插件**：同步期间重载插件会杀掉 rsync 进程，
   必然留下半成品。
4. **让单次传输量小一些**：减小「单批文件数上限」，每批处理更少文件，
   单批被中断波及的文件更少。

#### 关于默认排除规则 `..*`（重要说明）

配置页默认排除规则里有一条 `..*`，但它**挡不住你遇到的这种形态**：

| 排除写法 | 匹配的名字 | 能否挡住 `影片.mkv..xrp4gj` |
|---|---|---|
| `..*`（当前默认） | **以 `..` 开头**的名字 | ❌ **挡不住**（`..` 在中间） |
| `*..*` | **任何位置含 `..`** 的名字 | ✅ 能挡住 |

若要挡住这类临时文件，把排除规则里的 `..*` 改成 **`*..*`**。
（这是实测 rsync 通配行为得出的结论，不是推测。）

> ⚠️ 注意两点：
> 1. **排除规则只作用于源端**——它只防止把源端的临时文件传到 115，
>    **无法清理 115 上已经存在的残留**，已存在的仍需手动删。
> 2. 改排除规则属于配置变更，改完记得点「保存配置」。

### 修改了「同步的扩展名」，老文件会重新同步吗

不会自动重新同步。扩展名过滤只作用于**入队时刻**，已入库的老文件不受影响。
如果要让新扩展名的存量文件参与同步，请执行一次**补传**。

## 9. 手机端使用说明

插件已针对手机端（窄屏）做过适配，界面会自动切换布局：

- **按钮**不再溢出卡片 —— 宽度不足时按钮组自动换行或纵向堆叠；
- **列表条目**（冷却队列 / 异常清单 / 已忽略）在窄屏改为上下排布：
  上面是文件名与状态，下面是操作按钮，避免文件名被挤成几个字；
- **选项卡**（冷却队列 / 异常清单 / 已忽略）标签较长时，会出现左右滚动箭头，
  可横向滑动切换；
- **设置页**的开关从右侧移到说明下方，底部「查看看板 / 保存配置」各占一行。

适配断点为屏幕宽度 **600px**：小于 600px 用纵向布局，大于等于则恢复桌面横排。

> 若在手机上看仍有元素溢出，多数是浏览器缩放或宿主弹窗容器宽度异常所致，
> 可先尝试关闭浏览器缩放（保持 100%）再观察。

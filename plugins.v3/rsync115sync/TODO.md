> ⚠️ **与下方原始设计稿的最大差异：只有一条通道。**
> 设计稿的「通道 B：插件自建 `allow_anonymous` 端点」已于 2026-09-22
> **整体移除**（含四条防护配置与看板字段）。
> 原因：宿主端点对**任何**发送端都收得下报文，只是不认识发送端身份；
> 插件用 `webhook_parser` 认领（发送端带 `source=rsync115sync`）就能拿到它 ——
> 「宿主不替我们解析」不等于「宿主不替我们收」。
> 拆除的完整理由、代价与哨兵见 **DEVELOPMENT §9.18**。
> 下文设计稿保留原样，供对照；**凡涉及通道 B 的段落均已作废**。

### 已核实的关键结论（最终态）

| 来源 | 宿主支持 | 结论 |
|---|---|---|
| **Emby** | ✅ 原生（`app/modules/emby/` 有 `webhook_parser`） | 走平台链路即可 |
| **MDC-ng** | ❌ 宿主**不认识**（40+ 模块中无 mdc-ng/mdcz），但**收得下**其报文 | 同样打平台地址，`source` 填 `rsync115sync`，由插件认领 |
| **自建脚本** | — | 同上；只发 query string 也行（宿主另注册了 `GET /`） |

插件侧必须做的一件事：在 `get_module()` 里声明 `{"webhook_parser": self.webhook_parser}` ——
**只写方法定义等于死代码**（宿主不调用、不报错、无日志），见 DEVELOPMENT §9.17。

**已知残留风险**（DEVELOPMENT §4.0f ④ 记录）：冷却基准取 `min(发现时刻, mtime)`

**现状**：实测未观察到这种写入形态；真出现也不静默损坏 —— 会落进残留/对账异常

代价是 `_pending_queue` 的**值**从 `float` 变成 `{basis, hash/mtime}`，涉及持久化
结构迁移（需处理旧格式与新格式共存）。

- [ ] 注意顺延不能无限循环：连续 N 轮仍在变化应告警而不是永远等

### [ ] 10.5 CD2 上传/排队核对统一到「失败判定」入口（保持可选，已决策）

**现状缺口**：CD2 的「在传/排队」核对目前**只用在 strm 疑似那条路**
（`strm_ops._cd2_suppress_new_suspects`），**对账失败那条路完全不查**。
于是大文件还在上传、目标端暂时不存在或大小不符时，会被立即判为
`missing`/`corrupt` 并报警；下一轮才可能自行纠正。

**判据本身已经写好且很谨慎，不需要新造**（`cd2.py:120-134`）：

- 在传/排队集合 = 排队中 / 预处理中 / 传输中 / 已暂停 / 队列中；
- **刻意不含 `FINISH`** —— 完成却没有 strm，正是要抓的异常；
- **刻意不含 `ERROR`** —— 那是真的没传上去，应当继续报警；
- 卡死任务超过 `CD2_SUPPRESS_MAX_HOURS` 后失去豁免（`cd2_ops.py:226-254`），
  避免把真故障永久藏起来。

**方案**（待精简方案阶段 1 落地 `failed` + `fail_reason` 之后再做，
否则等于在旧的三份失败清单上各改一遍）：

- [ ] 把 `_cd2_suppress_new_suspects` 提升为通用的 `_cd2_in_flight(keys)`，
      三处判失败前统一调用：`missing` / `corrupt` / `no_strm`
- [ ] `failed` 允许回退：后续巡检若 CD2 出现对应在传任务，改回等待态，不重复报警
      （rsync 刚写完时 CD2 可能还没扫到挂载点，单次检查会漏）
- [ ] 未启用 CD2 时的诚实文案：配置页/看板明说「正在上传的大文件可能被暂时判为
      失败，下一轮会自动纠正」，不得让用户以为关掉 CD2 没有代价

**已决策：保持可选**（默认关闭、需 URL + Token），**不做成失败判定的必需前置** ——
否则会给插件引入凭据依赖，没配 CD2 的用户会拿到一堆「上传中」误报。

**必须保留的安全语义**：`None`（查不到/未启用）≠「没在传」，按本地判据走；
`FINISH`/`ERROR` 的刻意排除；卡死豁免上限。

## P3 — 观察项

### [ ] 11. 补传排空期间常规同步被推迟

`_scheduled_sync` 中补传优先，同轮只跑一种模式（共用执行锁与窗口配额）。
补传队列未排空时常规同步会推迟。队列自终止，暂可接受，**若用户反馈延迟明显**
再考虑改为按比例分配配额。

### [ ] 12. 大文件与超时参数的匹配

I/O 超时已对齐 shell 的 600 秒，但 `task_timeout` 默认 3600 秒（单次任务总上限）
是否够用，取决于媒体库规模与网络状况，需实机观察。

### [ ] 13. 多映射对时的配额分配

当前所有映射对共享同一份窗口配额，**先跑的映射对会先消耗额度**。
若用户有多组映射且希望公平分配，需重新设计（暂无明显需求）。

# 115 网盘同步助手 — 开发进度与问题清单

> 使用说明见 [USAGE.md](./USAGE.md)，待办事项见 [TODO.md](./TODO.md)。
>
> 本文记录本轮迭代（v0.0.4 → v0.1.8）的设计决策、发现的问题与遗留风险，
> 供后续迭代参考。

---

## 1. 迭代背景

插件最初的实现参考了同工作区的 shell 脚本方案
（`sync_115/sync_to_115.sh` 等）。一次全面代码走查后，与 shell 方案逐项比对，
发现若干**功能缺失、逻辑错误与风控风险**，因此进行了系统性改造。

**核心约束（用户明确要求）**：尽量不要全盘扫描 115 挂载路径。CD2 是 FUSE 挂载，
本地 `stat` 会真实请求到 115 服务器，按文件数计费，极易触发风控。

## 3. 本轮修复的问题

### 3.1 P0 — 看板按钮永久禁用（v0.0.4）

**现象**：看板「立即同步」「对账异常清单」的按钮点不动，与冷却状态无关。

**根因**：`:disabled` 绑定写成了

```javascript
:disabled="statusData.is_running || (itemLoading && itemLoading !== item.key)"
```

`itemLoading` 初值是**空字符串**而非 `null`，所以 `itemLoading && ...` 求值结果是
字符串 `""`。Vue 对布尔型 prop 有 `shouldCastTrue` 转换，会把 `""` 与属性名
`"disabled"` 一并转为 `true`（见 `@vue/runtime-core` 的 `setFullProp`）。

这正是「为什么其它按钮正常、只有这三个点不动」的原因 —— 其余按钮绑定的是纯布尔
表达式，只有这三处用了返回字符串的 `&&`。

**修复**：`!!itemLoading && ...` 强制转为布尔。

**验证方式**：用真实 Vue 运行时做了隔离复现，确认旧写法渲染为 disabled、
新写法可点击、纯布尔对照组正常。

### 3.2 P0 — rsync 非零退出码被误判为成功（v0.0.6）

**现象**：rsync 失败时用户仍收到「全部完整上传到位」。

**根因**：`has_error` 只在 `subprocess.TimeoutExpired` 分支置位，rsync 返回非 0
时从不置位。而成功判定是

```python
is_success = (not has_error and not total_missing and not total_corrupt)
```

增量对账恰好没发现问题时，就会判成功。

**修复**：按 shell 的 `_handle_rsync_exit` 语义分类 —— `0` 成功、`23/24` 可容忍告警、
其余致命。致命时置位并记录退出码；同时修正通知分支，致命失败**即使异常清单无变化
也必须上报**。

### 3.3 P0 — force 全量扫描可无限触发（v0.0.9）

**现象**：`/rsync_force` 是插件 API 开销最大的操作（遍历 115 全目录），
却可被随意反复触发。

**修复**：7 天冷却闸门；且**只有成功才计入冷却**（失败可立即重试排障）。
另外补上了缺失的 `--include` / `--exclude="*"` 过滤 —— 此前 force 模式既无
`--files-from` 也无任何 include 规则，等于对整棵目录树做无差别全量 rsync。

### 3.4 P1 — 缺少字幕与幽灵文件排除（v0.0.10）

- 默认扩展名缺 `srt/ssa/ass`。冷却机制的设计意图就是「留足外挂字幕下载时间」，
  字幕不入队意味着**它永远不会同步**，设计目标落空。
- 默认排除规则缺 `..*`（rsync 中断残留的临时文件）。
  > ⚠️ **事后实测修正**：`..*` 只能匹配**以 `..` 开头**的名字，而 rsync 残留的
  > 典型形态是 `影片.mkv..xrp4gj`（`..` 在**中间**），因此该规则**实际挡不住
  > 主流形态**，要挡住应使用 `*..*`。详见 3.10。

**修复**：对齐 shell 的完整扩展名列表与超时值；默认排除加 `..*`。
配套做了**老配置平滑迁移**：仅当取值恰好等于旧默认串时才替换，用户自定义值不动。

### 3.5 P2 — 文档与代码不符（v0.0.8）

README 声称「默认启用 `--inplace --size-only --modify-window=2`」，但代码明确
「绝不使用 `--inplace`」（为了兼容 115 秒传）；且宣传的 `/rsync_clean` 命令
**从未实现**。已订正，并补全实际支持的 9 条指令。

### 3.6 P1 — 看板首行圆角被裁（v0.0.5 / v0.0.12 补注）

**现象**：看板页面首行三个数据卡片顶部圆角显示不全，视觉上"缺了 radius"。

**根因**：宿主默认给 `.v-card-item + .v-card-text` 设置了

```css
padding-block-start: 0 !important;
```

内容区顶部内边距被强制归零，首行数据卡片紧贴卡片上沿，其顶部圆角落入父级
`.page-main-card` 的 `overflow-hidden` 裁剪范围内，因而被切掉。

**修复**：在内容区显式写 `padding-block-start: unset` 归一化顶部内边距，
并用 `margin-top: 16px` 提供标题与内容的间距 —— margin 不受该 padding
`!important` 约束，是稳定生效的方案。

> ⚠️ **维护提醒**：`padding-block-start: unset` 一行是在**真实宿主页面调试后**加入的，
> 且**必须带 `!important`**。宿主该声明本身即 `!important`，级联顺序为
> 重要度 > 权重 > 源码顺序，普通声明无论权重多高都覆盖不了 `!important`；
> 必须同样以 `!important` 且更高权重才能生效。
> 又因该属性非继承、`unset` 对非继承属性求值等同 `initial`（0px），
> 在多数情况下与宿主取值一致；显式声明的价值在于**宿主日后改动该值时不会复现圆角问题**，
> 属稳定性加固。**请勿凭「理论等价」删除该行。**

### 3.8 P0 — 入库事件漏听：46 个文件只监听到 3 个（v0.1.0）

**现象**：实际入库 46 个文件，插件只记录了极少数（用户反馈「只监听到 3 个」）。

**根因**：宿主**按文件类型把整理结果拆成三个不同的事件**，插件只注册了其中一个。
见 `app/chain/transfer/settlement.py` 的 `_durable_transfer_event`：

| 文件类型 | 宿主广播的事件 | 插件是否监听（修复前） |
|---|---|---|
| 主要媒体（mkv/mp4…） | `TransferComplete` | ✅ |
| 字幕（srt/ass/ssa/sup） | `SubtitleTransferComplete` | ❌ **未监听** |
| 音频（mp3/flac…） | `AudioTransferComplete` | ❌ **未监听** |

判定依据是 `_is_primary_media_file` / `_is_subtitle_file` / `_is_audio_file`
（`app/chain/transfer/filter.py`），字幕扩展名取自 `RMT_SUBEXT`
（默认 `.srt .ass .ssa .sup`）。

因此**所有外挂字幕与音频文件静默不入队**。剧集场景下每集常带 1~3 条字幕，
漏掉的就是它们 —— 这也解释了为什么「漏得多」而不是「偶尔漏」：
媒体文件与字幕文件的数量差就是漏听量。

**修复**：同时监听三种事件（`_TRANSFER_SUCCESS_EVENTS`），并按宿主是否提供
后两者动态收集，兼容旧宿主。

**后续发现（同一版本的补丁）**：

1. **必须幂等** —— 宿主的整理事件走 durable outbox，语义是 **at-least-once**，
   同一事件可能重复投递。原实现无条件覆盖时间戳，每次重投都把冷却重新计时，
   表现为「明明是 1 小时前入库的文件，冷却永远走不完」。现已在队列中的条目不刷新时间。

#### 3.8.1 一次错误归因的纠正（务必读完再改这里）

本节的早期版本曾写下两条**未经代码验证**的结论，后经完整核对已判定为**错误**，
现予撤回。保留记录是为了避免后来者重蹈覆辙。

| 曾经的错误结论 | 实际情况 | 依据 |
|---|---|---|
| 「宿主**只在整理批次收尾时**才广播事件」 | 事件**按文件即时发布**；批次收尾汇总只影响**用户通知**，不影响事件 | 见下方 ① |
| 「宿主对**字幕/音频不填 `file_list_new`**，所以字幕不入队」 | **不存在这种按类型判断的逻辑**；每次整理都带当前文件的路径 | 见下方 ② |

**① 事件与通知是两条独立路径**

`settlement.py` 的 `__default_callback` 中顺序是：

```python
event_payload = self._transfer_result_payload(task, transferinfo)  # 构造 payload
durable_writer.transfer_result(..., event_payload=event_payload,
                               settlement=settlement)              # 快照进 outbox
...
if self.jobview.is_finished(task):          # 批次收尾才汇总
    transferinfo.file_list_new = list(...)  # 只喂给用户通知
    __notify()
```

而 `db/adapters/chain.py` 取快照的时机在**批次汇总之前**：

```python
intent=OutboxIntent(payload=snapshot_transfer_result(event_payload)),
deliver=((lambda: publish(event_payload)) if settlement is None and publish is not None else None),
```

正常整理路径 `settlement` 必非 `None`（`__default_callback` 里为 `None` 会直接
`raise`），因此 **`deliver` 恒为 `None`，事件只走快照**，而快照早于批次汇总。
结论：**每个事件的 `file_list_new` 恒为「当前这 1 个文件」，批次汇总永不进入事件。**

**② `file_list_new` 不按文件类型判断**

`app/modules/filemanager/transhandler.py` 全部 4 处赋值（1155/1251/1396/1751 行）
都是单文件整理时填当前文件路径，**没有一处**按 `_is_subtitle_file` 之类做区分。

**结论：真正成立的只有「三类事件」那一条**（`_durable_transfer_event` 按
`_is_primary_media_file` / `_is_subtitle_file` / `_is_audio_file` 分派，证据明确）。
只注册 `TransferComplete` 确实会漏掉全部字幕与音频 —— 这条修复有效且必要。

**关于 `fileitem` 回退：保留代码，但不再宣称一个验证不了的机制。**
该回退是防御性兜底。它曾被解释为「字幕事件路径为空」，但该解释缺乏依据已撤回；
真实触发条件未知（可能是目标文件已不存在等）。它无害且能兜住未知情况，故保留。

#### 3.8.2 二次纠正：撤回撤过头了（`file_list_new` 到底会不会为空）

3.8.1 撤回「宿主按文件类型不给字幕填 `file_list_new`」之后，本插件一度把结论
**过度纠正**为「该字段不会为空」。经全量审计，正确表述介于两者之间：

**`file_list_new` 确实可能为空，但不存在按文件类型判断的规则。**

依据：`app.schemas.TransferInfo` 中该字段默认值为空 list，而全仓
**28 个 `TransferInfo(...)` 构造点里有 25 个不显式赋值** ——
覆盖失败分支、中间态，以及 `plan.py` / `module.py` 中的多个路径。
只有 4 处（`transhandler.py` 的 1155/1251/1396/1751）在 transfer 成功后
写入 `new_item.path`。

因此：

- 「字幕一定为空」（旧结论）—— **错**，查无按类型判断的规则。
- 「不会为空、回退多余」（过度纠正）—— **也错**，25 个构造点会走默认空值。
- 正确做法：**保留并加强回退**，按可靠性降级
  `file_list_new` → `file_list` → `fileitem.path`。

**教训（比 3.8.1 更值得记住）**：发现一个解释站不住时，正确的动作是**降级为
「待验证」**，而不是反向断言一个同样没有证据的新结论。两次都是在同一个字段上
「读了一半就下因果判断」。

#### 3.8.3 为什么本插件**不**订阅整理失败事件

官方事件说明建议连同 `TransferFailed` / `SubtitleTransferFailed` /
`AudioTransferFailed` 一起订阅。本插件**有意不订阅**，理由：

1. **整理失败 ⇒ 文件没有进媒体库**，本地库内根本没有该文件，入队也无从同步。
2. 失败事件里的 `fileitem.path` 是**下载器源路径**，不在媒体库映射内；
   若照常入队，会引入错误条目（或只产生噪声日志）。
3. 失败通知由 MoviePilot 自身承担（含失败阶段、原因、重试状态与 `/redo` 按钮），
   本插件重复播报没有增量价值。

若将来要做「失败也提醒」，应当**只记日志、不入队**，且需先确认
`fileitem.path` 的语义，避免污染冷却队列。

#### 3.8.7 幂等的边界：同步完成后重投拦不住（已评估，**有意不修**）

幂等判据是「该 key 是否在当前 `_pending_queue` 中」。而同步成功后会移出队列
（`_execute_sync` 中 `exit_code == 0 and mode == "ready"` 的分支）。因此：

| 场景 | 幂等是否生效 |
|---|---|
| 冷却期内重复投递 | ✅ 保留原时间戳，不重新计时 |
| **同步完成、条目已移出队列后重投** | ❌ **被当作新入库，冷却重新计时** |

**实际影响**：文件被重新排队 → 2h 后冷却到期 → 再传一次。但 rsync 的
`--size-only` 会发现目标端大小相同而**跳过实际传输**，只产生一次目标端 stat。
所以代价是「一次多余的 115 校验请求 + 看板数字虚高」，**不会重复上传、不会损坏数据**。

**为什么会有这种情况**：宿主 outbox 是 at-least-once，投递时插件若不可用会重试；
插件恢复后重投，而此时文件可能早已同步完成。

**为什么有意不修**：彻底幂等需要持久化「已同步 key」集合（带清理策略），
或让队列条目保留「已同步」状态。两者都要引入需要长期维护的状态，
而收益仅仅是省掉一次 stat —— **代价大于收益**。

> ⚠️ **维护提醒**：若将来发现同一文件被反复重新排队（而非偶发），
> 应先确认宿主是否在反复重投，而不是直接给队列加持久化集合。
> 另：重复入队目前会记成「监听到 1 个新入库文件」，日志上看不出是重投 ——
> 这是排查时的已知盲点，可考虑在入队时按 mtime 早于冷却时长给出提示。

#### 3.8.6 改用平台推荐的事件读取方式（event.snapshot()）

官方事件说明指出，插件应使用 `event.snapshot()` 读取**类型化 payload 快照**，
而本插件此前直接读原始 dict（`event.event_data`）。

**差别**：宿主对 `TransferComplete` 登记了契约（`contracts.py` 的 `_PAYLOAD_MODELS`
→ `TransferResultContractData`，且该事件在 `_SNAPSHOT_EVENTS` 内），
`snapshot()` 会按契约把 payload 解析成 Pydantic 模型，**字段名与类型由宿主保证**；
而原始 `event_data` 的定位是「保持插件旧对象字段不变」的兼容形状
（详见 `validate_event_payload` 的注释），字段一旦调整，插件只会**静默读到空值**。

这正是本项目前几轮反复踩的坑 —— `file_list_new` 为空的种种猜测，本质都在
用「防御式 getattr」去猜一个本该由契约保证的字段。

**实现**：优先 `snapshot()`，失败逐级回退，并**在日志中标注实际读取方式**：

| 情况 | 读取方式 | 行为 |
|---|---|---|
| 契约已登记、解析成功 | `snapshot` | 用类型化模型 |
| `payload` 为 None（未登记契约/旧宿主） | `raw` | 回退原始 dict |
| 事件无 `snapshot` 方法 | `raw` | 回退原始 dict |
| `snapshot()` 抛异常 | `raw` | 记 debug，继续处理 |

> ⚠️ **为什么必须保留回退**：若只走快照，遇到未登记契约的宿主或事件时
> `payload` 为 None，会让**原本能正常工作的事件全部读不到数据**。
> 回退保证最坏情况也不比改动前差，而日志能立刻显示走了哪条路。

**维护提醒**：日志里 `读取方式=snapshot` 说明契约路径生效；若长期是 `raw`，
说明该宿主未登记契约或快照解析失败，此时应保留回退而不要删除。
`snapshot.errors` 非空表示契约存在但校验有告警（字段变更的信号），
按 debug 记录、不阻断处理。

#### 3.8.5 诊断缺陷：分类顺序掩盖了真实病因

**问题**：事件处理器原先按「先判文件是否存在、不存在就跳过，再判映射归属」的顺序
处理。结果是 `不在任何映射内` 这个计数**永远为 0** —— 不是真的匹配上了，
而是根本走不到映射判断那一步。

**后果**：日志无法区分两种病因完全不同的情况，导致排查多次跑偏：

| 情况 | 真实含义 | 应对 |
|---|---|---|
| 路径**不在任何映射内** | 宿主的媒体库路径 ≠ 配置的源目录 | 改插件配置 |
| 路径**在映射内但读不到** | 前缀一致却 `os.path.exists` 失败 | 宿主机/容器挂载不一致 |

用户实际反馈的现象是「文件确实入库、服务器上能看到、也收到通知，但插件没记到入库时间」，
正是被这个缺陷掩盖的典型场景。

**修复**：改为**先判映射归属、再判存在性**，并分成三类分别记录：

- 已入队（info，含相对路径）
- 归属映射但容器内不可见（info，明确提示检查宿主机目录是否映射进容器）
- 不属于任何映射（info，同时打印当前配置的源目录便于对照）

**教训延伸**：这与 3.8.1/3.8.2 同源 —— **分类逻辑的判定顺序本身就是一种结论**。
先判 A 再判 B，等于断言「B 只在 A 成立时才需要考虑」，这个隐含断言若不成立，
统计数字就会骗人。写分支时要问：这个顺序会掩盖什么？

#### 3.8.4 事件处理必须自行兜底异常

官方事件说明明确：**事件处理器被丢到线程池执行，未捕获的异常会被宿主记为「插件错误」**。

原实现把入库排队逻辑直接写在注册方法里，没有任何 `try/except`。入库排队会做
文件系统探测与状态落盘，一旦意外（权限、路径异常、磁盘满）就会污染宿主的插件
错误统计，且单条事件失败可能影响整批处理。

现拆为两层：

- `on_transfer_complete` —— 注册入口，**只做异常兜底**，记 error + debug 堆栈，
  **不 re-raise**；
- `_handle_transfer_event` —— 真正的业务逻辑。

**维护提醒**：新增入库相关逻辑请写进 `_handle_transfer_event`，不要绕过兜底层。
若确实需要在入口做前置判断，也务必让它保持「不会抛异常」。

**给后来者的教训**：本插件多轮排查中的错误结论，全部源于「读了一半就下因果判断」。
凡是写进文档的机制性结论，**必须附上文件与行为依据**；拿不出证据的，就写成
「现象 + 待验证」，不要写成因果。

**同类隐患**：事件走 durable outbox（at-least-once），若投递时插件不可用，
事件会进入有限重试；超过重试上限即永久丢失。事件机制本身无法兜住这一点，
故提供了源端扫描作为可选兜底（默认关闭，原因见 4.4）。

### 3.9 P2 — 文件列表分页（v0.1.1）

**背景**：冷却队列可能积累上百条，一次全渲染既卡顿又难浏览。

**做法**：每页 15 条，三个标签（冷却队列 / 对账异常 / 已忽略）各自独立页码。
页码状态用 `pageQueue` / `pageFailed` / `pageIgnored` 分别保存，切换标签不丢失位置。

**三个关键设计点**：

1. **对账异常标签必须先合并两个清单再分页**。该标签原本渲染 `missing_files` 与
   `corrupt_files` 两个独立列表；若各自分页，「每页 15 条」就变成每页最多 30 条，
   与用户预期不符。现合并为 `failedEntries`（带 `kind` 字段区分），
   渲染时按 `kind` 决定配色与按钮提示文案。
2. **`selectableItems` 改为「本页」而非「全量」**。批量选择以页为单位才符合直觉；
   若仍按全量，点「全选本页」会选中用户看不见的条目，误同步风险很高。
3. **页码越界就地纠偏**。同步成功条目被移除后，原页码可能超出实际页数，
   用户会卡在空白页且无法自行返回（页码条因 `pages > 1` 不成立而隐藏）。
   现于 `paginate()` 内 `Math.min(max(1, page), pages)` 并写回页码 ref。

**实现位置**：`Page.vue` 的 `paginate()` 为三标签共用的切片助手，
返回 `{ total, pages, page, pageRef, slice }`，其中 `pageRef` 供模板翻页按钮绑定。

> ✅ v0.1.1 正式发布时已执行 `vite build` 并提交重建后的 `dist/`。
> 注意：alpha 期间 `dist/` 与源码会短暂不一致，属预期（alpha 不构建）。

### 3.10 P1 — 临时文件残留与 `..*` 排除规则的实际效果（实测）

**缘起**：用户报告 115 上出现 `黄泉的使者 S01E03.…mkv..xrp4gj` 这类文件。

**实测确认的事实**（本地 rsync 3.4.1 复现，非推测）：

1. **临时文件由 rsync 生成在目标端**，命名规则是 `<正式文件名>.<6位随机后缀>`。
   源端不产生残留（实测源端仅保留原文件，目标端出现 `.f.mkv.RPJczE`）。
2. **传完才改名为正式文件名**，因此中断必然留下半成品。
3. **`SIGKILL` 与 `SIGTERM` 都留残留**（实测两种信号后目标端均存在临时文件）。
   注意本插件用 `Popen.kill()`（即 SIGKILL），rsync 无法捕获、必然无机会自清理；
   但改用 SIGTERM 同样不会清理，故**没有改动的必要**。
4. **排除规则 `..*` 挡不住这种形态**：

   | 排除写法 | 匹配对象 | 能否挡住 `影片.mkv..xrp4gj` |
   |---|---|---|
   | `..*`（当时默认） | 以 `..` **开头** | ❌ 挡不住（`..` 在中间） |
   | `*..*` | 任何位置含 `..` | ✅ 能挡住 |

   即默认规则有效范围比预期窄 —— README 曾称「已加入 `..*` 以减少新增污染」，
   该表述**对主流形态不成立**，已订正。

**生产环境成因修正（用户实测反馈）**：用户遇到的实际场景是「文件**已传完**，
CD2 执行改名时因**网络波动**失败」—— 即 rsync 数据传输 100% 完成，
最后一步 rename（真实调用 115 接口）没有成功。两个关键推论：

1. **残留文件大小与正式文件完全一致**（与「传到一半被杀」的形态不同），
   不能用大小判断是否传完 —— 应以 115 云端是否存在正式文件为准。
2. **插件结构上看不到它**：插件的所有判断都基于 CD2 挂载视图，而该残留只出现在
   115 云端（挂载视图与 115 服务端不一致，CD2 的属性/列表缓存可能向插件报告
   过期的「成功」状态）。这同时意味着：**对账与自动重试都可能不知道失败发生了**
   —— 看板一切正常、异常清单为空。用户的兜底手段是 `/rsync_search` +
   `/rsync_confirm` 定向重传（不依赖对账结果）。

> ⚠️ 这一条与 3.8.1/3.8.2 的教训同源但更隐蔽：本次 rsync 侧的机制（临时文件命名、
> 目标端产生、信号残留）是实测的，但**「生产环境里哪一步失败」只有用户现场才能确认**。
> 文档初稿只写了 rsync 中断一种成因，实际主要成因是 CD2 改名失败 ——
> **机制排查要区分「插件可观测的失败」与「插件视野外的失败」两类**。

**结论与处置**：**结论与处置**：

- **不建议插件自动清理**：清理需遍历 115 目录并执行删除，是「遍历 + 破坏性操作」，
  与全局「尽量不扫 115 挂载点」的约束直接冲突，风控风险远大于收益
  （与 TODO 中否决 `/rsync_clean` 的理由一致）。
- **改代码无必要**：用户手动删除即可，插件不引用这些文件，删除不影响队列与记录。
- **可选缓解**：把默认排除规则从 `..*` 改为 `*..*`（需评估对用户自定义配置的影响，
  以及是否会误伤合法的含 `..` 文件名 —— 正规影片名不会在扩展名后再出现 `..`，
  但仍应走配置迁移机制而非直接覆盖）。

**处置**：仅更新文档（USAGE 常见问题给出完整处理步骤），**代码与默认值暂不改动**。

### 3.11 P1 — 目标端"假成功"导致重传永不生效（v0.1.4）

**现象**：CD2 改名失败后，CD2 挂载视图显示目标文件「存在且大小正常」，
但 115 服务端实际只有改名失败的半成品（形如 `影片.mkv..xrp4gj`）。
插件任何形式的重传（retry / confirm）都**不会真正上传** ——
`rsync --size-only` 比较源/目标大小一致而跳过。

**根因**：插件的一切判断都经过 CD2 挂载这层视图，而这层视图是脏的。
视图与云端不一致时，插件没有手段发现「该文件实际没传成功」。

**修复**（同 sync_115 仓库 retry_file.sh 的既有做法，插件化并加护栏）：
`/rsync_retry <文件名>` 升级为「搜 → 删 → 传」闭环：

1. `_search_target_files` —— 按关键字扫**源端**（与同步/补传同口径：
   扩展名过滤 + 排除目录裁剪，零 115 API）；
2. `_delete_dest_files_for_retry` —— 经 CD2 挂载删除目标端对应文件
   （`rm` 会真实调用 115 删除接口，视图与云端一起被纠正）；
3. 定向 rsync 重传（`custom_files` 既有通道，retry 模式原生支持）。

**破坏性操作的三道护栏**：

- 关键字单次最多匹配 15 个（`_RETRY_KEYWORD_LIMIT`），超限**直接拒绝**
  而非截断执行 —— 删了重传与只读搜索不同，宁可不执行也不大范围误伤；
- 只按「源端相对路径 → 目标端同路径」精确删除；删除前校验**源端文件必须存在**，
  无前缀 / 无法归属映射的 key 一律拒绝；
- 删除后**复查**：rm 抛错或文件仍存在（CD2 假删）都归入「删除失败」，
  调用方必须跳过这些文件 —— 带脏视图重传会被 `--size-only` 跳过，
  白白消耗限流配额；目标端本就不存在时无需删除、直接可传。

**边界说明**：关键字只搜源端，云端 `..` 中缀的残留不在源端清单里，
天然不会被该指令碰到 —— 残留清理仍在 115 云端手动完成（见 3.10）。

**已知限制**：rm 与重传不是原子操作 —— 删除成功后、重传完成前，媒体库
短暂缺该文件（下次正常同步会补上）；若重传中途失败，该文件进入异常清单，
与既有 retry 行为一致。

### 3.7 P1 — 移动端布局溢出（v0.0.12）

**现象**：手机端样式支持差 —— 按钮超出卡片范围、文字被挤压换行错乱。

**根因（按钮溢出）**：Vuetify 的 `.v-card-item` 是 grid 布局，列宽定义为

```css
grid-template-columns: max-content auto max-content;
```

`append` 列按 **`max-content`** 计算宽度 —— 那是**固有宽度下界，不会收缩**。
窄屏下右侧按钮组因此被顶出卡片，再由外层 `.page-main-card` / `.config-main-card`
的 `overflow-hidden` 裁掉，视觉上就是「按钮超出范围」。
同因，`auto` 列（标题）也会被 `max-content` 列挤压。

**根因（间距被吞）**：外层容器把 `padding: 18px 22px !important` 写成**内联样式**，
媒体查询无法覆盖，窄屏下白白吃掉大量横向空间。

**修复**：

1. `grid-template-columns` 改为 `max-content minmax(0, auto) minmax(0, max-content)`
   —— 有空间时仍按内容宽度，空间不足时允许收缩，收缩后按钮组依 `flex-wrap` 换行。
   因 `.v-card-item` 由 Vuetify 组件渲染，scoped 选择器匹配不到底层的
   `.v-card-item__append`，**必须用 `:deep()`**。
2. 外层 `padding` 从内联样式**收敛进类规则**，作为唯一来源，移动端再行收窄
   （外层 18/22 → 10/12，内容区左右 16 → 10，合计省下约 36px）。
3. 列表行（冷却队列 / 异常清单 / 已忽略）由固定横排改为
   `flex-column flex-sm-row`：窄屏纵向堆叠、宽屏恢复原样。
4. 操作工具条同理堆叠，按钮在窄屏下占满整行，便于点按。
5. 选项卡加 `show-arrows`：三个中文长标签（如「入库延迟冷却队列 (12)」）
   在窄屏必然溢出，开启后在溢出时出现滚动箭头。
6. 设置页开关行（左说明 + 右开关）改纵向排列，避免开关被挤出右边界；
   底部「查看看板 / 保存配置」在窄屏各占一行。

**断点**：统一用 `max-width: 599.98px`，与 Vuetify 的 `sm`（`min-width: 600px`）
严格互补，避免 600px 这一像素上出现两套规则同时生效或同时失效。

> ⚠️ **维护提醒**：移动端规则依赖模板里的 `flex-sm-row` / `align-sm-center` 等
> **响应式工具类**（均在 Vuetify 的 `min-width: 600px` 媒体查询内，源码顺序在基础类之后）。
> 若把这些工具类改回非响应式版本，窄屏堆叠会失效。改动前请一并检查。

### 3.12 P1 — 疑似清单的两种成因不可区分：先补生成 strm，再决定是否重传

**背景**：「缺 strm」有两种成因，表现**完全一致**，处置成本差好几个数量级：

| 成因 | 云端实际状态 | 正确处置 |
|---|---|---|
| ① 助手漏生成 | 文件完好 | 重新生成指针即可 |
| ② CD2 改名失败假成功 | 只有 `..xxx` 半成品 | 必须删旧重传 |

插件本地视角无法区分，因此 v0.1.9 之前只能把两者都当成「疑似」让用户**删旧重传** ——
对情况 ① 而言，那是白删一次云端文件再完整重传一遍。

**做法**：借助手插件走一次云端目录遍历，用它当判别器：

- 生成**成功** ⇒ 情况 ①，**无需重传**（省下整轮删除 + 上传）
- 生成后**仍无** ⇒ 情况 ②，此时删旧重传的正当性反而更充分

被请求的条目从疑似清单**移回「待观察」并以请求时刻重新计时**，复用既有三态状态机
（strm 出现 ⇒ 自动解除；窗口到仍无 ⇒ 回到疑似，此时带「补生成后仍无」标记，
判定比首次更硬）——这样不需要为异步的助手另加一条轮询路径，而且用户能在观察期
直接点「检查 strm」看结果，不必盯着疑似清单手动刷新。

**移动的时机是承重的：命令确实发出之后，不是收到请求时。**
第一版在发命令**之前**就移动，用户实测表现是「点了一下，条目不见了」——
助手拒收（路径不在它的全量列表里）时命令根本没执行，条目却已经离场，
窗口到又带着一个错误结论回来。**把「命令已发出」当成「生成已执行」**，
顺着这个结论去删旧重传，删掉的是一个完好的云端文件。
现在两道闸门：发送前预检拦掉必然被拒的路径；发送后按**实际发出命令的目录**
反查命中哪些 key，只有它们才移回观察期（逐目录发送时部分失败也适用）。

**重新计时的窗口是固定 1 小时（`strm.REGRACE_HOURS`），不跟随宽限期配置。**
两者度量的是不同的延迟：宽限期量「rsync 报成功 → strm 出现」的刮削/入库传播，
这里等的是助手的一次**云端目录遍历**。用户把宽限期调到 24h（理由是刮削慢）
不该连带让补生成的结果在半天内无法判定 —— 那才会真的把功能调坏。
窗口以此为**下界**：已生成的情形会在下一轮巡检立刻解除，不必等窗口结束。

**两个连带改动**（不改就是「点了没反应」或「两边各说各话」）：

1. **主动扫描不再把观察期条目降级为疑似**。补生成条目此刻的 .strm 按定义还不存在，
   扫描一跑就会把它打回疑似 —— 用户点完按钮看到的仍是同一批条目，功能表现为完全没作用。
   观察期自带到期机制，让扫过的条目自己走完窗口即可（扫描结果里单独列出跳过的数量）。
2. **计时基准统一由 `strm.watch_state_of` 解析**，看板显示与巡检判定**共用同一个函数**。
   否则补生成条目会显示成「看板说还剩 5 小时、下一轮巡检已判到期转疑似」——
   两个数字各自自洽，用户完全无从判断该信谁，这是最难排查的一类分歧
   （同一类教训见 `/status` 的 `strm_watch_clocks` 外发字段）。

**窗口到了仍无 strm 时，本地视角分不出四种成因** —— 用户实测反馈的困惑正是
「我已经知道网盘上没有这个文件，点了补生成，然后呢？」。四种成因里三种该删旧重传、
一种删了纯属白删，而它们在**只有 strm 缺失**这一个观测点下完全同形：

| 成因 | 云端情况 | 删旧重传 |
|---|---|---|
| 从未传成功 | 没有 | ✅ 对症（删除是空操作） |
| CD2 改名失败 | 只有 `..xxx` 残留 | ✅ 对症 |
| 传到一半 | 有，大小不符 | ✅ 对症 |
| 助手没识别 / 没执行 | **文件完好** | ⛔ 白删（rsync 还会 `--size-only` 跳过） |

**把观测点前移一步**：`pair.dest` 是 CD2 挂载点，读它的大小是**纯本地调用、
零 115 API**，足以分开上面四行。于是给每个新入清单的条目附一条
`dest` 结论（`_annotate_dest`），看板直接显示，用户不必自己去 115 里翻。

三条**必须**约束（都不是注释，是行为）：

1. **只能用它的假阴性方向**：3.11 的「CD2 假成功」正会让坏文件显示成
   大小一致（残留大小与正式文件相同，见 3.10），所以这份结论的假阳性方向是
   「把坏文件看成好的」。据此跳过上传 = 真的漏掉坏文件；据此**拦下删除** =
   最坏只是「让用户去查一下助手」。因此它唯一能影响行为的地方是
   `_api_strm_retry` 的**事前拦截**，方向恒为「少做一次破坏性操作」。
2. **不得参与清单清理**：据此把条目从清单摘掉，等于静默忽略一个真坏文件，
   后果与用户主动「忽略」一样重，而用户并不知道自己忽略了它 ——
   `_annotate_dest` 只写不删（有结构性测试锁住）。
3. **挂载未就绪必须整体退化成 unknown**：`dest` 根目录读不到时
   `os.path.exists` 对每个文件都返回 False，照此判定会给整批扣上
   「云端没有文件」的帽子 —— 而那只是 CD2 没挂上。同理，`getsize` 抛错
   与「确实不存在」必须分开（用 `None` 而非布尔值表达「读不到」）。

**探测无效时 fail-open**：unknown 一律放行删旧重传。若把 unknown 也拦下，
CD2 一抖动用户就完全无法处理疑似清单 —— 而那批条目很可能真的该删。

**重传前重新探测**，不复用清单里那份：清单里的结论来自入清单那一刻（可能一小时前），
用户是看到建议之后才点的按钮，中间完全可能又跑过一次同步 ——
用过期事实做破坏性判断是不能接受的。

**一处修注**：`dest_probe_outcome` 的三个分支**顺序不影响结果**（枚举 8 种输入
组合比对过，属等价变异，改掉也不会让测试失败）。初稿在注释里把它写成了
「承重逻辑」，那是错的 —— 已订正为「仅为可读性保留」。同类问题见 3.8.1。

**为什么这次允许在观察期放按钮**（与「观察期不放操作按钮」并不矛盾）：
当初拒绝的是**破坏性**操作 —— 删旧重传会诱导用户删掉刚传好的文件、白耗一次
删除与重传配额。而「检查 strm」是纯本地只读：零 115 API、不占限流配额、
不加执行锁，同步任务跑着的时候照样能查。

**两次被实测打脸的设计决策**（记下来，都是「凭推测写机制」的实例）：

1. **参数必须是目录，不能是文件**。
   最初按助手的函数签名以为「传文件也行」，用户实测日志推翻了它：
   - 2026-08-17 传文件（`.../杀手妈咪 S01E05.mkv`）→ 助手打印「网盘媒体目录 ID
     获取成功」后生成 **0 个** STRM 文件。它拿到的 ID 指向文件本身，其下无可遍历内容。
   - 2026-08-13 传目录（`.../Season 01`）→ 正常生成 6 个。
   - **传文件不报错，只是静默什么都不做** —— 最难排查的一类失败。
2. **不能从助手配置反查网盘路径**。
   最初写了三级回退（`full_sync_strm_paths` → `monitor_life_paths` →
   `increment_sync_strm_paths`），方向恰好写反了：
   - 助手只把 `full_sync_strm_paths` 交给 `PathUtils.get_p115_strm_path` 做匹配；
     另外两个字段里的目录传过去**必然**匹配失败。
   - 用户实机 9KG 映射就只在 `monitor_life_paths` 里 —— 反查得出路径，发过去必被拒。
   - 该拒绝提示只发给助手侧用户，**本插件收不到**，表现为「点了按钮什么也没发生」。

   改为**用户在本插件显式配置「网盘目录」**（映射的 `pan_dir` 字段）。理由不止覆盖 9KG：
   反查依赖对方配置的**字段名与格式**（属实现细节，对方改名即静默失效），
   且本地 strm 目录与 115 网盘目录是**两棵独立的树**，「本地路径减前缀」在原理上不成立。

**命令通道的一个失真**（同类静默失败，已加守卫）：宿主把命令串按空白切分后再用
**单个空格**拼回（`command.py`：`cmd.split()[0]` / `" ".join(cmd.split()[1:])`），
因此目录名里的**连续空格**会被折叠，`/TV/剧  名` 到助手那边变成 `/TV/剧 名`，
路径匹配失败且本插件看不到。这类路径现在直接列为「未处理」，不发注定失败的假命令。
单个空格、括号、中日文、`{}` 都无损（用户实机的目录名全属这一类，已验证）。

**成本控制**：助手对**每个参数**都会遍历该目录的整个云端子树，所以真实成本由
**目录数**决定而非文件数。实现上逐目录去重（20 个文件散在 3 个季节目录 ⇒ 3 次小遍历），
单次目录数上限 `STRM_GEN_DIR_LIMIT`（默认 20），且**超限整批拒绝**而不是截断执行 ——
静默截断会让用户以为整批都处理过了，比明确拒绝更糟。

**为什么是手动触发**：这一步会让助手**访问 115 网盘**。清单几十条时自动触发
等于自动打出几十次遍历，与插件整体的风控保守取向相悖。

**越权护栏**：`/strm_generate` 只接受已在疑似清单中的 key（与 `/strm_retry` 同口径），
防止调用方构造任意路径让助手去遍历云端目录。

## 4. 新增能力

### 4.0 非视频文件不进入 strm 交叉验证（v0.2.2 修复，用户实测反馈）

**现象**：用户在看板「strm 疑似上传异常」标签页里看到**非视频文件**
（字幕、图片、元数据）也被纳入监控。

**为什么会发生**：`_strm_arm_watch` 的登记闸门只判断了两件事 ——
「该映射是否配了 strm_dir」与「是否命中忽略规则」，**没有判断文件类型**。
而 strm 助手只为**视频容器**生成指针文件，字幕/图片/元数据永远不会有 .strm。
于是每个 `.srt` 入库并同步成功后都会被登记观察，宽限期一到就转成
「疑似上传异常」，而且**永远无法解除** —— 它本来就不该有 strm。

**为什么必须在登记处拦，而不是展示层过滤**：疑似清单是**可执行操作**的数据源 ——
「删旧重传」会去删 115 端的对应文件，「忽略」需要用户为一条本就正常的记录做手工豁免。
只在展示层过滤，这些操作仍会落在字幕上。这与 3.12「先补生成再决定是否重传」
是同一类考虑：清单里的每一条都意味着一次真实的云端操作。

**实现**（判据**只此一份**）：

- 新增 `_strm_watchable(key) -> (可否参与, 原因码, 原因说明)`，四处共用：
  1. `_strm_arm_watch` 登记闸门（入口拦截，并统计跳过的非视频数量）；
  2. `_strm_check` 巡检（清理旧版本落盘的非视频**观察**条目，而非转疑似）；
  3. `_check_watch_now` 手动检查（同一出口，清理并说明原因）；
  4. `_prune_invalid_strm_suspects` 疑似清单载入清洗（原判据改调它，去掉重复实现）。
- 新增 `_prune_invalid_strm_watch()`：载入时清洗观察清单里不可能有 strm 的条目，
  并连带失效其补生成标记。放在 `_strm_gen_requested` 恢复**之后**调用 ——
  早于它调用只能清到一个空的标记字典，旧标记会留下来把新条目误标成
  「补生成后仍无」。
- 原因**分「码」与「文案」两段**（`constants.SKIP_NON_VIDEO` / `SKIP_NO_STRM_DIR`）：
  码用于分支判定（例如统计跳过了多少非视频），文案只进日志。若让调用方去匹配
  中文文案来判断分支，改一次措辞就会让分支静默失效 —— 这是「跳过计数突然全为零」
  这类难查回归的来源。

**⚠️ 常量放 `constants.py` 而不是 `strm_ops.py`**：`test_split_contract.test_mixins_are_stateless`
禁止 Mixin 模块出现**任何**模块级赋值（宿主按实例重建命名空间时模块级可变状态会被
分身共用）。第一版把原因码定义在 `strm_ops.py` 顶部，这条契约测试当场失败 ——
按拆分约定，常量一律归 `constants.py`，协作方显式导入。

**顺带修复（同一批 review 发现）**：`test_batch_settlement.py` 有两条用例用
`post_m=` / `post_c=` 关键字调用 `paths.merge_force_anomalies`，而形参名实为
`post_missing` / `post_corrupt` —— 它们**一直抛 TypeError** 却没人发现。
已改为位置传参（与生产调用一致），形参改名不会再让用例静默失效。

### 4.0b 观察窗口可被「确认失败」越过，且确认后放行删旧重传（v0.2.3，用户实测反馈）

**现象**：用户在观察期条目上明确知道该文件**没真的传到 115**（云端只剩
`影片名.mkv..xrp4gj` 残留、正式文件压根不存在），却**无处可点** ——
观察期内看板只提供只读的「检查 strm」，而「检查」用的是
`strm.watch_state_of` 解析出的钟（补生成条目为请求时刻 + 1h），窗口没到就
**无论点多少次都不会提前判定**。用户只能干等到期，最长 6 小时。

**根因是两个把「保护」变成「锁死」的设计**：

1. **窗口没有出口**。宽限期衡量的是「还可能有救的时间」，却被当成了
   「你必须等多久」的上限。窗口内不提供删除按钮是对的（防误删刚落地的文件），
   但**不给确认通道**就把已经知道答案的当事人一起拦在了外面。
2. **删旧重传守卫在黑名单场景下必然误伤**。`_api_strm_retry` 在删除前会重新探一次
   云端可见性，探测为 `DEST_OK`（可见且大小一致）时拒绝执行。而 CD2 改名失败的
   典型形态恰恰是「残留大小与正式文件**完全一致**、挂载视图一切正常」
   （见 3.10 / 3.11）—— 也就是说，在最需要删旧重传的那个场景里，这道守卫
   **必然**拦下请求。旧文案给的出口是「先重启同步任务再重试」，但重启后 CD2
   视图重新拉取，很可能仍是「可见且大小一致」，形成死循环。

**实现**（判据同样只此一份）：

- 新增第三种 origin `strm.ORIGIN_CONFIRMED`（前两种是 `watch` / `scan`）。
  它是**唯一一条「结论来自人而不是探测器」的入口**，删除守卫正是凭它区分
  「机器觉得没问题」与「人已经确认有问题」—— 混用 origin 会让守卫只能二选一：
  要么永不放行（用户被锁死），要么一律放行（坏文件被静默放过）。
- 新增 `_promote_watch_to_suspects(keys, origin, reason)`：观察清单 → 疑似清单的
  越窗通道，同时失效补生成标记（留着它会让看板把**用户确认的事实**渲染成
  「补生成后仍无」这种生成侧推断）。已按同一结论入清单的条目只摘观察副本、
  **不刷新时间戳**（否则每点一次「首次疑似时间」就往后跳）。
- 新增看板端点 `POST /strm_confirm_failed` + 聊天指令 `/rsync_strm failed` +
  观察期条目按钮「确认失败」。纯本地操作，故**不加执行锁**（与「检查 strm」同口径）。
- `_api_strm_retry` 增加 `force` 二确认：已确认条目首次点击只返回 `needs_force`
  与那句提醒（"探测显示可见且大小一致"），用户再点一次才真删。

**⚠️ 两类护栏必须分开看，这里只推翻了一类**：

| 护栏 | 作用 | 本改动 |
|---|---|---|
| **数据护栏** | 能不能误删到别的东西 | **一条未动**：只接受观察/疑似清单里的 key，删除仍走相对路径精确对齐的三道闸 |
| **判定护栏** | 怕误判所以多等一会儿 / 先拦一手 | 用户显式推翻这一条 |

把两者混作一团，才会得出「窗口绝不可越过」「守卫绝不可放行」这种把用户锁死的
结论；而只动判定护栏并不降低任何安全性 —— 当事人已经亲自看过 115 了。

**整批 vs 逐条（踩过一次的坑）**：`force` 起初按「整批是否全为已确认条目」判断，
但勾选状态**跨标签页保留**，一批里混着两类很常见，结果是确认过的条目被没确认过的
拖累（怎么点都删不掉）。改为按条目分流后，**分支顺序变成承重的**：
必须先判「未确认的」并整批拒绝，再判「已确认的」返回 `needs_force`。
反过来的话，前端会把「整批拒绝」当成「确认不足」去弹二确认，用户点两次仍被拒
—— 而真正该告诉他的是「先取消勾选那几条」。这条有专门的用例锁住
（`test_unconfirmed_entries_are_not_affected_by_confirmed_ones`）。

**决策记录**：**不做**自动判定。窗口内大多数文件确实是好的，把「用户知道答案」
变成「插件替用户猜」会立刻破坏现有的误报率。

### 4.1 全局上传限流与风控退避（v0.0.7）

三层闸门，`ready`/`retry`/`backfill`/`force` **全局共用**（P0-2 起 force 真正接入）：

```
入口闸门  退避期未过 / 配额用尽 → 整轮直接 return，零 API 调用
批次上限  单次 rsync 处理量有界，超出部分留待下轮（force 截断项留在异常清单）
配额预扣  启动 rsync 前先扣减并落盘（force 同样在 rsync 前按本批问题数预扣）
```

**force 的执行形态（P0-2，v0.2.1）**：
1. 对每个映射先做**只读全量对账**（`rel_paths=None`）—— 这是 7 天冷却真正约束的「全树遍历」；
2. 把缺失 ∪ 残缺收成相对路径，经批次上限截断后走 `--files-from` 定向传输；
3. 传输后只复检本批，再与预对账未尝试部分 `merge_force_anomalies` 合并进最终异常清单；
4. 配额**中途**耗尽时 **force 不 break 后续映射**：关掉传输（`force_transfer_allowed=False`），
   继续只读对账 —— 否则剩余映射要再等一个 7 天冷却才能被核对。
   ⚠️ 与入口闸门区分：**进入时**已耗尽/处于退避期 → 整轮 `return`，连对账都不做
   （闸门在映射循环之前，对所有模式含 force 生效）。本条只描述「跑到一半才耗尽」。

旧实现对整棵源树做无 `--files-from` 的 rsync，`pair_files` 恒为空，预扣与批次上限全部旁路；已移除 include/exclude 整树传输分支。

两个**正交**维度，缺一不可：

| 机制 | 作用 | 防的是 |
|---|---|---|
| 单批上限 | 单次 rsync 规模 | 命令行过长、单次峰值 |
| 窗口配额 | 单位时间总量 | **115 风控（主要）** |

**关键设计决策**：

1. **配额预扣而非事后统计** —— 若在传输完成后才计数，进程被重载会导致计数丢失，
   下一批直接绕过限流。改为 rsync 启动**之前**扣减并落盘，关闭该竞态窗口。
2. **窗口计数与退避截止时间持久化** —— 跨重载、跨重启保留。
3. **stderr 风控特征检测** —— 命中 `429` / `too many requests` / `频繁` 等关键词
   立即进入退避并终止本轮，而不是继续冲击 115。

### 4.2 存量媒体补传（v0.0.8）

**解决的问题**：插件只能感知启用之后的入库事件，启用前已入库的媒体永远看不到。
而**媒体文件往往带外挂字幕**，若只同步媒体会漏掉字幕。

**设计要点**：

- **扫描零 API**：候选构建只 `os.walk` 源端，全程不碰 115 挂载点
- **成组补传**：以「媒体文件 + 同主名伴生字幕」为单位
- **独立队列**：补传队列与 `pending_queue` 分离，不参与入库冷却计时，
  避免污染「冷却中 / 已就绪」统计
- **自动续跑**：由定时巡检推进，队列与进度持久化
- **传输走 `--files-from`**：定向处理，绝不整目录遍历

**副作用（已在 UI 明示）**：无法在不访问 115 的前提下判断目标端是否已存在，
所以**候选数 ≈ 最少请求次数**。因此补传前先预览数量并让用户确认，
避免一次点击悄悄发出上万请求。

### 4.3 整理完成事件监听（v0.1.0）

同时监听 `TransferComplete` / `SubtitleTransferComplete` / `AudioTransferComplete`，
三者共用同一个处理器。事件常量在模块加载时构造（`_TRANSFER_SUCCESS_EVENTS`），
因为装饰器在类体执行阶段就要求值。

**为什么必须三个都监听**：宿主按文件类型分派事件，只监听第一个会静默丢掉
全部字幕与音频（详见 3.8）。

### 4.5 strm 交叉验证（v0.1.5）

**动机**：3.11 的根因（CD2 假成功）在插件现有视角内无解 —— 对账与 --size-only
都经过挂载视图。用户提出的方案：利用 strm 插件生成的本地 .strm 作为**独立见证**
（其判断依据与 CD2 视图无关，且检查是纯本地文件操作，零 115 API）。

**实现**（按用户确认的设计：不同根、用户配置路径；strm 与整理后文件同名）：

- 映射级 `strm_dir`（留空=该映射不启用）；
- 三态生命周期：同步成功 → `_strm_watch`（待观察，宽限期默认 6h）
  → 到期未生成 → `_strm_suspects`（疑似异常，看板+按钮）；strm 生成 → 解除；
- 巡检挂在定时同步入口前，内部 30 分钟节流（`_STRM_CHECK_INTERVAL`），
  源端消失的观察项直接清理；
- 处理走「确认后删旧重传」（`_api_strm_retry`，复用 v0.1.4 删旧通道），
  **不做无确认的自动重传** —— strm 插件自身漏生成与真异常不可区分，
  误报源无法排除；重传成功后 `_strm_arm_watch` 自动解除疑点。

**通知**（复用同步报告那套通道：`post_message` + `_plugin_mtype`，交由宿主
「通知场景开关」路由，默认仅管理员）：
- **只在「新发现」时提醒一次**（`_strm_notified` 闩锁），清单内旧条目不再重复推送，
  否则每轮巡检都重推同一批文件，用户很快会静音；
- **清单清空时补推「已全部解决」并重置闩锁** —— 既有收尾反馈，
  也保证下次新发现能重新提醒；
- 通知正文含文件清单、判定依据、处理入口与「误报也安全」说明。

**设计取舍记录**：
- 只允许对疑似清单内的 key 执行重传（越权 key 拒绝），防止构造任意路径；
- 宽限期下限 0.5h，防止 0 值把「上传中/刮削中」误判为异常；
- strm 重传后仍留在疑似清单直至复核，避免重传失败后疑点凭空消失。

**列表内批量处理**（alpha，`552b131`）：后端 `/strm_retry` 从 v0.1.5 起就接受
`keys` 数组并逐条删旧重传，**前端此前只传 `[key]` 单条**，批量通道一直是通的
却用不上。补齐时有两个必须记录的判断：

1. **分流的依据是「选中项成分」而非「当前标签页」**。勾选状态跨分组保留
   （`selectedKeys` 是全局单值，不按标签页隔离），用户可能在别的分组按下按钮。
   因此提交前按 key 是否在 `strm_suspects` 里拆分，分别投给 `/strm_retry`
   与 `/sync_item`，混合选择先弹确认框说明分流规则。

   ⚠️ **表述订正**：本节初稿写成「strm 项必须删旧、普通对账项删旧是多余且危险的
   写操作」，**这个说法不准确**，会误导后来者以为 `/sync_item` 通道完全不删文件。
   实际差异见下表 —— `corrupt` 项本来就会被删，且**应该**删：

   | 条目来源 | 目标端实际状态 | 走删旧函数会怎样 |
   |---|---|---|
   | `missing`（对账） | 文件不存在 | **空操作**（`dest_size is None` 直接跳过） |
   | `corrupt`（对账） | 文件在，大小不符 | **会被删**，且必要 —— 半成品会干扰 115 秒传 |
   | strm 疑似 | 文件在，大小一致 | **只有这条路能删掉它**，否则 `--size-only` 永远跳过 |
   | 冷却队列 `ready` | 文件在，大小一致且**正常** | ⚠️ **会被白白删掉** + 全量重传，纯浪费流量与窗口配额 |

   所以分流的实质是「**谁有权限删掉一个大小看起来完全正常的文件**」，
   而不是「一个删一个不删」。最后两行是关键：**两者在大小上无法区分** ——
   「坏得很彻底所以大小完全相同」与「好文件」在 `getsize()` 眼里一模一样。
   系统能确知「该删」的只有 strm 疑似清单，这也是 `_api_strm_retry`
   必须保留服务端守卫（`:2543` 只接受清单内 key）的原因，不能只靠前端分流。
2. **`selectableItems` 与「存活集合」必须同步扩口径**。两者此前都不含 strm 项，
   结果是：勾选 strm 条目后点「全选本页」会被静默清掉，或 30 秒轮询刷新时
   因不在存活集合里被清除。这类缺陷不报错、只表现为「勾了没反应」，是最难
   自查的一类，改动这类集合时务必三处一起看（渲染、`selectableItems`、存活过滤）。

**顺带删除 `GET /strm_suspects`**：它与 `/status` 返回的 `strm_suspects` 字段
是同一份数据，全仓库零调用者（看板只依赖 `/status` 取数）。保留会让同一条状态
出现两条取数路径，早晚产生分歧。注意这不影响任何功能 —— 它从未缺失前端 UI，
只是**数据走了 `/status` 那条路**。

**配置页补 `strm_grace_hours` 输入框**（alpha，`9effbf5`）：该字段自 v0.1.5 起
只有后端（`_api_get_config` 返回、`_api_save_config` 保存），配置页无控件，
而 USAGE.md 已写「可调」—— 属文档承诺与实现不符。补控件时一并给
Config.vue 的响应式默认值加上 `strm_grace_hours: 6.0`：`/config` 未返回该字段时
（宿主配置里从未存过），`v-model.number` 绑定 `undefined` 会让输入框空白并写回
`NaN`，后端 `float(config.get(...) or 6.0)` 会吞掉 NaN 但配置里已落盘脏值。

### 4.4 源端补齐扫描（v0.1.0，**默认关闭**）

> 📌 **前置说明**：本节早期版本称「宿主只在整理批次收尾时广播事件」，
> **该前提已撤回**（详见 3.8.1）—— 事件是按文件即时发布的。
> 因此本扫描的定位从「补批次收尾的错过」修正为「补 outbox 重试耗尽后的永久丢失」，
> 触发条件比原先设想的**更罕见**，这也是它默认关闭的另一个理由。

> ⚠️ **默认关闭的原因（实测反馈）**：该扫描的判据是「文件 mtime 比上次扫描新」，
> 这**无法区分「真的新入库」与「老文件被重新写入」**。刮削写 nfo、下载器续传、
> 套件定期刷新时间戳，都会让同一个老文件每轮被重复判为新文件。用户实测到的现象是
> 「每隔几分钟就出现一个其实 1 小时前就入库的文件」，且因为补齐项不参与冷却，
> 它会立刻被同步。因此默认关闭，并在配置页写明利弊，只有确实经常丢事件的用户才开启。

**解决的问题**：宿主只在整理批次收尾时广播一次事件；若那一刻插件正在重载
（同步任务本身会触发重载），该事件永久丢失且不会重放。事件机制无法自愈。

**做法**：每轮 `ready` 同步开头，对每个映射 `os.walk` 一次本地源端目录，
用文件 `mtime > 上次扫描时间` 找出新出现的文件补入待同步清单。

**成本**：纯本地目录遍历，**不触碰 115 挂载点**，零 API 请求、不触发风控 ——
与 `_api_backfill_scan` 的成本性质相同（见 5.3 关于 FUSE stat 的说明）。

**关键设计**：

1. **首轮只建立时间基准，不入队** —— 否则首次启用会把整个媒体库灌进队列。
2. **补齐项不参与冷却** —— 这些文件比原计划已经多等了很久，再等一轮无意义。
3. **幂等** —— 同时检查 `_pending_queue` 与 `_missed_queue`，重复扫描不会重复告警
   （此点曾在实现中遗漏：只检查了前者，导致每轮都重复报告同一批文件）。
4. 文件已不在源端时直接清出清单，避免长期堆积。
5. **判据的固有局限**：mtime 变新只说明「文件被写过」，不等于「新入库」。
   若将来要重新默认启用，必须先解决这个歧义（例如改为比对宿主整理历史，
   或要求 mtime 距今不超过一个窗口，以排除「很久没动突然被 touch」的老文件）。
5. **节流**：扫描间隔下限 1800 秒（`_MISSED_SCAN_INTERVAL`）。大媒体库下每轮同步
   都整树遍历代价过高（冷启动、频繁手动同步、补传连跑时尤其明显）。
   被跳过的轮次**不会丢事件** —— `last_scan` 基准不推进，下次真正扫描时
   文件 `mtime` 仍大于该基准，照样会被捞出来。
6. **仅在真正纳入本轮时才移出清单**：若该文件因批次上限/配额未实际处理，
   提前移除会让它既不在冷却队列、也不在补齐清单，等于彻底丢失。
7. 移出后**立即落盘**，避免记录只存在于内存、重载即丢。

### 5.3 配额预扣在失败时也扣减

rsync 失败时配额已经扣除，不会退还。这是**有意的保守设计**（宁可少传不可多传），
但连续失败会白白消耗窗口额度。影响有限，暂不修改。

### 5.4 补传候选的口径是估算

候选基于「源端存在 + 不在队列/异常/忽略清单」推断，无法确知目标端状态。
因此候选里**必然包含已同步过但从未入过队的文件**。这些靠 rsync `--size-only`
在传输阶段跳过（不重传），但每次仍要一次 stat。

若将来 CD2 提供可靠的目标端清单接口，可显著降低这一开销。

### 5.5 并发与调度

`_scheduled_sync` 里补传优先于常规巡检，**同一轮只启动一种模式**（两者共用同一把
执行锁与同一份窗口配额，同时启动会导致后者抢不到锁而静默无效）。
副作用：补传队列未排空期间，常规同步会被推迟。队列有限且自终止，可接受。

### 5.6 fork 推送不触发 workflow

本仓库是 `jxxghp/MoviePilot-Plugins` 的 fork，**push 到 main 不会触发
Plugin Release 工作流**（已多次确认 `total_count` 不增加）。当前每次发版靠手动
`gh workflow run "Plugin Release"`。建议在仓库 Settings → Actions 中开启
fork 的 push 触发。

### 5.7 已过期但未清理的文档承诺

v0.0.8 已从 README 移除 `/rsync_clean`，但**代码中从未实现该命令**。
若有用户按旧文档寻找该功能，需要解释。清理幽灵文件本质是「遍历 + 删除」115 上的
文件，属高风险操作，建议**不做**（见 TODO）。

## 6. 发版记录

> ⚠️ 下表的「版本」指**已发布**的版本。
>
> 📌 **本插件在 alpha 阶段的版本号处理方式，已在 2026-09-22 更正（重要）**
>
> 起因是一次真机事故：v0.1.0 之后的多个 alpha 修复**始终没有改版本号**，

1. **排除规则仍走 rsync 首条匹配** —— `--exclude=` 列表顺序有意义；force 已不再
   使用 include/`--exclude=*` 整树传输（P0-2 改走 `--files-from`），但 ready 等
   模式仍依赖排除规则过滤源端。
2. **配额必须在 rsync 启动前预扣并落盘** —— 改成事后统计会重新打开重载绕过限流
   的竞态窗口。force 同样遵守（先对账得到问题清单，再按本批 `pair_files` 预扣）。
2b. **出队与 strm 登记只看对账，不看退出码** —— `exit_code == 0` 作门禁会让 23/24
   批次里已就绪的文件永不出队（P0-1）。整轮失败判定仍按不变量 #4 容忍 23/24。
2c. **对账前必须确认 src/dest 仍存在** —— `_audit_files_integrity` 在目录缺失时返回
   **空清单**而非报错；若不拦截，挂载掉线会被当成「全部通过」→ 错误出队 / arm strm /
   经 `audited_keys` 清掉历史异常。结算段有 `audit_valid` 门禁（v0.2.1 review 修复）。
2d. **队列 key 的反向解析一律走 `paths.rel_path_of_key()`** —— 任务名可含冒号，
   `split(":", 1)` 在第一个冒号处切开会把 `TV:主库:S01E01.mkv` 切成
   `主库:S01E01.mkv`，相对路径凭空多一段，拼出的文件系统路径永远不存在
   （表现为 strm 条目被判 `source_gone` 清理、可见性探测报 unknown）。
   出队日志用 `pair_files` **正向**构造 key，根本不反解析。
   > 📌 v0.2.1 的 commit message 曾写成「禁止 `split(":", 1)` 反解析」，
   > 但当时全仓仍有 5 处未迁移（`strm.py` 1 处、`strm_ops.py` 4 处）。
   > 本次 review 已全部收口到 `rel_path_of_key`，该表述现在才成立。
   > 另注：`paths.split_pair_key` 目前**全仓无生产调用者**（仅测试引用），
   > 真正在用的是 `rel_path_of_key` 与 `pair_for_path`。
3. **补传队列不要并入 `pending_queue`** —— 会污染冷却计时与看板统计。
4. **退出码 23/24 是有意容忍的** —— 不要改成「非 0 即失败」，那会让正常的
   源文件变动频繁告警。容忍的是**整轮失败判定**；单文件是否出队/进 strm
   一律以对账为准（不变量 #2b / P0-1）。
5. **老配置迁移只能精确匹配旧默认串** —— 放宽匹配条件会覆盖用户自定义配置。
6. **入库事件必须监听三个事件类型** —— 只注册 `TransferComplete` 会静默丢掉
   全部字幕与音频（宿主按文件类型分派，见 3.8）。新增文件类型时同步扩展
   `_TRANSFER_SUCCESS_EVENTS`。
7. **源路径归属必须按路径边界比较** —— 用 `startswith` 会让 `/media/TV`
   误匹配 `/media/TV2/x.mkv`，把文件挂到错误的映射上。
8. **版本号规则：`x.y.z` 每段只能是 0-9 单个数字，满 10 即进位**
   （即 `0.0.10` 不允许，应写 `0.1.0`；`0.9.10` 不允许，应写 `1.0.0`）。
   注意这与常规语义化的理解不同 —— **进位不代表功能级跃迁**，仅为位数约束。
   v0.0.13 之前已发布的版本号保持原样，规则自 v0.1.0 起生效。
   五处需同步：插件类 `plugin_version`、`package.json`、配置页版本徽标（硬编码在
   `Config.vue`）、索引 `version`、`history` 首项。
9. **排查事件问题前，先分清「事件」与「用户通知」是两条独立路径**
   —— 事件**按文件即时发布**（每个文件一次），用户入库通知则**按媒体/季批次合并**，
   且受「发送通知」开关与「后台/手动」门槛约束，两者互不影响。
   误把通知的批次语义套到事件上，就会得出「批次收尾才广播」这类错误结论
   （本插件曾据此写下错误文档，见 3.8.1）。
10. **事件走 durable outbox（at-least-once）**：同一事件可能重复投递，处理器必须幂等；
    投递时插件不可用会进入有限重试，超限后**永久丢失**且不重放。
11. **机制性结论必须附代码依据** —— 见 3.8.1 的教训。拿不出证据的写成
    「现象 + 待验证」，不要写成因果；更不要用「勿凭理论删除」去固化未验证的推断。

12. **事件 payload 按平台推荐用 `event.snapshot()` 读取**（类型化快照，字段由宿主契约
    保证），**但必须保留原始 dict 回退** —— 未登记契约或旧宿主时 `payload` 为 None，
    只走快照会让原本可用的事件全部读不到数据。日志里 `读取方式=` 即实际路径（见 3.8.6）。
13. **事件处理器会在线程池里跑，异常要自己兜住** —— 未捕获会记为宿主「插件错误」。
    注册入口 `on_transfer_complete` 只做兜底，业务逻辑写在 `_handle_transfer_event`（见 3.8.4）。
14. **`file_list_new` 可能为空**（28 个构造点里 25 个走默认空值），
    路径来源须按 `file_list_new` → `file_list` → `fileitem.path` 降级；
    `fileitem.path` 是下载器源路径，可能不在映射内，匹配不到只记日志、不可错误入队。
15. **不订阅整理失败事件是有意为之** —— 失败即未入库，入队无意义且会污染队列（见 3.8.3）。

16. **alpha 版本：部署前必须先向用户确认，且 alpha 标记不得写进版本号字段**
   （预发布形式记为 `x.y.z-alpha.n`，各段同样受单数字约束）。
   若确认为 alpha：**只提交代码，不 build、不 deploy、不触发 Plugin Release**。
   alpha 标记只出现在提交信息与文档里，三个版本字段始终保持纯 `x.y.z`。
   原因：`check_plugin_versions.py` 不接受 `-alpha.n` 后缀，会报「不是合法语义版本」，
   而该门禁同时跑在 `plugin-gate.yml`、`release.yml` 与本仓 pre-push 钩子里，
   写进版本字段会直接卡住推送与 CI。**已决定不放宽门禁**，请勿改动它去接受预发布后缀。

## 8. 代码结构：拆分记录

### 8.1 阶段 1（alpha，`ed2ba1d`）— 抽出四个无状态模块

`__init__.py` 一度达到 3128 行 / 61 个方法，其中 `_execute_sync` 单方法 572 行、
`handle_command` 352 行。拆分按「先搬风险最低的」推进，阶段 1 只搬**纯逻辑**：

| 模块 | 行数 | 内容 |
|---|---|---|
| `constants.py` | 105 | 默认参数、rsync 退出码、伴生字幕扩展名、各巡检节流、日志裁剪上限 |
| `paths.py` | 120 | `brief_paths`、映射对名归一化、key 前缀解析、排除目录/扩展名口径 |
| `ignore.py` | 94 | 忽略规则匹配与增删（**不含持久化**） |
| `strm.py` | 112 | strm 期望路径推导、三态流转判定、宽限期换算 |

**决定性约束 —— 什么能拆、什么不能拆**（依据 `docs/Plugin_Development.md` 7.4）：

> 宿主会为虚拟分身「在实例专属模块命名空间中重新执行源码」，但**插件自行导入的
> 第三方模块全局量仍然是共享的**。

于是结论很明确：

- ✅ **可以搬**：纯函数、常量、无状态逻辑 —— 不存在跨实例污染问题；
- ❌ **不能搬**：一切可变状态（`_pending_queue` / `_strm_watch` / 限流计数 /
  `_ignored_rules` …）。这些必须留在插件实例上，否则两个分身会共用同一份队列。
  因此新模块的签名一律是「传入状态 → 返回结果」，如
  `ignore.is_ignored(key, rules)` 而不是 `Ignorer().is_ignored(key)`。
  后者看着更面向对象，实则会制造「谁才是真相来源」的第二个答案。

**为什么主类不能离开 `__init__.py`**：版本门禁
（`.github/scripts/check_plugin_versions.py`）从 `plugin_dir/__init__.py` 里提取
类级 `plugin_version` 字面量。主类一旦搬走，门禁直接报「未声明 plugin_version」。
同理 `package.json` / 索引 version / 新模块都改变不了这一点。

**打包无需改动**：`release.yml` 用 `zip -r ... -x "*/__pycache__/*" -x "*.pyc"`，
子目录天然包含。仓库内已有先例（`agentresourceofficer` 27850 行 + `services/`、
`lunatvsource` 7355 行 + 6 个模块），宿主以 `app.plugins.<id>` 包方式加载，
包内相对导入可用。

### 8.2 拆分带来的真实收益（不只是「好看」）

顺带消除了三处**真实的重复与不一致**：

1. **映射对名回退表达式在 9 处各自硬编码**，且写法不完全一致：
   `pair.get("name") or (pair.get("src") or "").strip().rstrip("/")`。
   任一处漏掉 `rstrip("/")`，同一个文件就会在不同代码路径下归属到**不同的 key
   前缀**，表现为「事件入队了、同步时却找不到它」这类极难定位的问题。
   现统一走 `paths.pair_name()`。
2. **排除目录集合与扩展名白名单在 3 处重复构造**，现统一走 `paths` 的两个函数。
3. **`_remove_ignore_rule` 原先用重新赋值列表实现**，而调用方持有的是同一个
   列表对象。改用就地切片赋值，语义不变但消除了对象身份分歧的隐患。

### 8.3 拆分中发现并订正的一处失真

`_strm_check` 原实现：

```python
if state == SUSPECT:   new_suspects.append(...)
elif state == WATCHING: continue
elif strm_exists:      settled_ok.append(key)     # ← 问题在这
else:                  dropped.append(key)
```

「源端已消失」与「映射被改成没有 strm_dir」这两种清理项，若恰好 `strm_exists`
为真（例如源端删了、strm 还在），会被归进 `settled_ok`，也就是巡检返回值里的
`ok`。不影响功能，但**计数长期失真** —— 排查时看不到真实的清理规模。

现拆成三个出口：`SETTLED`（正常解除）/ `SOURCE_GONE` / `NO_STRM_DIR`，
后两者只计入 `dropped`。判定顺序保持与原实现一致（映射失效 → 源端消失 →
strm 已生成 → 是否到期），顺序是承重的，已在 `strm.classify_watch` 的注释中写明。

### 8.4 拆分方法（可复用于阶段 2）

阶段 1 的验证手段，**不依赖真实宿主**，可在无 MoviePilot 环境时复用：

### 8.5 ⚠️ 一个只有实例化才能发现的坑

拆分第一版把 `_MISSED_SCAN_ENABLED_DEFAULT` / `_LEGACY_DEFAULTS` /
`_MISSED_SCAN_INTERVAL` 从**类体**删掉、只保留模块级别名（值确实已经 import
进来了，看起来冗余）。结果 `__init__` 里的 `self._MISSED_SCAN_ENABLED_DEFAULT`
直接抛 `AttributeError` —— **插件实例化即失败**。

`py_compile` / `compileall` 都**发现不了**这个问题，因为它们不执行类体求值后
的属性访问。类体别名是承重的，判断标准是「有没有代码用 `self.X` 访问它」，
而不是「值是否已经存在」。

**教训**：拆分后必须真正实例化一次，仅做语法检查远远不够。

### 9.1 动机

现有入库监听依赖宿主的整理完成事件（`TransferComplete` / `SubtitleTransferComplete` /
`AudioTransferComplete`）。它监听不到这些场景：

- 用户**手动放入**文件（不经下载器/整理流程）
- **外部工具**（其它脚本、其它容器）搬入文件
- 整理事件**漏发**（宿主 durable outbox 超过重试上限即永久丢弃，见 3.8.7）

Webhook 可作为**第二来源**覆盖上述场景。来源两处：Emby、MDC-ng。

### 9.2 宿主 webhook 链路（已核实）

```
Emby/MDC ──HTTP──▶ POST /api/v1/webhook/?token=API_TOKEN&source=<实例名>
                        ↓ verify_apitoken（宿主统一鉴权）
                   WebhookChain.message(body, form, args)
                        ↓ webhook_parser()   ← 由**模块**提供，插件不参与解析
                   eventmanager.send_event(EventType.WebhookMessage, info)
                        ↓
                   插件 @eventmanager.register(EventType.WebhookMessage)
```

源码位置：

| 环节 | 文件 |
|---|---|
| HTTP 端点（POST/GET，需 `token`） | `app/api/endpoints/webhook.py` |
| 链路与广播 | `app/chain/webhook.py` |
| 解析分发 | `app/chain/base.py:514`、`app/modules/emby/__init__.py:59` |
| 事件类型定义 | `app/schemas/types.py:226`（`WebhookMessage = "webhook.message"`） |
| 事件契约 | `app/runtime/event/contracts.py:100` → `WebhookEventInfo` |

**payload 结构**（`app/schemas/mediaserver.py:171` 的 `WebhookEventInfo`）常用字段：
`event` / `channel` / `server_name` / `item_type` / `item_name` / **`item_path`** /
`media_source` / `media_id` / `json_object`（原始报文）

### 9.3 两个来源的支持情况 —— 决定方案形态

| 来源 | 宿主支持 | 依据 |
|---|---|---|
| **Emby** | ✅ 原生 | `app/modules/emby/__init__.py:59` 有 `webhook_parser`，`emby.py:829` 有 `get_webhook_message`，支持 `playback.start/stop`、`library.new` 等 |
| **MDC-ng** | ❌ **宿主不认识** | 遍历 `app/modules/` 全部 40+ 模块，**无 mdc-ng / mdcz**。媒体服务器模块只有 `emby` `jellyfin` `plex` `trimemedia` `zspace`（`watchsync` 支持的 `zspace` 即后者） |

**当时的结论是「方案必然是双通道」** —— 因为不能指望宿主替我们收 MDC-ng。
这个结论后来被推翻了一半：宿主确实不替我们**解析** MDC-ng，但宿主**收得下**
MDC-ng 的报文，只要发送端把地址配成平台入口。**收报不等于认人**，
当时把这两件事混成了一件（订正见 9.18）。

### 9.4 插件自建端点的能力（已核实 · 该端点已移除，见 9.18）

`app/adapters/web/plugin/routes.py:116-125`：

```python
allow_anonymous = api.pop("allow_anonymous", False)
auth_mode = api.pop("auth", "apikey")          # "bear" 或 "apikey"
if not allow_anonymous:
    dependencies.append(Depends(self._verify_token if auth_mode == "bear" else self._verify_apikey))
```

即插件的 `get_api()` 可以声明 `"allow_anonymous": True` 的端点，跳过宿主鉴权 ——
自建 webhook 正是这种场景（MDC-ng 不会带 MoviePilot 的 token）。

### 9.5 仓库内的参照实现：`plugins.v3/watchsync`

`watchsync` 已经实现了同类功能，可作为直接参照：

```python
@eventmanager.register(EventType.WebhookMessage)
def handle_webhook_message(self, event: Event):
    if getattr(event_data, 'channel', '') not in ["emby", "zspace"]:
        return
    supported_events = ["playback.pause", "playback.stop", "library.new", ...]
```

两个值得照抄的做法：

1. **按 `channel` 过滤**：多个插件可能同时订阅 `WebhookMessage`，各自只处理自己的来源
2. **不用 `event.snapshot()`，改用 `getattr(event_data, ...)`** —— 因为
   `WebhookMessage` **未登记在 `_SNAPSHOT_EVENTS`**（`contracts.py` 只登记了类型而非快照），
   走快照路径拿不到 payload。
   ⚠️ 这与本插件 `_handle_transfer_event` 的做法**相反** —— 那里必须优先用
   `snapshot()`。差异原因已记录在 3.8.6：是否走快照取决于**该事件类型有没有登记契约**，
   不能一概而论。

### 9.6 方案：双通道 + 合流（通道 B 已废弃，见 9.18）

```
通道 A（平台链）：订阅 EventType.WebhookMessage
                 由 webhook_parser 认领（发送端显式声明收件人）
                 且事件为入库类 → 取 item_path
通道 B（MDC）：插件自建 POST /webhook/mdc（allow_anonymous）   ← 已移除
                取路径（字段名待定，见 9.8）

        两条通道合流到同一入口：
        webhook → 取路径 → 校验归属映射（复用 paths.pair_for_path）
                         → 校验源端文件存在 → 入冷却队列（复用现有幂等入队）
```

Emby 后台 Webhook 配置：

```
http://<moviepilot>:3001/api/v1/webhook/?token=<API_TOKEN>&source=<emby实例名>
```

`source` 可省略（宿主会遍历所有 emby 实例），但**建议填**，避免多实例时解析错乱。

**关键设计**：webhook 是**补充而非替代**。同一文件可能同时从两条路进来，
现有 `_pending_queue` 的重复检测天然幂等（不刷新冷却计时），不会重复入队 ——
这一性质在 3.8.2 已被验证，是复用的基础。

### 9.7 通道 B 的安全风险与最终防护链（曾按此实施，端点已于 2026-09-22 移除）

> 本节保留为**历史记录**：四道防护、`_ingest_from_parts`、`path_in_roots` /
> `match_mapping` 都已随端点删除（见 9.18）。留下它是因为「暴露面一旦打开，
> 兜底要靠不依赖用户配置的那一道」这条推理本身仍然成立，将来若有人再提自建
> 端点，可以直接看到当初的代价清单。

`allow_anonymous: true` 意味着**知道 URL 就能往插件灌数据**：

- 伪造入库 → 触发不必要的上传（消耗 115 风控配额）
- 灌入大量伪造路径 → 撑爆冷却队列

最终实现为**四道串联**（顺序即拒绝顺序，代码在 `_ingest_from_parts`）：

| # | 手段 | 说明 | 默认 |
|---|---|---|---|
| 1 | 端点开关 | 必须显式开启；**默认关闭**（暴露接口不能是升级的副作用） | 关 |
| 2 | 来源 IP 白名单 | 支持精确 IP 与 `192.168.1.` 前缀 | 空（不限） |
| 3 | 密钥 | `X-Webhook-Secret` 头 **或** `?token=` 查询串 | 空（不校验） |
| 4 | **路径白名单** | **无条件生效**；显式配置优先，未配置时退回各映射源目录 | 恒生效 |

**为什么第 4 道必须是「无条件」**：前三道都可能因为「用户没配」而形同虚设，
只有路径白名单是**不依赖任何用户配置**的兜底 —— 伪造者能编造任意路径字符串，
但不可能让它同时落在你配置的媒体库目录下。

**与设计稿的一处收紧**：设计稿说「退回 `sync_pairs` 源目录即复用已有判据」。
实施时保留了退回行为（保证开箱可用），但**同时提供显式白名单字段并建议必填** ——
因为 MDC 的入库目录与媒体库常常不是同一棵子树，退回行为在那种场景下会
「看起来能用、实际全被拒」，而用户只能看到一个笼统的失败。

比较判据没有复用 `paths.pair_for_path()`，而是在 `webhook.py` 里独立实现
（`path_in_roots` / `match_mapping`）：两者都要做**逐段比较**（`/media/TV2` 不得
落进 `/media/TV`，这与 3.11 记录的那类错误归属同源），但 webhook 层是纯函数、
不应反向依赖同步链路的实现细节。两处判据相同、语义不同：webhook 层回答
「可信吗」，同步层回答「同步到哪」。

### 9.8 关于「实施前需要用户提供」的四项 —— 实施时的处理（第 2 项已随端点失效）

| 原待确认项 | 处理方式 |
|---|---|
| MDC-ng 的真实报文样例 | **未拿到，因此不猜**。改为候选字段表（`PATH_FIELD_CANDIDATES` + `NESTED_CONTAINERS`）逐项尝试，并把**未识别时的报文结构摘要**写进看板与日志 —— 用户推一条就能看出「该把哪个字段加进候选表」，不必等我们猜对 |
| MDC 是否支持自定义 Header | 当时两种都做了：`X-Webhook-Secret` 头 **与** `?token=` 查询串。**端点已移除，此项作废** —— 现在只需要发送端能在 URL 上带查询串（`?token=<API_TOKEN>&source=rsync115sync`），若连查询串都改不了，用反向代理补 |
| 要监听的事件类型 | 只监听入库类（`library.new` / `library.update` / `item.added` / `item.updated`）；播放、标记、收藏显式**排除在白名单之前**（`EMBY_IGNORE_EVENT_PREFIXES`）。理由见 9.10 |
| Emby 定位：补充还是替代 | **补充**。整理事件监听原样保留，两条来源合流到同一个入队函数 |

> 第三项是实施阶段**新增的关键发现**：播放类事件在 Emby 里同样携带 `Item.Path`。
> 若按「只挑出要处理的事件」的正向写法（白名单），一旦漏了某个播放事件名，
> 后果是**用户每看一集就重新上传一次该集** —— 静默、持续、消耗风控配额。
> 因此实现改成**先排除事件族前缀、再查白名单**，漏一个入库事件名只是少同步一个文件
> （能从日志看到），漏一个播放事件名的代价却大得多。

### 9.9 实施顺序

1. **先做通道 A（Emby）** —— 宿主链路已通、无需自建端点、无需处理鉴权，风险最低
2. **通道 B 两步走**：先写一个**只记日志、不做任何处理**的临时 debug 端点，
   让你配上去观察真实 payload；拿到真实报文后再写解析器

3. 与现有入库链路合流，并**补测试**（webhook 解析、路径校验、幂等、来源过滤）

> ⚠️ **不要凭猜测写解析器**。本项目已多次在「凭推测写机制」上吃亏 ——
> 3.8.1 记录的两次无依据结论（「宿主只在批次收尾广播」「file_list_new 按类型置空」）
> 都是这样产生的。没有真实报文就动笔，只会重蹈覆辙。

### 9.10 实施记录：与设计稿的差异，以及为什么

**① 放弃了「先写只记日志的 debug 端点」这一步。**
理由是它要解决的问题已经用更好的方式解决了：候选字段表 + **未识别时把报文的
字段结构摘要写进看板与日志**。debug 端点需要用户配两次（先配 debug、看完再改
正式地址），而结构摘要把「看报文」这件事变成常驻能力 —— 每次未识别都留痕，
用户不必特意去观察，我们也不必等一轮往返。摘要只记**字段名与类型**，不记路径值。

**② 「未知字段」不报错，只计数。**
设计稿设想的是「拿到真实报文后写解析器」。实施时反过来：解析器先尽力而为地覆盖
已知形态，拿不到就把**结构摘要**摆出来。这样一个我们没想到的发送端不会表现成
「静默无响应」，而是看板上「收到 > 0、入队 = 0、未识别 > 0」这一可读组合，
用户照摘要把字段名报过来即可扩展候选表 —— 不需要改代码结构，只加一个字符串。

**③ 入队逻辑抽成 `_enqueue_ingest_paths` 并让两条来源合流。**
设计稿只写了「合流到同一入口」，没写这一层的具体形状。最终它成为事件链路与
webhook 链路的**唯一**入队实现，事件链路的 `_handle_transfer_event` 只负责
「从 payload 里取路径」，取完交给它。代价是动了一处已稳定运行的代码，收益是
两条来源不可能出现行为漂移 —— 归一化、映射归属、扩展名过滤、忽略清单优先、
幂等（不刷新时间戳）、补齐清单清理只有一份实现。

> **⚠️ 这条第一次实施时没做完**：当时只是把 webhook 链路接到了 `_enqueue_ingest_paths`，
> 整理事件链路里那份**逐字重复**的入队实现还留着，它比 webhook 那份**少了忽略清单判断** ——
> 于是「被忽略的文件仍会经整理事件入队」这个洞依然存在，而文档却已经写成「两条来源不可能漂移」。
> 复核时发现并彻底删除：`_handle_transfer_event` 现在只负责「从 payload 里取候选路径」，
> 其余判据一处实现。教训是**声明合流不等于完成合流**，合流必须检查旧实现是否真的删掉了。
>
> 顺带修掉两个由这次合流暴露出来的真实缺陷（同一函数内、相互独立）：
> 1. **已在「待补扫」清单的条目被判成重复投递** → 补齐扫描发现了它、真实入库事件又被拒，
>    该文件从此既不在冷却队列、也没被任何一轮同步取走，用户只能看着清单里永远挂着一条。
>    正确语义是「升级」进正常冷却队列并移出待补扫清单。
> 2. **幂等判据的顺序**：「待补扫清单」曾作为重复判据被置于「已在冷却队列」之前，
>    而一个文件可以同时出现在两处（webhook 抢先入队、随后补齐扫描又发现它），
>    于是重复投递会绕过幂等检查、把冷却重新计时。

**④ `WebhookMessage` 必须直接读属性，不能走 `event.snapshot()`。**
与整理事件的写法**恰好相反**，且这个差异不会以任何报错的形式出现 ——
`snapshot()` 正常返回、`payload` 为 `None`、于是路径为空、于是「什么都没发生」。
已核实：`WebhookEventInfo` 登记在契约表里，但 `WebhookMessage` **不在**
`_SNAPSHOT_EVENTS` 内（`contracts.py:132`）。未来若宿主把它加进去，本插件的
`getattr` 读法**仍然有效**（快照与原始 payload 字段同名），因此这个选择不会过时。

**⑤ 运行态计数落盘。**
设计稿未提。实施时为它单独持久化（`webhook_stat`）：用户的排查习惯是
「推一条 → 重载插件 → 去看板确认」，只在内存里的话重载即清零，永远看不到刚推的
那一条，现象会表现成「每次重载后都是 0 次，是不是没收到」。

**⑥ 事件白名单从「正向挑选」改为「先排除事件族前缀」。**
见 9.8 的说明：两类误判的代价严重不对称 —— 漏一个入库事件名少同步一个文件，
漏一个播放事件名则让用户每看一集就重传一集。防护要建在**代价大的那一侧**。

**⑦ 端点方法必须全链路 async，且新增了一组「真路由」测试。**
读请求体只能 `await request.json()`，因此 `_ingest_from_request` 是协程；
而它最初的调用方 `_api_webhook_ingest` 写成了**同步**函数，于是协程对象被当成
普通返回值交给响应编码器，报错是与真实原因毫无关联的
`TypeError: 'coroutine' object is not iterable`。现两者皆 async 并 `await` 衔接。

更要紧的是这条：参数类型写成 `Any` 时 FastAPI 会把它当**查询参数**而不是注入
`Request` —— 端点注册成功、OpenAPI 正常生成、HTTP 200，但来源 IP / 请求头 /
请求体全读不到，密钥校验永远失败、报文永远是空的。这种「注册成功、调用成功、
结果全空」的失效在桩宿主里根本走不到，于是补了一组**真路由**契约用例：把端点
挂进真实 FastAPI 应用、用 `TestClient` 发真请求，逐一验证参数注入与报文解析。

> 📌 自建端点移除后（9.18），这组 harness 没有删 —— 它被**改挂到平台链路**：
> 现在搭出来的是宿主端点 `POST /api/v1/webhook/`，请求经它进入
> `WebhookChain`，再由插件的 `webhook_parser`（经 `get_module()` 声明表取得）
> 认领。也就是说，这条「用真请求而不是直接调函数」的经验被继承下来了，
> 只是对象从「我们自己的端点」换成了「宿主的端点」—— 而后者更接近真机。
（坑：FastAPI 实际调用的是注册时**捕获**的 `route.dependant.call`，测试里只改
`route.endpoint` 不会改变分发目标，两处都要换。）

**⑧ 看板侧的缺口：后端返回了、文档写了、前端没画。**

USAGE.md 的「怎么确认这条路通了」整节把四项计数与「最近报文结构」写成看板上可见，
而 `Page.vue` 此前从未渲染 `statusData.webhook` —— 后端用例只断言 `/status` 里
有这个字段，而字段确实在，**所以这个缺口不会让任何测试变红**。用户按文档去看板
自查，看到的是空看板，只能得出「webhook 没生效」这个错误结论。

此类「文档 ↔ 后端 ↔ 前端」三方不一致必须从**模板侧**断言才能发现，因此补了三条
看板契约用例（计数是否被渲染、面板是否有显示条件、模板用到的字段是否都有空值兜底）。

> 显示条件的判据值得单独说明：**不能**用「webhook 功能已启用」—— 渠道默认就是
> `emby`，用它判断等于面板对每个用户常驻显示「收到 0 条」，门控形同虚设，
> 还会让没配 webhook 的人怀疑自己配漏了。当时用的是「曾收到过请求 **或** 自建端点
> 已开启」：没有 webhook 流量的人看不到这块面板。
>
> 📌 **后一项已在 2026-09-22 随端点移除**（见 9.18），现在的判据只剩
> 「曾收到过请求」。这个改动本身不影响上面的推理：门控的正确靶子一直是
> 「有没有流量」，自建端点开关只是当时顺手加的第二个入口 ——
> 它同时暴露了一个设计气味：**用「功能开关」当显示条件，等价于把
> 「用户配过什么」当成「这条链通不通」的证据**，而两者并不等价。

### 9.11 ⚠️ 自查发现：单靠平台 webhook **不够**，且用它必须做一件事

提交前的自我审查里复查了一遍宿主链路，结论要写在最前面，因为它决定这项功能是否可用：

**平台 webhook 会不会更简单？** 分两半回答：

**「发送端怎么接」这一半，平台确实更简单。** 通道 A 的存在价值就是这个：
不用自建端点、不用自己管密钥与 IP 白名单，宿主用 API Token 鉴权，Emby 直接回调
`/api/v1/webhook/?token=...&source=...` 即可。所以文档里一直写「用 Emby 的话不需要
打开自建端点」—— 这个判断经复查成立，没有要改的地方。

> 📌 三个月后再看这句话，它其实已经给出了删除通道 B 的路线：**平台侧本来就更好**，
> 唯一的反例是「宿主不认识的发送端」。9.18 证明了那个反例不成立（宿主收得下，
> 只是不认识），于是「更好的那一半」自然成了全部。

**但整条链上有一个会让功能静默失效的坑，且它就在平台这一侧。**
宿主把 webhook 报文的解析交给 `webhook_parser` 这个模块方法，而它的契约是
（`contracts.py:1089`）：

```
ModuleMethodContract(
    family="integration",
    aggregation=ModuleResultAggregation.FIRST_NON_EMPTY,   # 取第一个非空结果
    plugin_short_circuit=True,                             # 非空即短路
    public_to_plugins=True,                                # 插件可实现
)
```

`webhook_parser` 同时出现在 `_OBSERVED_HOST_METHODS` 与「公开给插件」的可实现集合里。
配合 `dispatcher.py:169` 的调度顺序（**插件优先、宿主殿后**）与
`_provider_call_mode`（result 非空 + FIRST_NON_EMPTY → 返回 `STOP`），语义是：

> **任何一个启用的插件只要实现了 `webhook_parser` 并返回非空结果，
> 宿主的 Emby / Jellyfin / Plex 解析器就再也不会被调用。**

这不是推断，是用宿主自己的调度代码跑出来的复现（`/tmp/mp-src`，本机可重跑）：

```
# 反证 1：插件返回非空 → 宿主解析器被跳过（这就是必须实现钩子的原因）
provider ours      mode= original
   result = OUR_EVENT
provider host_emby mode= stop
   STOP, not called          ← Emby 解析器被跳过
FINAL: OUR_EVENT

# 反证 2：插件返回 None → 宿主解析器照常接棒（这就是我们采用的策略）
provider ours      mode= original
provider host_emby mode= original
FINAL: EMBY_EVENT
```

复现命令（在 MoviePilot 源码根目录执行，需要 click 可导入）：

```python
from app.runtime.extensions.module.dispatcher import ModuleInvocationDispatcher as D
from app.runtime.extensions.module.dispatcher import _ProviderCallMode
from app.runtime.extensions.module.contracts import get_module_method_contract
c = get_module_method_contract('webhook_parser')
def ours(body=None, form=None, args=None): return None       # 本插件的策略
def host_emby(body=None, form=None, args=None): return 'EMBY_EVENT'
result = None
for f in (ours, host_emby):
    mode = D._provider_call_mode(c.aggregation, result, f, allow_relay=False)
    print(f.__name__, '->', mode.value)
    if mode is _ProviderCallMode.STOP:
        print('  (被跳过)'); break
    result = D._aggregate_provider_result(result, f(), mode, c.aggregation)
print('FINAL:', result)
```

**自查结论：本插件必须实现 `webhook_parser`，且对本插件不关心的来源一律返回 `None`。**

为什么这是必须做的而不是「顺带的优化」：不实现它，我们就得赌「别的插件永远不实现」。
一旦赌输（任何插件为任何目的实现了这个钩子并返回非空），宿主的 Emby 解析器被跳过，
`WebhookEventInfo` 根本不会被构造，`EventType.WebhookMessage` 不广播，本插件一行日志
都不会有 —— 现象与「Emby 回调没配好」完全一样，而排查方向会全部指向错误的地方。
用户没有任何可自查的线索。

**实现策略：只认领「显式声明发给本插件」的报文，其余一律 `return None`。**
返回 `None` 等于「我没意见」，后续 provider（含宿主原生 Emby 解析器）照常接棒 ——
`FIRST_NON_EMPTY` 的短路只在**结果非空**时触发。

> ⚠️ **认领判据绝不能按 `channel` 判定。** 第一版实现就是这么写的（拿用户配置的
> `webhook_channels`，默认 `emby` 去匹配报文的 channel），自查时发现是个严重错误：
> 宿主的 Emby 解析器产出的 `channel` **恰恰就是** `emby`
> （`app/modules/emby/emby.py:1082`）。按它认领会把宿主本来能正常处理的 Emby 报文
> 抢过来、短路掉宿主解析器，于是健康检查、图片获取等宿主功能一起失效 ——
> 而本插件只想要一个路径，代价完全不成比例。
>
> 现在的判据是**发送端必须显式声明收件人**，且只认一个专属标识：
> `source=rsync115sync`（查询串）或 `X-Webhook-Target: rsync115sync`（请求头）。
> 宿主自己的解析器拿 `source` 去查**新媒体服务器实例名**，`rsync115sync` 不是实例名，
> 它们只会返回 `None` 并继续，不存在抢错的可能。仓库已自带 `emby` 白名单的哨兵用例。

> 这条与 §9.10 的 `WebhookMessage` 读取方式（不能走 `event.snapshot()`）是两个
> 独立的问题，都源自「平台 webhook 这条链比整理事件那条链更依赖约定、更少类型保证」。

#### 实现时必须避开的三个坑（都已踩过并有哨兵用例）

**① 请求体的载体形态。** `/api/v1/webhook/` 传给 provider 的 `body` 是
`await request.body()` 的**原始 bytes**（`app/api/endpoints/webhook.py`），不是解析好的
dict；`form` 才是 `await request.form()`。而三家宿主模块用的载体各不相同：
Emby 用 form（JSON 塞在 `form["data"]`）、Jellyfin/TrimeMedia 用 body、Plex 用 form。
所以解析层把 form → body → args 三种都试一遍，不能只认一种。

**② 候选字段必须**大小写不敏感**。** Emby 自己的报文字段就是 `Item.Path`（大写 P），
而候选表按小写写。严格按大小写取值会把「字段名对了、只是首字母大写」判成「未识别」，
用户照报文结构摘要也看不出问题出在大小写上 —— 这是本项目反复吃过的「静默无响应」类坑。

**③ 认领与渠道过滤必须自洽。** 认领后构造的 `WebhookEventInfo.channel` 是
`rsync115sync`，而 `_handle_webhook_event` 的渠道过滤只放行用户配置的渠道（默认
`emby`）—— 第一版会「认领一条报文、再自己把它过滤掉」，现象与「没收到」完全一样。
现在处理侧对 `WEBHOOK_TARGET` 单独放行，并有一条「认领 → 入队」的闭环用例钉住。

> 三条都属于同一类：**每个环节单独看都正确，串起来却什么都不发生**。
> 这类问题只能靠端到端的闭环用例发现，单元级的断言全都会通过。

#### 那自建端点还需要吗

需要，但理由比原来更清晰了：**`webhook_parser` 解决不了 MDC-ng。**
那个钩子拿到的仍然是**宿主已经决定要处理**的报文 —— 而宿主不认识 MDC-ng，
不会为它构造 `WebhookEventInfo`，也就没有 `WebhookMessage` 事件可广播。
`webhook_parser` 只改变「谁来解析」，不改变「宿主认不认识这个发送端」。

所以两条通道的分工是：

| | 通道 A（平台链） | 通道 B（自建端点） |
|---|---|---|
| 发送端 | 宿主认识的（Emby/Jellyfin/Plex） | 宿主不认识的（MDC-ng、自建脚本） |
| 鉴权 | 宿主 API Token | 插件内部四道防护 |
| 本插件要做 | 实现 `webhook_parser` 认领 + 订阅事件 | 暴露匿名端点 + 自己防伪 |

#### 一个仍待真机确认的点

`webhook_parser` 的签名契约里 `required_parameters=("body","form","args")`，但
`base.py:514` 的调用方式与 emby 模块的签名（`def webhook_parser(self, body, form, args)`）
都是一致的；本插件的实现按同一签名写。**若宿主用的是关键词调用而插件用位置参数，
不会报错也不会告警**（`diagnose_module_callable` 在兼容阶段只返回问题、不拒绝 provider），
只是拿不到值 —— 属于要真机确认的一项，已加入下方清单。

### 9.18 拆除通道 B：自建 webhook 端点整体移除（2026-09-22）

**决定：删除插件自建的 webhook 端点，以及为它配套的四条防护配置。**
入库来源只剩平台链路一条。

#### 移除了什么（清单，便于日后 review 时对账）

| 类别 | 内容 |
|---|---|
| 端点 | `POST /api/v1/plugin/Rsync115Sync/webhook`（`allow_anonymous: true`） |
| 函数 | `_api_webhook_ingest` / `_ingest_from_request` / `_ingest_from_parts` / `_webhook_payload_of` / `_webhook_allowed_roots` / `_webhook_ip_allowed` |
| 纯函数（`webhook.py`） | `secret_ok` / `header_lookup` / `path_in_roots` / `match_mapping` |
| 配置项 | `webhook_self_enabled` / `webhook_secret` / `webhook_ip_allowlist` / `webhook_path_allowlist` |
| 运行态字段 | `/status` 的 `webhookStat.self_enabled` / `secret_set` / `allow_roots` |
| 前端 | Config.vue 的四行设置 + 四个默认值；Page.vue 的「· 自建端点（未）开启」徽标与可见性判据 |
| 依赖 | `_FastAPIRequest` 导入块（端点移除后无人引用） |

**保留**了 `webhook_channels`（渠道过滤）与 `webhook_parser` 认领逻辑 ——
前者对平台链路仍然必要，后者已经是唯一入口。

#### 为什么

**① 它存在的前提被真机推翻了。** 通道 B 的唯一理由是 §9.3 的结论：
「宿主不认识 MDC-ng，所以 MDC-ng 的报文必须由插件自己收」。
但这个结论把**收报**与**解析**混成了一件事。真机验证（§9.16/§9.17）
之后事实是：宿主端点 `POST /api/v1/webhook/` 对**任何**发送端都收得下报文，
它只是不认识发送端身份；而插件通过 `webhook_parser` 认领（发送端带
`source=rsync115sync`）就能拿到它。两条事实合起来 ——
**「宿主不替我们解析」并不等于「宿主不替我们收」** —— 通道 B 的前提就没了。

**② 免鉴权入口的代价与收益倒挂。** 自建端点是本插件**唯一**一个
`allow_anonymous` 入口。§9.7 的四道防护里，前三道（开关/IP/密钥）都
「用户不配就等于没有」，只有路径白名单是不依赖配置的兜底。也就是说，
安全水位取决于用户是否恰好配齐 —— 而它换来的场景窄到只剩
「发送端连 URL 查询串都改不了」。用四条配置项 + 一整套防护链 + 看板字段
+ 两处文档去覆盖这一个场景，不划算。

**③ 两个入口 = 两套错误语义，排查分支翻倍。** §9.16 已经记过：
同一个畸形请求，打宿主是 400，打自建端点是 200 且正常入队。
看似「自建端点更宽容」，代价是用户遇到「什么都没发生」时，
**必须同时考虑两个入口的失败模式**，而两者的斜杠规则还是**相反**的
（宿主必须带尾斜杠、自建端点必须不带）。少一个入口，少一半分支。

#### 换来了什么替代能力

移除后，原先只有通道 B 能覆盖的场景对应如下：

| 原先需要通道 B 的场景 | 现在的做法 |
|---|---|
| MDC-ng / 自建脚本入库 | 同一个平台地址 + `?source=rsync115sync`（或 `X-Webhook-Target: rsync115sync`） |
| 发送端只能发 query string，发不了 body | 宿主端点**同时注册了 `GET /`**（`webhook_message_get`），走 `args` 一样能进来 |
| 发送端改不了 Content-Type（§9.16 成因 B） | 需要反向代理补 header，插件内部不再兜这件事（见下） |

#### 明确的代价（不掩饰）

**① 失去了「Content-Type 配错也能活」这条退路。**
§9.16 记录的成因 B（声明 `multipart/form-data` 却发裸 JSON）里，
自建端点因为**先试 JSON** 而能兜住，宿主端点的读取顺序（`body` → `form`）
会直接 400。现在这条路没了。**可接受的理由**：成因 B 的根因在发送端配置，
改对发送端才是正解；自建端点只是让一个配错的发送端「看起来能用」，
而它同时也掩盖了「发送端配错」这件事本身。USAGE 4.5.2 保留了
「到达 = 0 时按序查这三项」的清单，把排查方向指过去。

**② 老地址会 404。** 升级后必须把发送端地址改成平台入口
（USAGE §4.5.3 有升级提示）。这是**唯一**的破坏性变更，且只影响
此前主动开启过自建端点的用户 —— 该端点默认关闭，未开启的用户无感。

**③ 暴露面换成了「依赖宿主鉴权」。** 平台端点的 `token=<API_TOKEN>`
由宿主 `verify_apitoken` 校验，强度取决于用户的 token 管理。
这比「自建端点 + 用户可能没配的密钥」更可控：至少鉴权是**默认生效**的，
不需要用户额外做对什么。

#### 怎么保证没有残留（哨兵）

- `test_no_self_built_endpoint_is_registered` —— 断言 `get_api()` 里
  **不存在**路径为 `/webhook` 的端点，且**没有任何**端点带
  `allow_anonymous`。这条是移除的**正向哨兵**：将来谁再把自建端点加回来，
  它会红。
- `test_stub_host_status_defaults_align_with_frontend` —— 断言
  `/status` 不再返回 `self_enabled` / `secret_set` / `allow_roots`，
  且前端模板不再引用它们（否则恒取 `undefined`，是一类静默失效）。
- `test_host_route_accepts_documented_payload_shapes` /
  `test_host_route_enqueues_every_path_in_the_list` —— 移除后
  重新钉住**唯一**入口的闭环，避免出现「删掉了通道 B、通道 A 也没验过」。

### 9.17 ⚠️ 只实现 `webhook_parser` 是死代码 —— 必须在 `get_module()` 里声明

**这是 2026-09-22 真机联调的最终结论，也是本项目迄今最贵的一个教训。**

#### 症状与代价

`source=rsync115sync` 的报文打进来，宿主日志能看到请求，**插件一行日志都没有**。
排查依次走过：

| 轮次 | 怀疑对象 | 结论 |
|---|---|---|
| 1 | Content-Type 与 body 形态不匹配 | 真踩到了（400），**但不是本次的因** |
| 2 | 地址缺尾斜杠被 307 重定向 | 真踩到了，**也不是** |
| 3 | 映射配置 / 字段名 | 都不是 |
| 4 | **`get_module()` 从未声明** | ✅ 这才是 |

前三轮全部建立在「插件已被调用」这个**错误前提**上，因此怎么查都查不到 ——
这是本次真正值得记的东西：**跨系统静默失效时，先验证链路是否接通，再排查链路上的每一步。**

#### 机理

宿主从 `get_module()` 返回的「方法名 → 方法」映射里收集 provider
（`app/runtime/extensions/plugin/projection.py` 的 `modules()`）：

```python
declared = plugin.get_module()
if declared is None:
    continue          # ← 本插件此前就走到这里，对所有模块方法不可见
modules[(plugin_id, plugin.get_name())] = declared
```

基类 `_PluginBase.get_module()` 的实现是 `pass`（返回 `None`）。
**所以只写 `def webhook_parser(self, body, form, args)` 永远不会被调用，
既不报错也没有任何日志。** 修复就是一行：

```python
def get_module(self) -> Dict[str, Any]:
    return {"webhook_parser": self.webhook_parser}
```

#### 为什么自查发现不了

这一条比「装饰器被删」（见 `test_registration_contract.py` 文件头）更隐蔽：

- **没有删除记录、没有 diff** —— 这个声明从未存在过，不是被谁删掉的。
- **`grep webhook_parser` 会命中方法定义**，让所有基于搜索的自查误判为「已实现」。
- **宿主不报错** —— 基类默认返回 `None` 是合法值，宿主只当这个插件没声明模块方法。
- **`_diagnose_callable` 也不会抱怨** —— 它只在**已被收集**的 provider 上检查签名，
  没被收集的根本走不到那一步。

#### 排查中还暴露了一个部署层面的坑：改了没推 = 真机没变

前三轮修复（Content-Type 文档、尾斜杠文档、`get_module()` 声明）都只落在**本地提交**里，
`origin/main` 上始终没有 `get_module`。于是 NAS 拉到的仍是没有声明的版本，
真机现象**一个字都没变** —— 而每轮我都以为「修好了，你再试」。

判据（真机日志里一眼可辨）：

| 现象 | 含义 |
|---|---|
| 有 `请求插件 xxx 执行：webhook_parser` | 声明生效，provider 已被收集 |
| 只有 `请求系统模块执行：webhook_parser` | **没有任何插件 provider** —— 声明没生效（或版本没更新） |

第二条日志是宿主在 `execute_system_modules` 里打的（`dispatcher.py`），
与插件那条 `info` 级「请求插件 … 执行」是**两条不同的日志**；后者没出现，
就说明插件根本没被收集进 provider 列表。

> 补充：真机日志级别为 DEBUG 时，`dispatcher.py` 会额外打出
> `模块方法契约：webhook_parser -> integration` —— 那只是**契约查表**，
> 不代表任何 provider 被调用。**不要把它当成「插件已被调用」的证据**
> （这正是本次误判的一个诱因）。

**对策（已实现）**：`init_plugin` 的启动摘要里增加一行**正面确认**：

```
INFO [Rsync115Sync] 认领钩子已注册（webhook_parser 已向宿主声明）：source=rsync115sync 的平台 webhook 报文会被本插件接管…
```

声明缺失时改为 `error` 级告警。这样「版本对不对」不再需要人肉去核对一条
**不存在**的日志，而是有一条明确的存在性断言。

> 教训：**「我修好了」必须以「产物真的到了运行环境」收尾。**
> 只在本地 commit 而不 push/deploy，等于没修 —— 而由于每轮现象完全一样，
> 这种失误在排查过程中**几乎不可察觉**。跨环境调试时，先确认代码真的到位，
> 再解释现象。

#### 已加的两道哨兵

1. `test_registration_contract.py::test_webhook_parser_is_declared_in_get_module`
   —— 静态断言 `get_module()` 的返回字典里含 `webhook_parser` 键。
   断言的是**返回值**而非「方法名出现在源码里」，后者正是当初误判的原因。
2. `test_registration_contract.py::test_webhook_parser_declaration_returns_the_bound_method`
   —— 运行时真调一次 `get_module()`，核对取到的是**本实例的绑定方法**且
   `__name__ == "webhook_parser"`。只验「是个绑定方法」不够：
   `{"webhook_parser": self._别的方法}` 同样能通过（签名不符在兼容阶段只诊断不拒绝），
   这个「键对值错」的变异体实测**逃过了第一版断言**，故补上按名核对。

#### 同时修掉了测试里的同源缺陷

`_host_chain_route` 这个 harness 当初写的是 `plugin.webhook_parser(...)` ——
**直接调实例方法，绕过了声明表**，因此它复刻不出真机的失效：测试全绿而真机全哑。
现改为经 `_declared_webhook_parser(plugin)` 取 provider，该函数**只**从
`get_module()` 里拿、拿不到就 assert 失败，绝不退回直接调用。
验证：删掉那行声明后，两个成功路径用例（`test_multipart_without_boundary_but_json_content_type_works`、
`test_host_route_with_trailing_slash_is_the_only_working_form`）立即失败。

> 教训与 §9.14 的「端到端闭环用例」同源，但更进一层：
> **测试替身的真实度要用「它能否复现已知故障」来衡量。** 一个绕过了真实取用路径的
> harness，比没有 harness 更危险 —— 它给出的是虚假的安心。

### 9.16 「请求到了宿主、插件一行日志都没有」的两类成因（真机实测）

> 📌 **本节的两个成因都真实存在并已修复/文档化，但当时它们都不是那次故障的真因** ——
> 真因是 §9.17（`get_module()` 从未声明 `webhook_parser`）。本节仍有价值（两类坑
> 确实会独立触发），但阅读时请连着 §9.17 一起看：**先确认链路接通，再看本节。**

现象是用户原话：「MP平台可以看到webhook请求但看不到具体信息，rsync115sync插件
看不到任何日志」。之所以难，是因为**现象与「插件没被调用」完全一致**，
而实际原因都在更前面。

联调中先后踩到**两个**同类成因，**都不在插件侧**，且都会让插件彻底沉默：

| | 成因 A：尾斜杠 307 | 成因 B：`Content-Type` 不匹配 400 |
|---|---|---|
| 触发 | 地址写成 `/api/v1/webhook?token=...`（少尾斜杠） | 声明 multipart 却发裸 JSON（无 boundary） |
| 失败位置 | **路由层**（还没读 body） | 读 form 时（provider 调度之前） |
| 客户端看到 | `307 Temporary Redirect` | `400 Missing boundary` |
| 隐蔽度 | **更高** —— 307 看着像「已投递」 | 至少是个明确的错误码 |

两类都属于**「请求到过宿主、但从未进入插件」**，因此本插件（以及任何 provider）
都没有机会留下日志。下面分别记录成因与判据。

#### 成因 A：地址缺尾斜杠 → 307，请求根本到不了端点

宿主把 webhook 端点注册为 `@router.post("/")`（`app/api/endpoints/webhook.py:22`），
再经 `app.include_router(..., prefix="/api/v1/webhook")`
（`app/api/routers.py:66` + `app/startup/initializers/routers.py`）挂载，
因此最终地址是 **带尾斜杠**的 `/api/v1/webhook/`。请求少了尾斜杠时，starlette 在
**路由层**就返回 307 并指向补斜杠的地址 —— 既没有解析请求体，也没有调用 provider。

实测（复刻宿主路由形态）：

```
POST /api/v1/webhook?token=t&source=rsync115sync   -> 307  location: .../api/v1/webhook/?token=...
POST /api/v1/webhook/?token=t&source=rsync115sync  -> 200  正常
```

**为什么它比 400 更难查：** 307 在多数发送端看来像「已成功投递」—— 因为静默跟随
重定向后拿到的确实是 200。真正的失败只体现在**重定向会丢掉 POST body 与部分
请求头**，以及插件侧彻底的沉默。用户发送端日志里那条 307 是唯一线索。

> 🚨 **测试也会掩盖它：starlette `TestClient` 默认 `follow_redirects=True`。**
> 用它写这条用例会**自动跟到带斜杠地址并返回 200、全绿通过**，而真机上的发送端
> 未必跟随。因此本组用例统一用 `follow_redirects=False` 的客户端
> （`_host_chain_route_noredirect`）。这个「测试比真机宽松」的陷阱值得单独记一笔 ——
> 它会让一个真实故障在测试里**永远无法复现**。

**当时另一个反直觉之处：两个端点的斜杠要求正好相反。**

| 通道 | 地址 | 尾斜杠 |
|---|---|---|
| A 平台链路 | `/api/v1/webhook/` | **必须带**（注册为 `/`） |
| B 自建端点（已移除） | `/api/v1/plugin/Rsync115Sync/webhook` | 不能带（注册为 `/webhook`） |

用户按宿主习惯给自建端点补斜杠，同样会拿到 307 + 零日志。

> 📌 **通道 B 已于 2026-09-22 移除**（9.18），所以「两边要求相反」这个坑本身
> 也消失了 —— 现在只有一条规则：**平台链路的地址必须带尾斜杠**。
> 保留这段是因为它记下了更值钱的一课：**同一份「斜杠」知识在两个入口上是
> 相反的，而这正是「多一个入口 = 排查分支翻倍」的具体形态** ——
> 文档每加一行「注意 A 相反」的说明，都在给 9.18 的拆除决定投一票。
>
> 对应用例：`test_host_route_with_trailing_slash_is_the_only_working_form` 保留；
> `test_self_endpoint_requires_no_trailing_slash` 随端点删除。

#### 成因 B：`Content-Type` 与 body 形态不匹配，请求在进入插件前就被拒

宿主端点在调用任何 provider（含本插件的 `webhook_parser`）**之前**先做
`form = await request.form()`（`app/api/endpoints/webhook.py`）。若发送端声明
`Content-Type: multipart/form-data` 却发**裸 JSON body**（**没有 boundary**），
starlette 直接抛异常 → **400 `Missing boundary in multipart`**，
body 为空。此后：

- 插件**一行日志都没有** —— `webhook_parser` 根本没被调用。
- 宿主日志里只有一条 400、**内容为空**，看不出是什么报文、也看不出该查哪里。
- 「平台能看到 webhook 请求」= 请求确实到了宿主，只是被路由前的解析挡掉。

发送端的 `Content-Type` 下拉框很容易选中 `multipart/form-data`
（用户当时贴的配置正是 `Content-Type: Multipart/form-data` + JSON body）。
**修法在发送端：Content-Type 改成 `application/json`**（或不带该头）。
同一个报文、仅改这一个请求头，行为从「400 + 插件零日志」变为「200 + 正常入队」，
已由 `test_multipart_without_boundary_but_json_content_type_works` 与
`test_host_route_rejects_multipart_without_boundary` 两条用例钉住。

#### 为什么插件兜不住这两类失败，以及为什么删掉了「兜底」代码

一度在本插件里写过 `_probe_webhook_route` / `_log_webhook_route_failure`
（约 96 行），想在中转失败时留下路由级日志。**这是错的，已全部删除**：成因 A 的
307 发生在**路由层**、成因 B 的 400 发生在 **provider 调度之前**，SDK 也没有暴露
任何「路由中间件」钩子，因此这段代码永远不可能被执行 —— 留着只会让后人以为
「这里有兜底」。判据是**可达性**：一段永远不会运行的容错代码，比没有更危险。

能做的只有两件，都不是兜底而是**可观测**：

1. `claimed` 计数与报文样本落在**解析入口**（`_note_webhook_claim_attempt`），
   让用户能区分「没到插件」与「到了但认领失败」。这两类成因之下 `claimed` 恒为 0，
   因此「到达 = 0」这条判据同时覆盖 A 与 B，不需要分别判断。
2. 在 `webhook_parser` 的**上方注释**、`USAGE.md`（含「到达=0 时按序查这三项」
   的清单）与看板里写明这两个失败模式。地址与 Content-Type 都属于**发送端配置**，
   插件只能把「去查什么」告诉用户。

#### 对比：自建端点不受成因 B 影响（可作退路）

> 📌 **本节记录的退路已于 2026-09-22 随端点一起移除**（见 9.18）。
> 下面的对比保留为历史依据 —— 它是「拆除通道 B 要付出什么代价」的原始出处。
> 移除后，成因 B 的排查终点是**发送端 Content-Type**（或反向代理）。

同一个「声明 `multipart/form-data`、实发裸 JSON」的请求，打宿主是 400，
打自建端点是 **200 + 正常入队**。差别不在本事，在**读取顺序与容错**：

| | 宿主端点 | 自建端点 `_ingest_from_request` |
|---|---|---|
| 解析顺序 | `request.body()` → **`request.form()`** → provider | **`request.json()`** → 原始 body → `request.form()` |
| 失败处理 | 不兜异常，直接 400 | 每段各自 `try/except`，失败就往下退 |

两个端点收到的 body 都是完整的（同一个请求），只是自建端点**先试 JSON**、
失败也不会把异常抛出路由，于是同一个报文照样解析出来。当时的实测依据是
`test_self_endpoint_survives_the_same_bad_content_type`（真 starlette 请求，
该用例已随端点一并删除）。

> ⚠️ 但它**不能**同时兜住成因 A：自建端点同样受尾斜杠重定向影响，只是方向相反
> （见上表）。换通道时斜杠要**去掉** —— 这条也随端点移除了。
>
> 也不要把它读成「自建端点更好，宿主那条路可以不管」：宿主链路鉴权交给宿主、
> 有宿主日志，是用户的默认用法；改对发送端才是正解，自建端点只是退路。
> 这个判断在 9.18 的拆除决定里被沿用了：既然它只是退路，而退路本身又要
> 四条配置与一套防护链来维持，那就不如不要。

#### 教训

**⓪ 先验证「链路是否接通」，再排查链路上的每一步。** 本节两个成因都是在
「插件已被调用」这个**错误前提**下排查出来的 —— 也就是说，它们是排查过程中
顺带发现的真实坑，而不是那次故障的原因。真正的根因（§9.17）一直没被怀疑，
恰恰因为它**没有任何观察入口**：宿主不报错、插件无日志、`grep` 还会命中方法定义。
**排查一个「完全没有信号」的失效时，第一步应当是问「我怎么知道它被调用了？」，
并为此造一个能观测的事实（哪怕只是一条 debug 日志）—— 而不是先假设它被调用了。**

**①「什么都没发生」必须能被拆成可区分的几种情况。** 本次三类失败
（请求没到插件 / 到了但认领失败 / 认领了但没入队）在改动前**观察到的现象完全相同**，
而修法分别在发送端地址、发送端 Content-Type、插件映射配置。可观测性的价值就在这里：
不是多打日志，而是让**不同的原因在现象上可分**。

**② 测试环境的宽松默认值会让真实故障无法复现。** `TestClient` 的
`follow_redirects=True` 会把成因 A 变成一个 200 的绿测试 —— 这类「测试比真机宽松」
的差异，比测试覆盖不足更危险，因为它给出的是**虚假的通过**。写跨层用例时要问一句：
「这个断言在真机上会因为什么而不成立？」

> 顺带确认了 §9.14 末尾「一个仍待真机确认的点」：`webhook_parser(self, body, form, args)`
> 的签名与宿主调用方式一致，真机可正常取到值（json_object 与 item_path 两条通路均已走通）。

### 9.15 9KG 场景：为什么目录展开和报文样本是必需的

这一节记录本功能**真正的目标场景**与由此确定的两项设计，避免后人把它们当成
「顺手加的便利功能」而简化掉。

#### 目标场景

9KG 类内容**平台无法识别**，因此永远不会有「整理完成」事件 —— webhook 不是
补充来源，是**唯一**来源。它的入库流程是：

```
另一个工程（下载/整理）→ 通知本插件 → 冷却队列 → 同步到 115
```

两个由此而来的硬约束：

1. **发送端的报文形态在开发期未知。** 那个工程不在本仓库里，字段名、是推目录还是
   推文件、有没有 `Event` 字段，都只能边跑边看。用户原话：「我不知道发送端会传递
   什么样的参数」。因此**不能把候选字段表当成一劳永逸的清单** —— 必须有一条
   「把未知报文原样留下来」的通路。
2. **「通知入库」最自然的载体是目录。** 那个工程刚下完一部电影/一季，手里有的是
   目录路径；要它自己遍历目录、逐个文件发通知，既不自然也容易和插件算得不一样
   （它不知道你的扩展名白名单与排除规则）。

#### 目录展开（`_expand_ingest_path`）

**必须放在扩展名过滤之前。** 目录名没有扩展名，直接进白名单必然被判 `skipped`，
而端点会返回 `success=True, 已入队 0 个` —— 发送端据此认为投递成功、不再重试，
用户看日志只看到「成功」。这是最坏的失败形态。

实现要点（每一条都被一条测试钉住）：

- 展开出的文件走**与直接推文件完全相同**的判据（`_enqueue_one_path`）。共用一份实现
  是硬要求，否则「推目录」与「推文件」迟早行为漂移。
- 扩展名白名单与**排除目录**（`@eaDir` / `#recycle`）在遍历层就地剪枝，复用
  `paths.valid_exts_of()` / `paths.excluded_dir_names()` —— 与同步扫描同一份口径。
- 展开有上限（`DIR_EXPAND_LIMIT = 500`）且**截断必须留痕**。无上限意味着「推一个
  9KG 根目录」能把冷却队列一次灌进上万个条目，115 风控配额随之被打满。
- 目录内无可用文件时**单独留 info**（`expanded` 计数 + 一条日志）。否则
  「推了个目录、什么也没发生」与「推了个不存在的路径」在日志上无法区分，
  而这两者的排查方向完全不同（改扩展名配置 vs 查挂载）。

> ⚠️ **返回值用 `is None` 判据，不要真值判断。** `_expand_ingest_path` 返回
> `None`（普通文件）/ 列表（目录，可为空）。写成 `if expanded:` 会让「目录内无可用
> 文件」这个合法的空列表掉进单文件分支，于是目录被当成文件做扩展名校验 ——
> 正好退回到本函数要修的那个 bug。**这个坑在实现当天踩过一次**，故在此明写。

#### 报文样本（`sample_payload`）

`last_payload_shape` 只记**结构**（键名 + 类型，不记值），这是为日志做的取舍。
但它答不出对齐字段真正需要的问题：**值长什么样**。`{movie: {file: str}}` 里那个
`file` 到底是 `/vol3/x.mkv`（该加进候选表）还是 `12345`（媒体库 ID，加了也没用），
只有看到值才知道。

因此新增一份**保留值**的最近报文样本：

- 只留最近 `WEBHOOK_SAMPLE_LIMIT = 5` 条（环形）。这是排障窗口，不是审计日志。
- **只在「取到路径」与「未识别」两个点位采样**，不在播放类噪声上采 ——
  后者会把环形缓冲刷满，而那正是最不需要看的一类。
- 逐字段截断（`SAMPLE_VALUE_MAX = 200`）并对 `token` / `secret` / `authorization`
  等字段脱敏为 `***`。看板是明文展示的，不能把可用凭据抄在屏幕上。
- 看板倒序展示（新的在前）：排障时用户刚推的那条必须在最上面，否则会照着一条
  几小时前的历史记录去对齐字段。
- 样本要**逐字可抄**，因此走 `<pre>` + `white-space: pre`（不折行）。折行会把
  `"item_path"` 断成两行，抄过去就成了两个错字段。

#### 对着真实场景验过的形态

```
推目录 /volume3/9kg/某电影 (2024)/（内含 2 个 mkv + 2 个 srt + poster.jpg + @eaDir/thumb.mkv）
  → added=4、expanded=1
  → 队列: movie.1080p.mkv / movie.2160p.mkv / movie.en.srt / movie.zh.srt
  → poster.jpg 被扩展名白名单挡掉；@eaDir/thumb.mkv 被排除目录挡掉
```

#### 9.15.1 `all_ext` 映射：推**单个文件**时必须带上同目录其它文件

真机反馈（2026-09-22，用户原话）：

> 9KG 下配置的是所有文件都上传，在 webhook 入库后，进行上传时，没有把媒体文件
> 所在目录下其他文件一并上传。

**成因不是解析，是入队粒度。** 整条链路（扩展名白名单 → 冷却队列 →
`--files-from`）**以文件为单位**：发送端推来一个文件路径时，只有那一个文件具备
「冷却是它、被同步的也是它」的资格，同目录的其它文件永远拿不到冷却资格，
于是永远不上传。而对 `all_ext` 映射来说这是自相矛盾的 —— 配置项的字面含义就是
「这个目录下的文件全都要上传」，用户不会预期「只有被 webhook 点到名的那一个」。

第九节其余部分讲的都是**推目录**那条路（`_expand_ingest_path`），它本来就对；
漏洞在**发送端只推文件**时。发送端不保证推目录（它手里可能只有「整理完成的那
一个文件」这个信息），所以兜底必须由插件做：`_collect_sibling_files()`。

设计边界（每一条都有测试钉住，见 `tests/v3/rsync115sync/test_all_ext_ingest.py`）：

| 决定 | 为什么 |
| --- | --- |
| **只在 `all_ext` 生效** | 默认映射的上传范围是扩展名白名单；顺手扩大范围等于绕过用户「只同步视频+字幕」的配置意图，每次入库都静默多传文件、多耗 115 风控配额。 |
| **只取同一层，不递归** | 兜的是「一部电影一个目录」这个真实形态。递归会顺手把 `Season 01/` 拉进来，那是「推目录」这条路的语义 —— 两条路的边界必须清晰，否则一次通知能膨胀成整季甚至整库。 |
| **硬上限 `SIBLING_EXPAND_LIMIT = 300`，且截断留痕** | 与 `DIR_EXPAND_LIMIT` 同一理由：异常目录（整库塞进一个目录）不能把冷却队列一次灌满。 |
| **复用 `expanded` 计数** | 与目录展开是同一语义（一次通知膨胀成多个文件），另起一个名字会让「为什么入队 5 个」出现两个可能答案。 |
| **兄弟文件逐个走 `_enqueue_one_path`** | 扩展名／忽略清单／幂等／待补扫升级四项判据完全共用。若在展开处自行放行，就会出现「忽略规则在目录路上生效、在文件路上失效」。 |

两个容易写错的细节，都在实现时踩过或差点踩到：

1. **上限要含被点到名的那个文件。** 先枚举同级文件到满、最后再把被点名的塞进去，
   总量会变成 `LIMIT + 1` —— 这类上限一旦是「大约」就等于没有。正确写法是先给它
   留一个位置（`room = limit - 1`）。
2. **返回值用 `is None` 判据**，与 `_expand_ingest_path` 同一条理由：`None` = 不适用
   （不是 `all_ext`），列表 = 适用。写成真值判断会让分支选错。

顺带收口的一处重复：`._*` / `.DS_Store` 这个垃圾文件判据原先在**三处**各写一遍
（补传前置扫描、双向对账、目录遍历），现统一为 `paths.is_junk_file_name()`。
漏写任何一处都会表现为「明明排除过的 macOS 垃圾文件被真的传上了 115」，
而那是**真实占用配额**的上传。

### 9.14 认领通道收到的是什么、日志打在哪里（自查用）

`source=rsync115sync` 走的是**宿主链路**（通道 A），不是自建端点。两段都要看清：

**① 认领阶段 —— 按「是否声明发给本插件」分档记日志。** `webhook_parser` 要在宿主
每个 webhook 报文上被调用一次，多数时候那报文不是给我们的，因此**不能无条件打
通知级日志**（会刷屏）。第一版据此写成「一律静默」，结果踩了坑：发送端
`source=rsync115sync` 确实配了、插件也确实什么都没做，而**两边日志都是空的**
（用户原话：「rsync115sync插件看不到任何日志，所以需要增加点日志来定位问题」）。

现在按「发送端是否显式声明收件人」分档，**声明了就必须留下可自查的线索**：

| 情形 | 日志级别 | 内容 |
|---|---|---|
| 报文没声明发给本插件（宿主 Emby 报文等高频路径） | `debug` | 一行「未声明发往本插件」 |
| 声明了，但**取不到任何路径** | **`info`** | 说明 + `describe_payload` 报文结构摘要 |
| 声明了，但路径**不属于任何映射** | **`info`** | 取到的路径 + 当前配置的全部映射源目录 |
| 声明了且认领成功 | 无 | 唯一证据是宿主广播的 WebhookMessage 被 `_handle_webhook_event` 接住（见下） |

两条 `info` 的分工是刻意的，因为它们指向**完全不同的修法**：前者改发送端字段名，
后者改插件映射配置。合成一条会让用户无从下手。

**另有 `claimed` 计数（看板「平台解析入口到达」）**，由 `_note_webhook_claim_attempt`
在**解析入口**统计 —— 与 `_handle_webhook_event` 的「收到事件」计数分工不同：
后者只覆盖成功认领的路，前者覆盖**所有声明发给我们的报文**。只有前者能区分
「报文没到插件」与「到了但认领失败」，而这两种情况在日志上曾**完全一样**（都是空）。

**② 入队阶段 —— 一条 INFO 日志。** 认领成功后宿主把 `WebhookEventInfo` 原样广播回来：

```
INFO [Rsync115Sync] v0.2.0 Webhook(宿主) 监听到 3 个新入库文件（event=library.new，
     channel=rsync115sync，server=rsync115sync，路径来源=item_path，json_object.paths），
     已加入 2h 延迟冷却队列: S01E01.mkv; S01E02.mkv; S01E03.mkv
```

日志里的 `路径来源=` 会列出**实际贡献了路径的每一处**（可多项逗号分隔）。
它是排查「字段没对齐」的唯一线索，因此取值即契约：

| 路径来源 | 含义 |
|---|---|
| `item_path` | 宿主解析器给的规范字段 |
| `json_object.Item.Path` | 原始 Emby 报文形态 |
| `json_object.paths` | **本插件认领时写入的多路径清单**（见下） |
| `候选字段` | 非 Emby 发送端，靠候选字段表命中 |
| `未识别` | 一处都没取到（调用方会改记 debug + 看板的报文结构摘要） |

**③ 认领时返回的数据项。** 返回的是宿主的 `WebhookEventInfo`（**不是**自造类型 ——
宿主直接把它交给 eventmanager，类型不符同样静默结束），字段固定为：

```
event="library.new"           # 固定：本插件只处理入库
channel="rsync115sync"        # = WEBHOOK_TARGET，**刻意不等于 emby**（见 9.11）
server_name="rsync115sync"
item_path=<命中的第一个路径>   # 契约只允许单个值
json_object={"paths": [...]}  # 命中的**全部**路径 —— 多出来的只能放这里
```

> #### ⚠️ `item_path` 的单值上限：认领时多路径必须靠 `json_object.paths` 带回
>
> 这一处曾丢文件，是「两端各自看都对、拼起来才错」的典型：`webhook_parser` 正确地把
> 命中的全部路径写进 `json_object["paths"]`，但接收侧 `extract_paths` 当时写成
> **「`item_path` 有值就直接返回」** —— 于是一次推 3 个文件只入队第 1 个，
> 后 2 个静默消失，而认领日志显示完全成功。修复是让 1 与 2 两处来源**合并并去重**
> 而不是短路（Emby 真实报文两处指向同一文件，去重后行为不变）。
>
> 教训与 3.8.1 同一类：**往返一致性要有跨两端的用例**。分别断言「认领返回了什么」
> 和「extract_paths 能读什么」都通不出这个 bug —— 必须走完整往返
> （`webhook_parser` → 宿主广播 → `_handle_webhook_event`），
> 见 `test_claimed_multi_path_payload_enqueues_every_path`。

```
1. 新增 Webhook 入库（补充来源）
现有监听挂在宿主「整理完成」事件上，看不到手动放入、外部工具搬入、整理事件漏发这三类入库。Webhook 作为补充来源覆盖它们 —— 不是替代：同一条入库走两条路进来时，冷却队列的重复检测保证不重复上传、不刷新冷却计时。
发送端只需把 webhook 地址指向平台入口 http://<moviepilot>:3001/api/v1/webhook/?token=<API_TOKEN>&source=<来源名>，本插件侧无需额外配置。Emby 后台（通知 → Webhooks）填 Emby 实例名即可；宿主不认识的发送端（MDC-ng、自建脚本）用同一个地址，把 source 换成 rsync115sync 由本插件认领。

2. 认领宿主 webhook 解析
宿主的 webhook_parser 是「插件优先、非空即短路」的模块方法，任何插件返回非空结果都会让宿主的 Emby/Jellyfin/Plex 解析器不再被调用。不实现它等于赌别的插件永不实现该钩子，赌输则整条平台 webhook 链静默失效（插件一行日志都不会有）。
本插件只认领显式声明发给自己的报文（?source=rsync115sync 或请求头 X-Webhook-Target: rsync115sync），其余一律返回 None 让宿主解析器照常接棒。刻意不按 channel 认领：宿主 Emby 解析器产出的 channel 正是 emby，按它认领会抢走宿主本可正常处理的报文并掐断宿主功能。
只处理入库类事件（library.new / library.update 等），播放、标记、收藏类事件一律忽略 —— 它们同样携带 Item.Path，不过滤会让「用户每看一集就重新入队并再上传一次」。

3. 移除自建的匿名 webhook 端点
原端点 POST /api/v1/plugin/Rsync115Sync/webhook 及其四条防护配置（端点开关、来源 IP 白名单、密钥、路径白名单）与看板相关字段已整体移除。该端点存在的唯一理由是「宿主不认识 MDC-ng，报文到不了插件」，但真机验证表明宿主端点对任何发送端都收得下报文，只是不认识发送端身份 —— 认领逻辑补上之后，这个免鉴权入口换来的场景窄到只剩「发送端连 URL 查询串都改不了」，却要维持四条可能因用户没配而形同虚设的防护，以及两套错误语义（两个入口的尾斜杠要求还是相反的）。
移除后本插件不再有任何免宿主鉴权的端点，入库来源只剩平台链路一条，鉴权由宿主 verify_apitoken 默认生效，无需用户额外配对什么。
升级注意：此前主动开过该端点的用户，请把发送端地址改回平台入口，旧地址会返回 404；另外发送端 Content-Type 配错时不再有过往那种「先试 JSON」的退路，需修正发送端或经反向代理补 header。

4. 支持「推目录」
发送端通知入库时直接发目录路径即可，插件自行展开成文件（只收扩展名白名单内的文件、跳过 @eaDir 等排除目录）。此前目录会被静默吞掉 —— 请求返回 success=True、入队 0 个，发送端据此认为投递成功而不再重试。展开有 500 个文件的上限且截断留痕（防止一次灌爆冷却队列、打满 115 风控配额）；目录内无可用文件时单独记日志，与「路径不存在」区分开。

5. 修复 all_ext 映射只上传被推送的那一个文件
勾选「同步所有文件类型」意味着该目录下的文件全都要上传，但入库链路以文件为粒度，发送端推来一个文件路径时，同目录的其它文件（同名不同扩展名的字幕/音轨/封面、发布组塞进同目录的 .nfo/.jpg）永远拿不到冷却资格，也就永远不上传。现补上兜底：单文件入库时把同目录同级文件一并纳入同一套判据（扩展名 / 忽略清单 / 幂等 / 待补扫升级）。
边界刻意收窄 —— 只在 all_ext 映射生效、只取同一层不递归（递归会顺手把 Season 01 拉进来，那是「推目录」这条路的语义）、硬上限 300 且截断留痕。

6. 修复入库漏文件与文件卡死
一次推送多条路径时只有第一条入队、其余静默丢失（item_path 按宿主契约只能放单个值，已改为合并 json_object 中的全部路径并去重）；「已在待补扫清单」被误判为重复投递导致文件永久卡死（既不在冷却队列、也不会被任何一轮同步取走），现改为升级进正常冷却队列。

7. 修复「平台能看到 webhook 请求、插件一行日志都没有」
两种成因，且现已可区分：① 地址缺尾斜杠 —— 宿主端点注册为 /api/v1/webhook/，少一个斜杠会被 starlette 在路由层重定向（307），请求从未进入插件，而多数发送端把静默跟随后的 200 当成投递成功；② 发送端 Content-Type 与 body 形态不匹配 —— 声明 multipart/form-data 却发裸 JSON（无 boundary）时，宿主在调用任何 provider 之前解析表单即返回 400，插件根本没被调用（仅把 Content-Type 改为 application/json，同一报文即正常入队）。
两者都属发送端配置，插件侧兜不住，因此改为让失败可区分：认领阶段按「发送端是否显式声明收件人」分档记日志；看板新增「平台解析入口到达」计数（统计所有声明发给本插件的报文而非仅成功认领的）与「最近报文样本」（含值、截断脱敏、只留最近 5 条）。因此「到达数 = 0」即可判定请求没到插件，直接去查尾斜杠与 Content-Type。

8. 修复认领通道完全失效（真机「插件零日志」的真因）
插件实现了 webhook_parser 却从未在 get_module() 里声明它，而宿主只从 get_module() 返回的映射里收集 provider，因此只写方法定义等于死代码 —— 宿主不调用、不报错、无任何日志，source=rsync115sync 的报文只会交给宿主自己的解析器（它们不认识这个 source，返回 None）。
已修复并加两道哨兵（静态断言声明表含该键；运行时核对取到的是本实例绑定方法）。同时修掉测试里的同源缺陷：测试替身原先直接调 plugin.webhook_parser，绕过了声明表，复刻不出真机的失效（测试全绿而真机全哑），现统一改为经声明表取 provider、取不到即断言失败。

9. 看板补齐 webhook 运行态面板
此前后端 /status 返回了四项计数与报文摘要、使用说明也写了可在看板自查，但页面从未渲染它们 —— 用户按文档去看板只能得到一个空看板并误判为「没生效」。

10. 测试
新增 tests/v3/rsync115sync/test_webhook_ingest.py 与 test_all_ext_ingest.py，全部用例总计 355 项通过，含入队判据、认领边界、真路由契约与「不注册任何免宿主鉴权端点」的哨兵，并用变异测试验证（关掉同目录展开 → 5 项失败；让默认映射也展开 → 2 项反向用例失败）。注意：本机无 MoviePilot 后端，测试在自建桩宿主下执行通过，真机验证仍需自行完成。
```

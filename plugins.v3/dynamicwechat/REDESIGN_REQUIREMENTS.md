# DynamicWeChat（动态企微可信IP）配置页与详情页重设计 —— 需求规格

状态：需求分析产出，等待计划确认。本文档不修改任何代码。
按仓库流程（docs/Plugin_Dev_Workflow.md），本文档对应第 1 步「设计 UI」的产出物；
下一步是据此罗列开发计划，确认后才动代码。

## 现状核实

- 插件/目录/索引版本：`plugins.v3/dynamicwechat/`，类 `DynamicWeChat`，
  `plugin_version` 3.0.2 = 索引 `package.v3.json` version 3.0.2 = history 首项 3.0.2，一致。
  渲染模式：未覆写 `get_render_mode()`，即 vuetify JSON 表单模式（非 Vue 模式，
  无 `dist/`，无联邦 CSS 门禁负担）。测试仅有 `tests/v3/dynamicwechat/test_v3_contract.py`。
- 已存在的相关实现（文件:行，均在 `plugins.v3/dynamicwechat/__init__.py`）：
  - `get_form()` 1565–1732；`get_page()` 1734–1864；`get_api()` 2002–2012（仅 `/test_notify`）；
  - `init_plugin()` 157–251：await_ip 静默复位 214–215；cron 默认值 165 与 198 的覆盖关系；
    应用ID 缺失仅写日志 241–244；
  - 保活循环 `_refresh_cookie_loop` 299–332（独立 10 分钟 cron，46 行 `_refresh_cron`）；
    IP 检测循环 `_check_ip_loop` 334–369（用户 cron）；
  - `refresh_cookie()` 1153–1255：三态结论、`_none_streak` 1190、连续 3 次告警 1201–1205、
    寿命累加 1243–1249；
  - `check_login_status()` 1257–1409：三态 docstring 1262–1273，验证码面板 30 秒等待 1331–1338，
    `_last_check_result` / `_login_confirmed_by` 副作用 1268–1273；
  - `check()` 561–590（cookie 失效时按 await_ip 分支）；`ChangeIP()` 824–864；
    `_send_cookie_false()` 932–1001；`_push_qr_code_async()` 1003–1097；
  - 验证码入口：`talk()` 1960–1978（以 ？ 结尾）、`get_command()` 1980–2000（`/wxcode`）；
  - magic string：`||wan` 解析 218–228；`ids||url1,url2` 覆盖探测 URL 716–722；
    `||Q` 静默标志 helper.py 163–166；渠道识别 helper.py 184–194（仅 ServerChan/IYUU/PushPlus）。
- 详情页当前只展示两样：二维码/过期时间（1738–1777）与 Cookie 寿命条（1778–1801），
  加一个「测试通知推送」按钮（1842–1862）。
- 与诉求的差距：后端已有的运行时状态（登录三态、连续无结论计数、两个循环、
  验证码等待、通知通道识别结果）在两个页面上**完全不可见**；现有两处信息还挂错了条件
  （见问题清单 P2/P3）。

## 原始诉求与理解

- 用户原话：为详情页（get_page）与配置页（get_form）「根据代码分析到的业务逻辑重新设计页面」，
  用户认为当前两个页面设计不合理。
- 我的理解：页面的信息量与真实业务状态脱节——插件内部已经区分了登录三态、两个独立循环、
  验证码等待、多通道通知等精细状态，但用户在页面上只能看到二维码和一条 Cookie 寿命条，
  且寿命条在多种失败场景下整体消失。重设计要把「代码里知道的状态」变成「页面上看得见的状态」，
  并按首屏准入判据重排配置项、修正 magic string 的可发现性。
- 差异或歧义：用户没有具体指出哪些点不合理，以下问题清单是逐条对照
  Plugin_Dev_Workflow 推导的，需用户确认哪些在本轮范围内（见未决问题）。

## 目标

一句话：用户打开详情页就能回答「Cookie 现在到底活着吗、两个循环在跑吗、卡在哪一步」，
打开配置页就能不看外部文档填对所有必填项并知道每个开关当前是否真的生效。

## 非目标

- 不改任何后台业务逻辑：循环行为、三态判定、通知发送、验证码流程全部保持现状。
- 不修两个已知待办缺陷（ChangeIP 二维码分支未置 `_cookie_valid=False` 841–849；
  `_push_qr_code_async` 的 `if self._my_send:` 守卫 1024 挡住仅 MP 通知用户）——
  已在 DEVELOPMENT.md 记录为独立待办，本轮页面重设计只负责把这些状态**如实显示**，
  不改变产生状态的行为。若用户拍板顺带修，另行记入计划。
- 不迁移 `UpdateWeChatIp`。
- 不做实时轮询刷新：详情页仍是「进入时快照」，与现状一致（不加 WebSocket/定时拉取）。
- 不把验证码输入默认做成页面交互（见未决问题 1，先只做等待状态可见）。

## 现状问题清单

逐条「现状（行号证据）→ 违反的规则」：

- **P1 四态缺失（工作流 §1.4）**：配置页每个开关只有 label，没有任何状态提示。
  `await_ip`（1623–1632）甚至整体不渲染——未填第三方 Token 时开关直接消失，
  用户无从得知「为什么别人有这个开关我没有」；且 `init_plugin` 214–215 会在
  other_channel 为空时把它静默复位为 False，开关「看起来开了、保存后没了」，无任何提示。
- **P2 提示挂错对象（§1.5）**：详情页 Cookie 寿命条（含红色失效态）整体 gated 在
  `_is_special_upload and self._enabled`（1778）。`_is_special_upload` 只在扫码登录、
  CookieCloud 写回成功或 cookie 头含 `_upload_type=A`（880、922、929、1142–1143）时为 True；
  cookie 失效、未启用、或 cookie 来自无标记的 header 时，**红色失效条整个不渲染**——
  恰恰是最需要看到它的时候它消失了。这正是 §1.5 的反例模式（提示嵌在被推到极端就消失的条件下）。
- **P3 二维码状态混淆（§1.4）**：1738–1746 把「已过期」「从未有任务」「插件未启用」三种情况
  合并成一个紫色条「二维码已过期或没有扫码任务」（1740–1741），三态互不分辨；
  且 get_page 有写副作用（1742 置 `_qr_code_image = None`），getter 改状态。
- **P4 magic string 无解释（§1.4/§3.5）**：`||wanN`（218）、`ids||url1,url2`（716）、`||Q`
  （helper.py 163）三个语法共用 `||` 分隔符，配置页 placeholder 均未提及：
  应用ID placeholder（1675）只说逗号分隔；通知方式 placeholder（1649）写「支持微信、
  Server酱、PushPlus、AnPush等Token或API」——其中**微信与 AnPush 根本不被 MySender 识别**
  （helper.py 184–194 只认 sct 前缀/含 iyuu/其余按 PushPlus），placeholder 在教用户填无效内容。
  两条 VAlert（1699、1711）放在页面最底部，离它们解释的字段隔了四行，违反 §1.5。
- **P5 测试按钮位置（§1.2）**：「测试通知推送」（1842–1862）挂在详情页，但它测试的是
  **配置**的正确性——新用户配完通知后的第一个动作就是验证，此时他恰好不在详情页。
- **P6 验证码等待不可见**：`check_login_status` 验证码面板会等待 30 秒（1331–1338），
  期间用户唯一被告知的方式是日志；扫码后盯详情页的人看不到「正在等验证码、该怎么提交」。
  入口（？结尾发到企微应用 / `/wxcode` 命令，1960–1978、1994–1999）只存在于通知文案与日志。
- **P7 必填项无校验反馈**：cron 标注 [必填]（1642）但留空时 init_plugin 165 的默认值被
  198 的 `config.get("cron")` 覆盖为 None，IP 检测循环 296–297 干脆不启动——静默不跑，
  页面无任何提示。应用ID 必填同理，只写日志（241–244）。
- **P8 循环状态不可见（§1.4）**：保活循环（10 分钟一次，独立 cron 46 行）与 IP 检测循环
  （用户 cron）是两个独立生命周期（init_plugin 295–297 分开启动），详情页完全没有呈现：
  上次检测结果、`_last_check_result` 原因（timeout / captcha_incomplete 等，1268–1271）、
  `_ip_changed`、当前 IP、连续无结论告警（1201–1205）全部只在日志里。
- **P9 通知通道有效性不可见**：MP 内置通知实际送达结果按宿主契约 `post_message` 返回 None
  不上报失败（CLAUDE.md「post_message 返回 None」条），页面更无从体现；第三方通道的
  识别结果（ServerChan/IYUU/PushPlus，helper.py 184–194）与上次发送错误字符串
  （`_send_cookie_false` 975–977 可拿到）也都没有展示。
- **P10 隐藏配置项**：`cookie_header` 在配置模型与 `__update_config`（1556）中存在，
  `get_cookie_async` 1124 还会拿它兜底，但 get_form 里**没有对应输入框**——
  一个真实生效却永远不可编辑、也不可见的字段。
- **P11 新能力无状态**：`pinned_ips`（1680–1690）与 `company_domain`（1654–1666）是
  3.0.0/3.0.2 新增能力，各占一行，无四态提示（DDNS 解析失败时 601–604 只写日志并放弃操作，
  用户在页面上看不到「为什么这次没改IP」）。

## 验收标准

1. Given `_cookie_valid=False`、`_is_special_upload=False`、`_enabled=True`，
   When 渲染 get_page，Then 返回结构中包含一条红色失效条，文本含「Cookie 已失效」，
   不因 `_is_special_upload` 为假而消失。
2. Given `_enabled=False`，When 渲染 get_page，Then 顶部出现灰色「插件未启用」条，
   Cookie 与二维码区不显示任何成功色（绿）内容。
3. Given `_none_streak >= 3`，When 渲染 get_page，Then 出现橙色网络告警条，
   文本说明「连续多次无法确认登录状态」及后果，不含 Markdown 标记。
4. Given `notification_token` 为空，When 渲染 get_form，Then 「IP变动后通知」开关仍然存在
   （可见但禁用或带警告说明），文案说明保存后会被自动关闭；不出现开关整体消失的情况。
5. Given 通知方式 placeholder 与帮助文案，Then 不再出现「微信」「AnPush」等
   MySender 不识别的渠道名；`||` 多通道与 `||Q` 静默语义在紧邻该字段的说明中出现。
6. Given 详情页渲染结果，Then 不包含「测试通知推送」按钮；Given 配置页通知卡片，
   Then 包含该按钮（api 路径 `plugin/DynamicWeChat/test_notify` 不变）。
7. Given get_page 被连续调用两次，Then 第二次调用不改变 `_qr_code_image`
   （渲染无写副作用）。
8. Given 二维码从未生成（`_qr_running=False` 且无图），Then 详情页显示中性灰
   「当前没有扫码任务」；Given 任务运行中且未过期，Then 显示绿色条+图片+过期时间；
   Given 任务运行中但已过期，Then 显示黄色「二维码已过期，请重新发起扫码」——
   三种文案互不相同。
9. Given cron 留空或非法，Then 配置页出现可感知提示（保存校验或状态条），
   不再静默不启动 IP 检测循环。
10. Given 详情页全部用户可见文本，Then 无 `**`、无反引号、无内部术语
   （「无结论」「_special_upload」等不得出现，需转译为用户语言）。
11. Given 旧配置值 `1000002||wan2`（未拆字段方案被采纳时），Then 升级后插件仍按
   多WAN 语义解析（迁移兼容）——若采纳拆字段方案，改为「首次保存时自动迁移旧值」。
12. 真机：NAS mp3 容器加载 v3.x.x，配置页五组控件齐全、详情页状态条齐全，
    一轮保活与一轮 IP 检测日志无异常。

## UI 归属建议

说明：本插件是 vuetify JSON 表单模式（无自定义 Vue 页面），移动端不引入
`setting-row-stacked` 等自定义 CSS（那是 Vue 模式规则）；移动端适配靠
每行 `cols=12`（窄屏单列）+ 长文本字段独占整行实现。

### 配置页 get_form

```
┌─ 首屏 · 基础 ─────────────────────────────────────────────┐
│ [启用插件] [立即检测一次] [强制更新IP]        （一行三开关） │
│ 检测周期 cron [必填，非法时行内提示] ← P7                  │
│ 应用ID [必填] placeholder：从企微应用URL末尾获取，           │
│   多个逗号分隔；明确警示「不要填 100000x 开头的自建应用」← P4 │
│ [本地扫码修改IP] ← 首次使用必经步骤（USAGE 第2步），首屏     │
├─ 首屏 · IP 来源（三选一组，当前分散且互相覆盖）← P11       │
│ ○ DDNS域名（优先）  ○ 多WAN（开关+最多出口数数字框）        │
│ ○ 探测URL（默认；自定义URL列表独立字段，替代 ids||url1,url2）│
│   当前生效来源状态行（绿/红，见状态矩阵 DDNS 行）           │
├─ 首屏 · 通知 ─────────────────────────────────────────────┤
│ [MP内置通知] + 状态行（如实说明无法查询送达）← P9           │
│ 第三方Token [textarea] + 紧贴字段的 ||/||Q 说明 ← P4       │
│   识别结果行：已识别 N 个通道 ← P9                         │
│ [IP变动后通知] 恒显示，缺前置时禁用+橙字原因 ← P1          │
│ [测试通知推送] 按钮（从详情页移入）← P5                    │
├─ 折叠 · 高级设置 ─────────────────────────────────────────┤
│ [使用CookieCloud] + 宿主 KEY 未配置的警告态 ← P1           │
│ 固定可信IP pinned_ips + 四态 ← P11                        │
│ （多WAN与自定义URL若用户否决拆字段，则原 magic string 语法  │
│   说明移到对应字段紧邻处）                                  │
└──────────────────────────────────────────────────────────┘
```

归属理由：基础区三开关与两个必填项是「新用户第一个决定」；IP 来源三选一是
「用它需要先填什么」的判断依据（填错来源会静默写错 IP）；通知区是配置正确性的
验证入口（测试按钮）。CookieCloud、pinned_ips 属「用了一段时间才想调」。
底部两条游离的 VAlert（1699、1711）删除，内容并入对应字段的紧邻说明。

### 详情页 get_page

```
┌─ 状态总览 ────────────────────────────────────────────────┐
│ 插件状态条（灰/橙/绿）                                     │
│ Cookie 登录态条（四态，去掉 _is_special_upload 门控）← P2   │
│   └ 连续无结论告警条（_none_streak≥3 时，挂本条之下）← P8   │

│ IP 检测行：cron · 上次结果 · 当前IP(脱敏) · 改IP是否成功     │
```
